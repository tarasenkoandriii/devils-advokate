# Деплой на Vercel Hobby

Монорепо деплоится как **четыре отдельных Vercel-проекта** из одного GitHub-репозитория — тот же паттерн, что уже использовался в других проектах стека (RoadScout/BTW: `apps/api`, `apps/admin`, `apps/btw`, `apps/landing` как отдельные Vercel-проекты). Не единый деплой корня репозитория — у API (serverless-функция), TMA (Next.js-приложение) и лендинга (статический Next.js) разная природа, совмещать их в одном проекте технически возможно, но усложнило бы конфиг без пользы.

**Честно про степень проверки**: всё ниже написано по документации и установленным паттернам, но ни разу не прогнано против реального Vercel — сеть отключена в среде, где писался этот код. Первый реальный `vercel --prod` (или пуш в GitHub с подключённым автодеплоем) — не формальность, а первая настоящая проверка.

4. **Проект 2 — TMA**:
   - Root Directory: `apps/tma`
   - Framework Preset: **Next.js** (определится автоматически, `apps/tma/vercel.json` подтверждает явно)

5. **Проект 3 — Landing**:
   - Root Directory: `apps/landing`
   - Framework Preset: **Next.js** (статическая генерация — все страницы через `generateStaticParams()` по локалям, см. `apps/landing/README.md`)

6. **Проект 4 — Admin**:
   - Root Directory: `apps/admin`
   - Framework Preset: **Next.js**
   - Build/Output Command — дефолтные
   - Домен этого проекта ОБЯЗАН быть в `CORS_ORIGIN` проекта API: админка ходит в API с `credentials: 'include'`, и без этого cookie `admin_session` браузером не отправится

> ### ⚠️ Ошибка сборки: «No entrypoint found which imports nestjs»
>
> ```
> Error: No entrypoint found which imports nestjs. Found possible entrypoint: src/main.ts
> ```
>
> Появляется, когда Vercel применяет к проекту **нативный Nest-пресет**.
> Утверждение «Vercel не распознаёт NestJS автоматически» (стояло в этой
> инструкции раньше) устарело: пресет теперь есть, и проект под него
> подпадает — в зависимостях `@nestjs/core`, в корне `nest-cli.json`.
>
> Дальше срабатывает наша собственная особенность: Nest-билдер ищет
> файл, который импортирует `@nestjs/*`, а `src/main.ts` импортирует
> только `./create-app` — `NestFactory` вынесен в `create-app.ts`, чтобы
> локальный запуск и serverless создавали приложение одинаково. Файл
> найден, нужного импорта в нём нет — сборка падает.
>
> **Чинить импортами не нужно.** На Vercel точка входа вообще не
> `src/main.ts`, а `api/index.ts` (serverless-обёртка) плюс `rewrites`
> из `vercel.json`; Nest-пресет этой схеме не нужен и только мешает.
>
> В репозитории это зафиксировано — `apps/api/vercel.json` содержит
> `"framework": null` (то же самое, что Framework Preset = **Other**),
> и настройки из `vercel.json` перекрывают дашборд. Если проект уже
> создан со старой конфигурацией: **Settings → Build & Deployment →
> Framework Preset → Other**, затем Redeploy.

> ### ⚠️ Ошибка сборки: «No Output Directory named "public" found»
>
> ```
> Error: No Output Directory named "public" found after the Build completed.
> ```
>
> Следующая по порядку после ошибки про Nest-пресет, и причина
> смежная. Как только framework перестал быть Nest, Vercel обращается с
> проектом как с обычным: выполнил `buildCommand` — теперь ищет
> директорию со статикой, чтобы её раздать. А `apps/api` статику не
> отдаёт вообще: весь трафик уходит в serverless-функцию `api/index.ts`
> через `rewrites`, а `vercel-build` делает только `prisma generate` и
> ничего не собирает в файлы.
>
> Проверка при этом безусловная — «функции есть, статики нет» Vercel
> валидным состоянием не считает. Стандартный ответ на неё — **пустой
> каталог `public/`**, он в репозитории есть (`apps/api/public/.gitkeep`),
> и `vercel.json` указывает на него явно: `"outputDirectory": "public"`.
>
> Пустой он не случайно: маршрутизация Vercel сначала ищет статический
> файл и только потом применяет `rewrites`, поэтому любой файл, который
> сюда попадёт, будет отдаваться по своему пути мимо API — и будет
> публично доступен. Каталог нужен ровно для того, чтобы проверка
> прошла.
>
> Альтернативы, от которых лучше воздержаться: `"outputDirectory": "."`
> раздаст как статику весь каталог проекта, включая исходники; legacy-
> секция `"builds"` уберёт проверку, но заодно отключит zero-config и
> сломает подхват функций из `api/`.

> ### ⚠️ Рантайм-ошибка: `FUNCTION_INVOCATION_FAILED` на любом запросе
>
> Сборка прошла, но каждый запрос отдаёт «This Serverless Function has
> crashed». В Runtime Logs (Vercel → проект → Logs) видно настоящую
> причину. Два реальных случая, оба уже закрыты в коде:
>
> **1. `Nest can't resolve dependencies of the SecretsService … argument
> Object at index [1]`** — приложение не собиралось в DI-контейнере
> вообще, ни в проде, ни локально. Второй параметр конструктора был
> объявлен как `ttlMs = 5 * 60 * 1000` без аннотации типа; tsc эмитит
> для такого параметра `design:paramtypes` = `Object`, Nest читает это
> как зависимость и ищет провайдер с токеном `Object`. Исправлено
> (`@Optional() @Inject(SECRETS_CACHE_TTL_MS) ttlMs?: number`), разбор —
> в комментарии в `src/secrets/secrets.service.ts`, регрессия закрыта
> тестом `src/__tests__/app-bootstrap.spec.ts`.
>
> **2. Ошибка Prisma при старте.** `PrismaService` вызывал `$connect()`
> в `onModuleInit`, то есть подключался к базе на каждом холодном
> старте, до маршрутизации. Любая проблема с базой (неверный
> `DATABASE_URL`, ограничение по IP, исчерпанный пул) роняла функцию
> целиком, включая эндпоинты, которым база не нужна. Теперь подключение
> ленивое — ошибка приходит на том эндпоинте, который реально пошёл в
> базу, и отдаётся нормальным JSON через `ApiExceptionFilter`.
>
> Если крашится что-то ещё — сначала Runtime Logs, а не гадание: там
> будет исходный стек. Локально то же самое воспроизводится за минуту:
> `cd apps/api && npx nest build && node -e "require('./dist/src/create-app').createNestApp()"`.

Root Directory — настройка уровня Vercel dashboard, не выражается в `vercel.json` — если создаёте проект через `vercel` CLI, а не dashboard, укажите её там же при первой инициализации (`vercel link`, вопрос "In which directory is your code located?").

### Ошибка Prisma: «The table `public.users` does not exist»

Подключение к базе работает, но схемы в ней нет. Ровно тот случай, о
котором предупреждает §3: `prisma migrate deploy` при отсутствующей
папке `migrations/` завершается успешно и **не создаёт ни одной
таблицы**.

Накатить схему с локальной машины (не с Vercel — serverless не место
для одноразовых DDL-команд):

```bash
# ШАГ 0, без него ничего не заработает: зависимости монорепо.
cd <корень репозитория>
npm install

cd apps/api
npx prisma -v             # должно показать 5.x — см. врезку ниже

# Строку подключения НЕ экспортируем в шелл: Prisma CLI сама читает
# apps/api/.env, а `db push` берёт оттуда directUrl (порт 5432) —
# именно прямое соединение и нужно для DDL, через пулер на 6543 оно
# не проходит. Достаточно, чтобы в .env были обе переменные.
npx prisma db push        # создаёт все таблицы из schema.prisma
npm run prisma:seed       # AIProvider/AIModel/промпты/классы хранения
```

> **Если всё же задаёте переменную в терминале — одинарные кавычки.**
> В zsh (и bash) `!` внутри ДВОЙНЫХ кавычек запускает history
> expansion: `!!` раскрывается в предыдущую команду. Пароль вида
> `!!Passw0rd!!` при этом превращается в мешанину из вашей же
> прошлой команды, а сообщение об ошибке выглядит совершенно
> необъяснимо (`zsh: no matches found: …`). Внутри одинарных кавычек
> подстановки нет:
>
> ```bash
> export DATABASE_URL='postgresql://postgres.<ref>:!!Passw0rd!!@host:5432/postgres'
> ```
>
> Отдельная причина предпочесть `.env`: экспорт кладёт пароль от боевой
> базы в историю шелла (`~/.zsh_history`), откуда он потом попадает в
> скриншоты и подсказки автодополнения.

> **⚠️ «Environment variables loaded from .env», а ошибка про порт всё
> равно та же.** Это самая обманчивая комбинация во всём разделе:
>
> ```
> npx prisma db push
> Environment variables loaded from .env
> Error: P1013: The provided database string is invalid.
>        invalid port number in database URL.
> ```
>
> Строчка «loaded from .env» означает только то, что файл **прочитан**.
> Prisma CLI использует dotenv в режиме по умолчанию, а он **не
> перезаписывает уже существующие переменные окружения**. Если в текущей
> сессии терминала когда-то делали `export DATABASE_URL=…` — побеждает
> экспорт, а `.env` тихо игнорируется. Именно так живёт последствие
> предыдущей врезки: испорченный history expansion экспорт остался в
> шелле, и Prisma разбирает его, а не файл.
>
> Проверка и лечение — в том же окне терминала:
>
> ```bash
> printenv DATABASE_URL | cut -c1-40   # если что-то напечаталось — вот виновник
> printenv DIRECT_URL   | cut -c1-40
>
> unset DATABASE_URL DIRECT_URL        # снимаем экспорт
> npx prisma db push                   # теперь читается apps/api/.env
> ```
>
> Надёжнее — просто открыть новое окно терминала: экспорт живёт только
> в своей сессии. Если и там ошибка повторяется, значит проблема
> действительно в `apps/api/.env` — проверьте, что `DATABASE_URL` и
> `DIRECT_URL` записаны каждая одной строкой, значение целиком в
> двойных кавычках (в `.env` их снимает парсер), без переносов и без
> повторного `DATABASE_URL=` внутри значения.
>
> Второе следствие того же правила: экспортированная переменная
> перебивает `.env` и для `npm run prisma:seed`, и для `npm run
> start:dev` — то есть приложение может ходить совсем не в ту базу,
> в которую вы только что накатили схему.

> **⚠️ Про `npm install` — это не формальность.** Если `node_modules`
> нет, `npx prisma` не находит локальный бинарь и молча скачивает
> **последнюю** версию Prisma (сейчас 7.x). А в Prisma 7 свойства
> `url` и `directUrl` в `schema.prisma` больше не поддерживаются — они
> переехали в `prisma.config.ts`. Выглядит это как ошибка схемы, хотя
> схема в порядке:
>
> ```
> Error code: P1012
> error: The datasource property `url` is no longer supported in schema files.
>   -->  prisma/schema.prisma:72
> ```
>
> Проект собран на Prisma **5.22** (`package.json`), и переезд на 7.x —
> отдельная задача (конфиг-файл, driver adapters), а не побочный эффект
> запуска одной команды. Лечится двумя способами:
>
> ```bash
> npm install                    # правильный: появится локальная 5.22
> npx prisma@5.22.0 db push      # разовый обходной путь, без установки
> ```
>
> По той же причине `npm run prisma:seed` отвечает
> `sh: prisma: command not found` — бинаря нет, потому что нет
> `node_modules`.

`prisma:seed` обязателен, а не «на всякий случай»: без записей
`AIProvider` резолвить `credentialRef` нечего, и все AI-фичи будут
падать с «provider not found», хотя ключи заданы.

**Чего здесь делать НЕ надо:** запускать `prisma:seed:dev` — этот сид
создаёт пользователя с полными правами оператора и сам откажется
работать, если `DATABASE_URL` указывает не на локальную базу.

После этого `pg_cron`-задания (три файла в
`prisma/manual-migrations/pg_cron_*.sql`) применяются отдельно, через
SQL Editor в Supabase — `db push` их не покрывает, это конфигурация
инстанса, а не схема.

### `API_PUBLIC_BASE_URL`: домен API-проекта, без слэша и без пути

Три ошибки в этой переменной дают ОДИН И ТОТ ЖЕ симптом — разговор
навсегда виснет в `TRANSCRIBING`, потому что вебхук с расшифровкой ушёл
не туда. Отличить их по симптому невозможно, поэтому формат проверяется
в коде (`src/common/public-base-url.ts`), до отправки задачи провайдеру:

| Значение | Что не так |
|---|---|
| `https://my-api.vercel.app/` | слэш на конце → в пути вебхука двойной слэш. Срезается автоматически, но лучше не полагаться |
| `https://my-admin.vercel.app` | **домен не того проекта.** Самая дорогая ошибка: адрес рабочий, отвечает 200, и всё выглядит настроенным — но вебхук приходит в Next.js-приложение админки, которое про него ничего не знает |
| `https://my-api.vercel.app/api` | путь в адресе → отказ с объяснением |
| `http://my-api.example.com` | не https. По этому адресу возвращается расшифровка разговора — открытым текстом её слать нельзя. `http://localhost` разрешён |

**Как убедиться, что это домен API, а не админки или TMA** — один
запрос, авторизация не нужна:

```bash
curl -s https://<ваш-адрес>/healthz
```

API отвечает JSON со `status`. Админка или TMA на этот путь отдадут
HTML страницы 404 — значит, адрес не тот.

### Первый оператор: «Нет доступных вкладок» после успешного входа

Вход по Telegram Login Widget прошёл, в шапке админки виден ваш `userId`,
но вместо вкладок — «Нет доступных вкладок — обратитесь к тому, кто
управляет деплойментом, за нужным флагом доступа», а любая страница
отвечает «Требуется роль модератора библиотеки».

**Это не ошибка, а спроектированное поведение.** Вход в админку открыт
любому пользователю Telegram — сессия создаётся, но не даёт ничего.
Доступ определяют три независимых булевых флага на `User`
(`admin-panel-tz.md` §4.1) — не RBAC-таблица, намеренно:

| Флаг | Что открывает |
|---|---|
| `isLibraryModerator` | вкладка «Библиотека» |
| `isVenueModerator` | вкладка «Заведения» |
| `isOperator` | «Пользователи», «Промпты», «Телеметрия», «Калибровка», «Сценарии», «Intake», «Медиа» |

Дальше флаги раздаются из самой админки (вкладка «Пользователи»), но
эта вкладка требует `isOperator` — то есть **первому оператору включить
себя из UI нечем**. Это осознанный компромисс: иначе понадобился бы
эндпоинт «сделать себя оператором», а он же — дыра в аутентификации.
Поэтому первый и единственный раз флаги ставятся руками в SQL Editor
Supabase.

`userId` берётся прямо из шапки админки (он там и показан ровно для
этого случая):

```sql
-- Имена колонок в camelCase, поэтому двойные кавычки обязательны:
-- без них Postgres приведёт их к нижнему регистру и не найдёт колонку.
update users
   set "isOperator" = true,
       "isLibraryModerator" = true,
       "isVenueModerator" = true
 where id = 'cmth49kgv000169mwtrqlgv6s';   -- ваш id из шапки
```

Если id под рукой нет, можно найти себя по Telegram-идентификатору:

```sql
select id, "telegramId", "isOperator", "isLibraryModerator", "isVenueModerator"
  from users order by "createdAt" desc limit 10;
```

Перелогиниваться не нужно: `/admin/auth/me` читает флаги из базы на
каждый запрос, а не запоминает их в сессии. Достаточно обновить
страницу.

**Не используйте для этого `prisma:seed:dev`** — он создаёт отдельного
фиктивного пользователя `dev-<id>` и намеренно откажется работать, если
`DATABASE_URL` указывает не на локальную базу.

### Загрузка аудио: почему она идёт мимо API и что для этого нужно

**Была проблема, она закрыта — но требует одной переменной, без
которой загрузка не заработает.**

Исходно `POST /conversations/:id/upload` принимал байты файла телом
запроса. На Vercel это неработоспособно: тело запроса к
serverless-функции ограничено **4,5 МБ**
([Vercel Functions Limits](https://vercel.com/docs/functions/limitations)),
плюс `apps/api/vercel.json` задаёт `maxDuration: 10`. Аудиодорожка
часового разговора — десятки мегабайт. Коварство в том, что отказ
приходит на уровне платформы, ДО кода: в Runtime Logs его не видно, а
локально и в докере он не воспроизводится вообще.

С 2026-08-31 основной путь другой — файл идёт **напрямую в приватный
Vercel Blob**, наш API байты не видит вовсе:

```
1. клиент → POST /conversations/:id/audio-upload-token
   API проверяет владение разговором и согласия, выдаёт одноразовый
   токен: конкретный путь, тип содержимого, максимум 500 МБ, 30 минут
2. клиент → PUT напрямую в blob.vercel-storage.com (multipart)
3. клиент → POST /conversations/:id/audio-blob { pathname }
   API проверяет через head(), что файл есть, и записывает путь
4. POST /conversations/:id/transcribe БЕЗ audioUrl
   API сам делает подписанную ссылку (6 часов, только чтение) и
   отдаёт её AssemblyAI
5. по вебхуку файл удаляется — и на успехе, и на ошибке
```

**Что нужно настроить — два действия, оба обязательны:**

1. **Переменная `VERCEL_BLOB_READ_WRITE_TOKEN`** в проекте API
   (Storage → Blob → создать стор → Connect Project; токен появляется в
   переменных проекта автоматически, но проверьте, что он есть именно у
   API-проекта). Она уже была в таблице §2 ради доказательств ДТП —
   теперь без неё не работает ещё и загрузка разговоров.
2. **Накатить схему заново** — в `Conversation` добавились два поля
   (`audioBlobPathname`, `audioBlobBytes`). Без этого API упадёт на
   первом же обращении к разговору с ошибкой про отсутствующую колонку:

   ```bash
   cd apps/api
   npx prisma db push
   ```

   `db push` здесь безопасен: добавление nullable-колонок данных не
   трогает. Сид повторять не нужно.

**Приватность:** blob создаётся с `access: 'private'` — публичной
ссылки на файл не существует. Соответственно, старая формулировка «файл
не сохраняется на нашем сервере» перестала быть точной и заменена в UI
на честную: файл лежит в приватном хранилище от загрузки до конца
расшифровки, потом удаляется.

Старый потоковый путь (`/conversations/:id/upload` + `audioUrl` в
`transcribe`) сохранён: локально и в докере лимита нет, и для отладки
цепочки одним `curl` он проще. На Vercel им пользоваться нельзя.

С 2026-08-31 такая ошибка больше не выглядит как «Internal server
error»: API отвечает 503 с текстом про `prisma db push` (коды Prisma
P2021/P2022), а подробности запроса наружу не уходят.

### Ошибка Prisma: «invalid port number in database URL»

```
PrismaClientInitializationError: The provided database string is invalid.
Error parsing connection string: invalid port number in database URL.
```

Сообщение указывает на порт, но порт почти никогда не при чём. Две
реальные причины, обе — про то, как значение попало в переменную:

**1. Значение вставили вместе с кавычками.** В файле `.env` кавычки —
часть синтаксиса, их снимает парсер dotenv. В UI Vercel парсера нет:
кавычка становится обычным символом, уезжает в конец строки, и «портом»
оказывается `6543/postgres?pgbouncer=true"`. В Vercel значение вводится
**без** кавычек:

```
postgresql://postgres.xxx:PASSWORD@aws-0-eu-central-1.pooler.supabase.com:6543/postgres?pgbouncer=true
```

**2. Спецсимвол в пароле без percent-encoding.** Разделителем логина и
хоста служит `@`, поэтому пароль вида `S8p@ss` разрезает URL не в том
месте. Supabase генерирует пароли со спецсимволами, так что случай
частый. Заменить в **пароле** (не во всей строке):

| символ | заменить на |
| --- | --- |
| `@` | `%40` |
| `/` | `%2F` |
| `:` | `%3A` |
| `?` | `%3F` |
| `#` | `%23` |
| `%` | `%25` |

Проверить строку локально, не показывая её никому:

```bash
node -e "const u=new URL(process.env.DATABASE_URL); console.log(u.protocol, u.hostname, u.port)"
# postgresql: aws-0-eu-central-1.pooler.supabase.com 6543
```

Если печатает что-то другое или падает — проблема в самой строке.

С 2026-08-31 API проверяет это сам: при старте `PrismaService` пишет в
лог конкретный диагноз («значение обёрнуто в кавычки», «больше одного
`@` — закодируйте пароль»), а не только симптом. Строку подключения и
пароль в лог он при этом не выводит — логи Vercel видит вся команда.

### Ошибка виджета: «Bot domain invalid»

Виджет отрисовался, но вместо кнопки входа показывает `Bot domain
invalid` — это ответ самого Telegram, не нашего кода. Означает ровно
одно: домен страницы не привязан к боту.

1. @BotFather → `/setdomain`
2. выбрать **того самого** бота, чей username стоит в
   `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` админки и чей токен задан как
   `TELEGRAM_BOT_TOKEN` на стороне API (если это разные боты, виджет
   отрисуется, но проверка подписи на бэкенде будет проваливаться всегда);
3. отправить домен админки — только хост, без `https://`, без пути и
   слэша: `advokate-admin.vercel.app`.

Особенности, на которых обычно спотыкаются:

- **один домен на бота.** `/setdomain` не список: новый домен заменяет
  прежний. Если Login Widget нужен на двух доменах (например, прод и
  стенд) — нужен второй бот со своим токеном;
- **preview-домены не подойдут** — они меняются при каждом деплое,
  привязывать их бессмысленно (см. предупреждение про preview ниже);
- Mini App (`/newapp`) — отдельная настройка и с `/setdomain` не
  конфликтует: TMA и админка могут жить на одном боте;
- после привязки страницу нужно перезагрузить с очисткой кеша
  (Ctrl/Cmd+Shift+R) — скрипт виджета кешируется.

### Как проверить, что API действительно работает

```bash
curl -s https://<домен-api>.vercel.app/healthz
# {"success":true,"data":{"status":"ok","startedAt":"…","uptimeSeconds":3}}
```

`GET /healthz` — единственный публичный эндпоинт без авторизации,

означает, что **API живой** (это его собственный формат ошибки через
`ApiExceptionFilter`), но выглядит как поломка и сбивает с толку.

### Предупреждение в логах: «CORS_ORIGIN is not set in production»

```
CORS_ORIGIN is not set in production — cross-origin requests (including apps/admin) will be blocked.
```

Это наш собственный `console.error` из `create-app.ts`, не ошибка
платформы. Пока переменная не задана, API отвечает на прямые запросы
(curl, браузерная строка), но **любой запрос из TMA, админки и лендинга
браузер заблокирует** — cookie админки не отправится, `fetch` упадёт с
CORS-ошибкой в консоли.

Значение — production-домены всех трёх фронтендов через запятую, без
слэша на конце:

```
CORS_ORIGIN=https://advokate-admin.vercel.app,https://<tma>.vercel.app,https://<landing>.vercel.app
```

⚠️ **Про preview-домены.** У каждого деплоя Vercel свой адрес вида
`devils-advokate-ahgd5lhuc-<team>.vercel.app`, и он меняется при каждом
пуше. Перечислять их в `CORS_ORIGIN` бессмысленно: в списке должны быть
стабильные production-домены (или кастомные домены, если они настроены).
Как следствие — на preview-деплоях фронтенды к API не достучатся; это
нормальное поведение, а не поломка. Если preview-окружение нужно
рабочим, заводите для него отдельный набор переменных в Vercel
(Environment = Preview) со своими доменами.

## 3. Первый деплой базы данных

Миграции **не запускаются автоматически** при каждом деплое (сознательно — см. `vercel-build` в `package.json`, там только `prisma generate`, не `migrate deploy`). Прогонять миграции на проде — отдельное, осознанное действие, не побочный эффект пуша в main:

> ### ⚠️ ПОВТОРНЫЙ АУДИТ 2026-08-30: команда ниже сейчас НИЧЕГО НЕ ДЕЛАЕТ
>
> Папки `apps/api/prisma/migrations/` в репозитории **нет** — ни одной
> миграции не сгенерировано ни разу. `prisma migrate deploy` при пустой
> истории завершается успешно с сообщением «No migration found» и не
> создаёт ни одной таблицы; следующий за ним `prisma:seed` падает на
> первой же вставке. Схема на проде до сих пор появлялась либо через
> `prisma db push`, либо ручным SQL — и ничто не проверяет, что боевая
> база соответствует `schema.prisma` (в схеме 225 `@@index`, в
> `manual-migrations/` — 122 `CREATE INDEX`; разница существует только
> там, где применяли `db push`).
>
> **Что делать, по-хорошему** — один раз завести baseline и дальше жить
> с нормальной историей миграций:
>
> ```bash
> cd apps/api
> mkdir -p prisma/migrations/0_init
> npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma \
>   --script > prisma/migrations/0_init/migration.sql
> # на УЖЕ существующей проде — пометить как применённую, не выполнять:
> DATABASE_URL="<pooled>" DIRECT_URL="<direct>" npx prisma migrate resolve --applied 0_init
> ```
>
> **Быстрый путь для чистой базы** (без истории — сознательный размен,
> тот же, что в локальном докер-стенде, см. `DOCKER.md` §2):
>
> ```bash
> cd apps/api
> DATABASE_URL="<pooled>" DIRECT_URL="<direct>" npx prisma db push
> ```

```bash
cd apps/api
DATABASE_URL="<pooled-url>" DIRECT_URL="<direct-url>" npx prisma migrate deploy
npm run prisma:seed  # провайдеры/модели/промпты/retention classes, см. prisma/seed.ts
```

Прогонять с локальной машины (или из CI-джобы), не с самого Vercel — serverless-функция не подходящее место для одноразовых миграционных команд.

**После `migrate deploy` — вручную применить `apps/api/prisma/manual-migrations/`.**
`prisma migrate` не покрывает то, что не выражается в `schema.prisma`: расширения
Postgres, `cron.schedule()`, ручные `ALTER COLUMN … TYPE` для уже накопленных данных.
На 2026-08-30 в папке:
- `schema_audit_2026_08_30.sql` — индексы на FK, `updatedAt`/`createdAt`, `Decimal(14,2)`
  для денежных полей, `DROP TABLE` для удалённых моделей (аудит `docs/AUDIT-DB-2026-08-30.md`).
- `intake_session.sql` — таблица `intake_sessions`, эквивалент того, что даст
  `prisma migrate` для `IntakeSession`; держать для сверки, а не вместо миграции.
- `pg_cron_reminders.sql`, `pg_cron_calibration.sql`, `pg_cron_intake_abandon.sql` —
  по одному `cron.schedule()` на каждое из трёх заданий за `SCHEDULER_DISPATCH_SECRET`
  (напоминания планировщика, ежесуточный пересчёт калибровки, обнуление зависших
  intake-сессий). Каждый файл выполняется один раз через SQL Editor Supabase, **после**
  того как у API есть реальный production URL — в файлах плейсхолдер
  `YOUR-PRODUCTION-DOMAIN.example`, который нужно заменить на настоящий.

## 4. ⚠️ Известный архитектурный риск — таймаут serverless-функции

**Лимит длительности одного вызова на Vercel Hobby — по разным источникам от 10 до 60 секунд** (расхождение, вероятно, связано с тем, включён ли Fluid Compute — проверить актуальное значение в документации Vercel на момент деплоя, не полагаться на цифру здесь). `apps/api/vercel.json` сейчас выставляет `maxDuration: 10` — консервативно, безопасно для plain Hobby без Fluid Compute.

**Это реальный риск для трёх фич**, не гипотетический: `AIRouterService` делает настоящие HTTP-вызовы к OpenAI/Anthropic/xAI (фичи 1, 7, 10 — генерация аргументов, Steelman, скрипты), с retry до `maxRetries` попыток. Один медленный ответ модели + один retry легко превышает 10 секунд. Если реальные деплои будут упираться в 504:

1. Проверить текущий лимит Hobby в актуальной документации Vercel — возможно, уже 60с по умолчанию.
2. Включить Fluid Compute в настройках проекта (может расширить лимит до 300с даже на Hobby).
3. Снизить `maxRetries` по умолчанию в `AIRouterService.execute()` для интерактивных запросов — сейчас `2`, при коротком лимите разумнее `1`.
4. Более серьёзная переработка (вне объёма этого прохода) — асинхронный паттерн (создать `AIJob`, вернуть `202 Accepted`, TMA поллит статус) вместо синхронного ожидания ответа модели в одном HTTP-запросе. `AIJob`-модель уже спроектирована с этим в виду (статусы `QUEUED`/`RUNNING`/`COMPLETED`), но текущий `AIRouterService.execute()` ждёт результат синхронно.

Пункт 4 — не сделан в этом проходе сознательно: это архитектурная переработка, не настройка деплоя, честнее оставить явным TODO, чем тихо понадеяться, что 10-секундного окна хватит на реальном трафике.

## 5. Прочие ограничения Hobby, о которых стоит знать

- **Только личное/некоммерческое использование** по условиям Vercel Hobby — если продукт становится коммерческим, потребуется Pro.
- **Once-daily cron** (если/когда появится реальный enforcement для `RetentionClass` TTL, см. `apps/api/prisma/README.md`, раздел "TTL-настройки") — паттерн, уже использованный в других проектах стека, обходится через Supabase `pg_cron`/`pg_net`, не через встроенный Vercel Cron, который на Hobby ограничен одним запуском в сутки.
- **Cold start** — первый запрос после периода бездействия будет заметно медленнее (создание Nest DI-контейнера с нуля, см. кэширование в `api/index.ts`).
