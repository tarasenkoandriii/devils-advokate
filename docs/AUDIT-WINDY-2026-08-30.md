# Windy как первичный источник погоды, Open-Meteo как fallback — 2026-08-30

По прямому запросу («может вместо Open-Meteo использовать Windy (fallback onto
Open-Meteo)»). Реализовано, не просто исследовано — в отличие от Google Places
Legacy (найдено, задокументировано, не тронуто без явного запроса), здесь запрос
на реализацию был прямым.

## Исследование — реальный контракт Windy Point Forecast API

Прочитана целиком `api.windy.com/point-forecast/docs`. Ключевые находки, повлиявшие
на реализацию:

- **Ключ — в теле POST-запроса** (`{"key": "..."}`), НЕ в заголовке — у Webcams/Map
  Forecast API того же провайдера ключ идёт заголовком `x-windy-api-key`, лёгкая
  ловушка перепутать между тремя продуктами одного вендора.
- **`weatherWarnings`** (response key `weatherwarnings-surface`) использует те же
  числовые WMO-коды, что уже лежат в `WEATHER_CODE_LABELS` (`open-meteo-client.ts`) —
  45/48/51/53/55/61/63/65/71/73/75/80/81/82/95/96 пересекаются почти полностью.
  Переиспользована та же таблица, не задублирована.
- **Выбор модели — не тривиален**: `weatherWarnings` по таблице совместимости
  документации поддерживают ТОЛЬКО `icon`/`iconD2`/`iconEu`. `gfs` (глобальный,
  первая интуитивная мысль) его вообще не отдаёт. `iconD2`/`iconEu` точнее, но
  покрывают только Европу. `icon` (ICON-Global) — единственная из трёх с глобальным
  покрытием, выбрана осознанно.
- **У Windy нет кода «ясно»/«облачно»** — `weatherWarnings` покрывает только
  значимые явления (дождь/снег/гроза/туман), не рутинную облачность. При его
  отсутствии/нуле условие синтезируется из трёх ярусов облачности
  (`lclouds`/`mclouds`/`hclouds`, % покрытия) — честная деградация до
  «ясно/переменная облачность/пасмурно» через простые пороги, а не подмена «нет
  данных», раз данные по факту есть в другой форме.
- **Температура в Кельвинах** — подтверждено не предположением, а чтением
  `response.units["temp-surface"]` в рантайме перед конвертацией (тот же принцип
  «сверяй рантайм-форму, не предполагай», что уже применялся сегодня к другим
  клиентам).

## Архитектура

`getForecastWithFallback()` в `WeatherForecastService`: при настроенном
`WINDY_API_KEY` — Windy первым, любая его ошибка (сеть/4xx/5xx/неожиданная форма)
падает молча на Open-Meteo, не наружу пользователю. Без ключа — Windy вообще не
запрашивается (не лишняя сетевая попытка на заведомо не настроенный платный
сервис). Open-Meteo остаётся обязательным, бесплатным, не требующим ключа —
поведение без `WINDY_API_KEY` идентично тому, что было до сегодня, ничего не
ломается для тех, кто не настроит новый ключ.

Геокодирование города остаётся на Open-Meteo — у Point Forecast API нет своего
geocoding-эндпоинта, только приём готовых координат.

## Тесты

Ни `open-meteo-client.ts`, ни новый `windy-client.ts` не имели файла тестов до
этого — закрыто для обоих. `windy-client.spec.ts` (10 тестов): форма запроса
(model=icon, ключ в теле), конвертация K→C по `units` (в т.ч. защита от ложной
конвертации, если `units` вдруг не Кельвины), выбор ближайшего индекса временного
ряда, переиспользование WMO-кодов, деградация на облачность при
`weatherWarnings=0`, честное «нет данных», когда и код, и облачность отсутствуют,
обработка сетевых/HTTP-ошибок. `weather-forecast.service.spec.ts` (+3 к
существующим 15): Windy успешно отвечает → Open-Meteo не вызывается вообще; Windy
настроен, но падает → тихий fallback на Open-Meteo, пользователь не видит ошибки;
без ключа → Windy не запрашивается вообще (ни одного сетевого вызова на
ненастроенный сервис).
