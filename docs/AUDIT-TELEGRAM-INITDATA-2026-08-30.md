# Аудит Telegram Mini App initData — 2026-08-30

Продолжение сегодняшнего сквозного аудита (после AssemblyAI и ElevenLabs).
Пользователь предоставил второй референс-проект (`silverfinance`, "отдебаженный
код с ТМА логином") — значительно более зрелая реализация, чем в `caller-id`.
Сравнение раскрыло вопрос, затрагивающий и рабочий проект.

## Что показал silverfinance

`tg-initdata.ts` не выбирает одну сторону в вопросе «входит ли `signature` в
HMAC classic-схемы» — считает hash ДВАЖДЫ (с `signature` и без) и принимает
совпадение с любым из двух. Комментарий в коде: «текущая документация говорит
исключать, но некоторые клиенты/окружения включают». Плюс `crypto.timingSafeEqual`
вместо строкового сравнения, и отдельный (debug-only) диагностический хелпер
`debugInitData()`, перебирающий известные варианты порчи (swapped key order,
re-encoded JSON, escaped slashes, Login Widget scheme vs Mini App scheme) —
явный след боевой отладки, не разового прочтения документации.

## Проверено по официальной документации

`docs.telegram-mini-apps.com/platform/init-data`: `signature` — часть
**полностью отдельной** third-party схемы валидации (`validate3rd`, Ed25519,
публичный ключ Telegram, НЕ токен бота). Классическая HMAC-схема по документации
исключает только `hash`. Но ни официальные примеры, ни независимые библиотеки
(Elixir, Python `parse_qs`, `init-data-py`) не показывают случая, где `signature`
присутствует ОДНОВРЕМЕННО с `hash` в примере classic-схемы — то есть документация
не даёт прямого ответа на реальный вопрос «что делать, если оба поля пришли
вместе». Три независимых источника (собственный комментарий devils-advocate-project
про «баг из предыдущих проектов», боевой опыт silverfinance, дальнейший поиск)
сходятся в одном: это подтверждённая неоднозначность в реальном поведении разных
версий Telegram-клиентов, не что-то, что можно один раз правильно угадать.

## Исправлено — `devils-advocate-project` (рабочий проект)

`telegram-init-data.util.ts` раньше ЖЁСТКО исключал и `hash`, и `signature` —
единственный вариант вычисления. Это надёжнее, чем у caller-id (который
`signature` не исключал вовсе), но всё ещё однобоко: клиент, который **включает**
`signature` в HMAC, был бы отклонён с `hash mismatch`. Переведено на
двух-вариантный расчёт (как у silverfinance) + `timingSafeEqual`. 2 новых теста:
обратный случай (клиент включает `signature`) и повреждённый/укороченный hash
(проверка, что сравнение разной длины корректно даёт `false`, не падает).
Jest: 63 сьюта / **509** тестов (было 507).

## Подготовлено — для `caller-id` (референс, не рабочий проект)

`telegram-webapp-auth.util.ts` изначально исключал только `hash`, `signature`
никогда не исключался — самый однобокий из трёх вариантов, реальный риск
отклонять валидные Mini App запросы для клиентов, не включающих `signature` в
HMAC. Подготовлена исправленная версия (двух-вариантный расчёт + `timingSafeEqual`,
тот же подход, что применён в devils-advocate-project), проверена рантайм
smoke-тестом (оба варианта клиента принимаются, испорченный hash отклоняется).
Файл не применялся в рабочую копию caller-id — это не проект, который
запрашивался на полный аудит, только референс для сравнения; итоговый файл
отдан пользователю на самостоятельное решение.

## Итог

Три реализации одной и той же проверки, три разных уровня зрелости — от
однобокой (caller-id, включала уязвимость) через промежуточную
(devils-advocate-project до сегодняшнего фикса) до защитной (silverfinance).
После сегодняшнего аудита рабочий проект соответствует самому надёжному
из трёх найденных подходов, с тестами на обе стороны неоднозначности.

## Продолжение — Login Widget (соседний путь авторизации, вход в админку)

Проверен и второй Telegram-путь в devils-advocate-project — `telegram-login-widget.util.ts`
(другая HMAC-схема: ключ `SHA256(bot_token)`, не `HMAC-SHA256("WebAppData", bot_token)`,
используется для входа в `/admin`, не в Mini App). Поля `signature` здесь не существует
(она специфична для Mini App initData), так что находка про две HMAC-схемы неприменима —
но та же проверка `!==` вместо `timingSafeEqual`, что чинилась сегодня в Mini App пути,
была и здесь. `caller-id`'s `telegram-auth.util.ts` (прямой аналог) использует тот же
`!==` — не расхождение между проектами, общий пробел. `silverfinance` для входа
использует совершенно другую схему (OAuth2/PKCE через `oauth.telegram.org` с JWT-проверкой
через JWKS) — не референс для той же функции, архитектурно другой механизм.

**Исправлено:** `timingSafeEqual` вместо `!==`, для внутренней консистентности с
Mini App путём. 1 новый тест — hash другой длины (не покрыто существующим тестом
«испорченный hash», который использовал ту же длину 64 символа). Jest: 63 сьюта /
**510** тестов (было 509).
