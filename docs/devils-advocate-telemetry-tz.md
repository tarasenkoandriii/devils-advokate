# Devil's Advocate — ТЗ: AI Operational Telemetry

> ⚠️ **Конфиденциально.** Технический компаньон-документ. Коммерческая ценность та же —
> не подлежит разглашению третьим лицам без согласия автора.

**Статус:** первая ревизия. В отличие от `devils-advocate-prompt-framework-tz.md` (закрывает
разрыв с уже существующей спецификацией, раздел 6 implementation-ready.md), у телеметрии нет
предшествующего документа — ни в `devils-advocate-tz.md`, ни в `devils-advocate-implementation-ready.md`
телеметрия не упоминается ни разу. Это значит, что первая задача — не описать целевое состояние,
а **осознанно сузить**, что вообще имеется в виду, прежде чем проектировать решение. Раздел 1 —
именно это сужение, не отступление от темы.

**Как читать:** раздел 1 — почему обсуждается не «телеметрия» вообще, а конкретно «операционная
видимость по уже накопленным данным»; раздел 2 — что уже пишется в БД и что честно отсутствует;
раздел 3 — минимальное дополнение к модели данных; раздел 4 — API-контракт; раздел 5 —
acceptance-тесты; раздел 6 — что сознательно не входит, и почему это не совпадает с тем, что
можно было бы ожидать от слова «телеметрия».

## 1. Сужение цели

«Телеметрия» без уточнения может значить что угодно — от учёта стоимости до алертинга в реальном
времени до полноценного observability-стека. Проверено в коде, что из этого физически возможно
уже сейчас, а что требует нового слоя сбора данных, которого пока нет вообще:

**Уже пишется в БД на каждый AI-вызов** (таблица `AIJob`, создаётся в `AIRouterService`,
единая точка входа для всех AI-вызовов проекта):
- `status` (`QUEUED → RUNNING → COMPLETED/FAILED/TIMEOUT/CANCELLED`)
- `retryCount`
- `modelVersionId`, `promptVersionId`
- `createdAt` / `completedAt` — оба поля реально записываются на обоих путях (успех и провал,
  проверено напрямую в `ai-router.service.ts:149` и `:297`) — значит, длительность вызова
  вычислима без единой новой строки кода
- `schemaValidation` (`PASS`/`FAIL`) — провалы валидации структуры вывода AI
- `inputScanStatus` — заблокированные на входе запросы (prompt injection/PII)

**Не пишется вообще, при этом физически проверено, не предположение:**
- **`taskType`** — параметр, которым `AIRouterService` выбирает модель (`resolveModelVersion`),
  но который **нигде не сохраняется** на самой записи `AIJob` (`ai-router.service.ts:118-131`).
  Без него телеметрия может группироваться только по AI-модели (3-4 возможных значения на весь
  проект) — не по фиче (85+ различных `taskType` по всему проекту). Это критично: вопрос
  «какая фича чаще всего падает» без `taskType` не задать в принципе, только «какая модель».
- **Токены и стоимость вызова.** Проверено — `AIRouterService` даже не читает поле `usage`
  из ответа AI-провайдера (обычно присутствует у всех трёх используемых вендоров), не то что
  не сохраняет его. `AIModelCapability.costClass` — это грубая строковая категория
  (`"low"|"medium"|"high"`), не фактическая цена и не счётчик токенов.

**Вывод сужения:** ревизия покрывает **операционную видимость** («сколько вызовов, какой
фичей, с каким успехом, как долго, сколько повторов») — данные для этого почти полностью уже
есть, не хватает одного поля. Учёт стоимости в эту ревизию сознательно **не входит** — это
отдельная задача с собственным дизайном (нужно решить, откуда брать цену за токен для трёх
разных вендоров, как часто она меняется, где хранить) — попытка втиснуть это сюда превратила бы
узкую, быстро реализуемую ревизию в отдельный проект. См. раздел 6.

## 2. Что уже работает и не требует изменений

- Сам факт, что все AI-вызовы проекта проходят через одну точку (`AIRouterService`) —
  телеметрия не требует правки 35+ сервисов-потребителей, только самого роутера.
- `AIJob.status`/`retryCount`/`createdAt`/`completedAt`/`schemaValidation`/`inputScanStatus` —
  готовы к использованию, ни одно из этих полей не меняется.
- Связь `AIJob → AIModelVersion → AIModel → AIProvider` — уже позволяет группировать по
  провайдеру/модели без изменений.

## 3. Минимальное дополнение к модели данных

Ровно одно поле — намеренно не больше.

```prisma
model AIJob {
  // ...существующие поля без изменений...

  // Пункт [N]: телеметрия по фиче — без этого поля агрегация возможна
  // только по AI-модели, не по конкретной фиче проекта (85+ значений
  // taskType по всему проекту на момент написания). Совпадает по
  // смыслу с AIModelCapability.taskType (уже есть в схеме), здесь —
  // просто фиксация ФАКТА, каким taskType был вызван конкретный job,
  // не связь с capability-записью (та описывает, что модель УМЕЕТ,
  // не что было вызвано в этот раз).
  taskType String?
}
```

`taskType` — nullable, не `required`: существующие записи `AIJob` (созданные до этой ревизии)
не имеют этого значения и не должны становиться невалидными задним числом. Новые записи
заполняют его всегда — правка одной строки в `AIRouterService.execute()`
(`data: { ..., taskType: sanitizedRequest.taskType }`).

`@@index([taskType, createdAt])` — добавляется для эффективной агрегации по фиче за период,
без него `GROUP BY taskType` на растущей таблице со временем деградирует.

## 4. API-контракт

Admin-facing, тот же паттерн, что `/admin/*` в `devils-advocate-prompt-framework-tz.md` —
не для конечного пользователя продукта.

### 4.1 Сводка по фичам за период

| Метод | Путь | Описание | Параметры | Ответ |
|---|---|---|---|---|
| `GET` | `/admin/telemetry/summary` | Агрегат по каждому `taskType` за период | `?from=<ISO>&to=<ISO>` | `TelemetrySummaryRow[]` |

```typescript
interface TelemetrySummaryRow {
  taskType: string | null; // null — вызовы ДО добавления поля, честно не скрываем как "unknown"-фичу
  totalCalls: number;
  byStatus: Record<'COMPLETED' | 'FAILED' | 'TIMEOUT' | 'CANCELLED', number>;
  avgDurationMs: number | null;   // null если ни один вызов ещё не завершился (completedAt пуст)
  p95DurationMs: number | null;
  retryRate: number;              // доля job с retryCount > 0
  schemaValidationFailRate: number;
  inputBlockedCount: number;      // inputScanStatus = BLOCKED
}
```

Живой агрегирующий SQL-запрос (`GROUP BY taskType`), не предвычисленная таблица — при
реальном масштабе проекта (личный/соло-проект, не высоконагруженный B2B-сервис) это оправдано
простотой, предвычисление добавило бы сложность без текущей необходимости (честно не
проектируется заранее «на будущее», см. тот же принцип, что уже применялся по всему проекту —
не строить инфраструктуру под нагрузку, которой пока нет).

### 4.2 Детализация по конкретной фиче

| Метод | Путь | Описание | Параметры | Ответ |
|---|---|---|---|---|
| `GET` | `/admin/telemetry/tasks/:taskType` | Последние N вызовов этой фичи, с деталями провалов | `?limit=50&status=FAILED` | `AIJobDetail[]` |

```typescript
interface AIJobDetail {
  id: string;
  status: string;
  modelVersion: string;       // "gpt-4.1" | "claude-sonnet-5" | ...
  promptVersionId: string | null;
  retryCount: number;
  durationMs: number | null;
  schemaValidation: 'PENDING' | 'PASS' | 'FAIL';
  inputScanStatus: 'PENDING' | 'PASSED' | 'BLOCKED';
  createdAt: string;
}
```

Не включает `output`/`partialResult` — это отладочные данные конкретного вызова, для них уже
есть прямой доступ к `AIInference`/`AIJob` через существующие механизмы работы с БД, дублировать
здесь не нужно (этот эндпоинт — про паттерны across many calls, не про содержимое одного).

### 4.3 Разбивка по моделям/провайдерам

| Метод | Путь | Описание | Параметры | Ответ |
|---|---|---|---|---|
| `GET` | `/admin/telemetry/by-model` | Тот же агрегат, что 4.1, но группировка по `modelVersionId` вместо `taskType` | `?from=&to=` | `TelemetrySummaryRow[]` (с `modelVersion` вместо `taskType`) |

Позволяет ответить на вопрос «какой из трёх AI-вендоров чаще всего таймаутит/падает» —
самостоятельная, отличная от 4.1 группировка тех же исходных данных, не дублирование.

## 5. Acceptance-тесты (Given/When/Then)

```
Given за последние 24 часа было 12 вызовов taskType="material-chat":
      10 COMPLETED, 2 FAILED
When запрашивается GET /admin/telemetry/summary?from=<24ч назад>&to=<сейчас>
Then в ответе есть строка taskType="material-chat" с totalCalls=12,
     byStatus={COMPLETED: 10, FAILED: 2, ...}
```

```
Given AIJob создан ДО того, как в проекте появилось поле taskType (миграция накатана,
      но исторические записи имеют taskType=null)
When запрашивается GET /admin/telemetry/summary
Then в ответе присутствует отдельная строка с taskType=null — исторические вызовы
     не пропадают молча и не приписываются случайной фиче
```

```
Given job имеет retryCount=2 (два повтора перед успехом)
When запрашивается сводка за период, включающий этот job
Then retryRate в соответствующей строке учитывает этот job как "имевший повтор" —
     проверяется прямым булевым условием retryCount > 0, не приближённо
```

```
Given ни один job с данным taskType ещё не завершился (все ещё RUNNING/QUEUED)
When запрашивается сводка
Then avgDurationMs и p95DurationMs — null, не 0 и не ошибка —
     0 подразумевал бы "вызовы мгновенные", это неправда, честное отсутствие данных
```

```
Given запрошен GET /admin/telemetry/tasks/material-chat?status=FAILED&limit=50
When в БД только 3 проваленных job с этим taskType
Then возвращается ровно 3 записи, не дополняется вызовами других статусов до лимита
```

## 6. Что сознательно не входит — и почему это реальное ограничение, не лень

- **Стоимость вызовов в деньгах.** Требует: (а) чтения `usage`/token-полей из ответа
  каждого из трёх AI-провайдеров (сейчас не читается вообще), (б) таблицы актуальных цен за
  токен по каждой модели (меняются вне контроля проекта), (в) решения, как быть с уже
  устаревшими ценами для исторических записей. Это отдельная ревизия, не строка в этой.
- **Алертинг / уведомления при аномалиях** (например, «FAILED-доля выросла на 20% за час») —
  требует выбора канала (email/Telegram/webhook) и порогов, которые нужно откалибровать на
  реальном трафике проекта, не выдумать заранее.
- **UI/дашборд.** Как и в `devils-advocate-prompt-framework-tz.md` — эта ревизия описывает
  только API; при реальной соло-разработке админ-эндпоинты можно опрашивать напрямую
  (curl/Postman) без визуального слоя, пока не появится конкретная нужда в нём.
- **Предвычисленные агрегаты / отдельная таблица роллапов** — сознательно не проектируется
  на этом этапе (см. §4.1) — добавлять инфраструктуру под нагрузку, которой нет, значило бы
  усложнять раньше необходимости.
- **Трейсинг отдельного запроса через несколько AI-вызовов** (например, весь путь одной
  material-chat сессии от первого сообщения до последнего) — телеметрия этой ревизии
  агрегирует **по фиче за период**, не связывает вызовы друг с другом в один пользовательский
  сценарий; это другая, более сложная задача (нужен correlation id, которого сейчас нет ни в
  одной записи), не входит.
