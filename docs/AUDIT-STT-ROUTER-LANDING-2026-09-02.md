# Аудит проекта 2026-09-02 (второй за день): STT-провайдеры, AI-роутер, job-landing

Запрос владельца: «полный аудит проекта, упор на stt provider, ai
router, job-landing». Первый аудит дня (`AUDIT-PROJECT-2026-09-02.md`)
закрыл общие находки и доработал ТЗ лендинга; после него в проект вошёл
Пункт [stt-multi] (Soniox / AssemblyAI / ElevenLabs), и этот проход
смотрит в первую очередь на него, на асинхронную полосу роутера и на
воронку лендинга.

Метод: три независимых прохода по трём областям (каждый — чтение кода,
схемы, тестов и документации без запуска), затем проверка КАЖДОЙ
находки по коду вручную, исправление подтверждённых и регрессионный
тест на каждую значимую правку. Живых API, Postgres и Telegram в
песочнице нет — всё, что требует их, названо ниже как непроверенное.

Итог: 2 блокера, 9 дефектов среднего веса, ~20 мелких — все
подтверждённые исправлены. Отклонённые находки перечислены отдельно.
Проверка после правок (включая продолжение, §6): 817 jest + 704 standalone (api), 100 (tma),
10 (landing), lint 0, тайпчек четырёх приложений, `nest build`.

## 1. STT-провайдеры (Пункт [stt-multi])

### 1.1 БЛОКЕР — повторная доставка вебхука разговора не идемпотентна по побочным эффектам

`ConversationsService.handleTranscriptionWebhook`. Оба провайдера
ретраят вебхук на не-2xx и на таймаут нашего ответа — а обработчик
делает GET результата, пишет транскрипт, ставит паралингвистику и
трогает счётчик потребителей файла, то есть ответить быстро не может.
Транскрипт при повторе перезаписывался идемпотентно (upsert + deleteMany
— исправление 30.08), но дальше повтор:

- ещё раз вызывал `paralinguistics.enqueueForConversation` — вторая
  платная джоба на тот же разговор;
- ещё раз вызывал `releaseMediaConsumer(id, 1)` — счётчик 2 → 1 → 0, и
  файл удалялся, пока первая паралингвистическая джоба его ещё читала
  (гарантированный отказ второго потребителя, а не гипотеза).

Исправление: разговор, ушедший дальше `TRANSCRIBING`, повтор не трогает
(`{ acknowledged, matched, duplicate: true }`); `FAILED`
переобрабатывается намеренно — прошлая попытка могла упасть на
временной ошибке GET, а результат у провайдера готов. Тест: две
доставки → одна паралингвистика, файл жив, счётчик 1, транскрипт не
удвоен.

### 1.2 БЛОКЕР — голосовые реплики: гонка двух доставок

`SparringService` / `MaterialChatService.handleVoiceReplyWebhook`
проверяли `job.status === PENDING` обычным чтением, затем секунды
ждали ответ AI-оппонента и только потом писали `COMPLETED`. Вторая
доставка в этом окне проходила ту же проверку — две пары реплик в
диалоге, двойной счёт LLM.

Исправление: новое значение перечисления `PROCESSING`
(`SparringVoiceReplyStatus`, общее для обеих моделей; миграция
`voice_reply_processing_2026_09_02.sql` — `ALTER TYPE … ADD VALUE IF NOT
EXISTS`, выполнять отдельным вызовом без транзакции ДО выката кода) и
атомарный забор `updateMany({ where: { id, status: PENDING }, data: {
status: PROCESSING } })` — второму обработчику `count = 0`. Клиент TMA
(`SparringSection`, `MaterialChatSection`, `types.ts`) опрашивает
`PROCESSING` как `PENDING`. Тесты: `Promise.all` двух доставок → одна
пара сообщений в обоих сервисах.

### 1.3 Soniox хранил файл и транскрипт 30 дней

`/v1/files` и `/v1/transcriptions` у Soniox живут до 30 дней по
умолчанию, и удаление транскрипта НЕ удаляет файл. Реализация [stt-multi]
не делала ни одного DELETE — при том что согласие пользователя
(`EPHEMERAL_SERVER`) обещает транзит, а не хранение у субподрядчика, и
у нас самих файл удаляется по завершении потребителей.

Исправление: `SonioxSttProvider.cleanup(apiKey, transcriptionId,
fileId)` — оба DELETE, best-effort (отказ — warn, результат не
теряется; 404 — не отказ). Вызывается в `fetchResult` после чтения
транскрипта и на ветке `error`; НЕ вызывается, пока задача не готова
(вебхук придёт снова); в `transcribeSync` — в `finally`. Тесты: порядок
запросов (GET status → GET transcript → DELETE transcription → DELETE
file), отсутствие DELETE для `processing`, уборка при ошибке, отказ
сети на уборке не теряет результат. Граница: незавершённую задачу
Soniox удалить не даст — для неё действует retention провайдера.

### 1.4 Тексты согласий называли только AssemblyAI

`ThirdPartyAudioConsentPrompt` и `AudioProcessingConsentPrompt`
описывали получателя звука как AssemblyAI — для ru/uk-сессии это
неправда с момента [stt-multi]. Оба текста переписаны (Soniox для ru/uk,
AssemblyAI для en, ElevenLabs при сбое; у провайдера копия удаляется
после результата), версия текста `v2`. Повторного запроса у уже
согласившихся нет: бэкенд проверяет тип согласия, не версию;
получатель сменился на равного по договору субподрядчика, круг данных
не расширился. Это продуктовое решение — если владелец считает иначе,
достаточно проверки версии в `ConsentService`.

### 1.5 Потолок опроса AssemblyAI на синхронной полосе

40 с — «фоллбек для всех» на английском упирался бы в 504. Выровнено:

`sttProvider` в `requestTranscription`). Компонентами сейчас не
используется (основной путь — blob), поправлено, чтобы не стало
ловушкой.

## 2. AI-роутер

### 2.1 Идемпотентность игнорировала выбранную модель

`hashInput` не включает `preferredModelVersionId`, а `findReusableResult`
не фильтровал по модели: «сравнить движки» на одном промпте
(селектор §3.15) молча возвращало ответ прошлой модели за новую, с
`aiInferenceId` чужого движка в телеметрии. Исправление: фильтр
`modelVersionId` разрешённой модели в поиске переиспользуемого
результата (надёжнее, чем хэшировать предпочтение — важна фактически
выбранная модель). Тест.

### 2.2 `pollRunning`: блокировка вне транзакции и голодание очереди

`SELECT … FOR UPDATE SKIP LOCKED` вне транзакции отпускает блокировку
сразу по завершении запроса — два одновременных срабатывания крона
опрашивали одни и те же джобы (двойной GET к провайдеру и гонка записи
результата). Второе: `ORDER BY "updatedAt"` без её изменения при опросе
означало, что при очереди длиннее `limit` одни и те же старые джобы
опрашивались каждый раз, а свежие — никогда. Исправление: `UPDATE …
SET "updatedAt" = now() WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)
RETURNING id` — кто поднял, тот опрашивает, очередь ходит по кругу.
Тест на форму запроса.

### 2.3 Lease при заборе QUEUED

`claimQueuedJobs` ставил двухчасовой `EXTERNAL_INTERACTION_MAX_WAIT_MS`
в момент забора; воркер, упавший между забором и постановкой, оставлял
джобу `RUNNING` без `externalInteractionId` на два часа, хотя провайдер
о ней не знал. Теперь при заборе — `QUEUED_LEASE_MS` (15 мин),
двухчасовой — после реальной постановки в `submitQueued`.

### 2.4 `inputScanStatus` никогда не заполнялся

Блокировка сканом бросала ошибку ДО создания джобы, а прошедшие джобы
оставались с дефолтным `PENDING` — `AIJob.inputScanStatus = BLOCKED` не
появлялся в базе никогда, и телеметрия `inputBlockedCount`
(`TelemetryService`) была структурно нулём: операторская сводка молча
показывала «инъекций нет». Исправление: прошедшая джоба создаётся с
`PASSED`; заблокированная попытка записывается FAILED-джобой с
`BLOCKED`, привязкой результатов скана и владельцем
(`recordBlockedAttempt`, best-effort — отказ записи не превращает
честный отказ клиенту в 500). Побочный эффект, названный: заблокированные
попытки теперь считаются в суточный лимит пользователя — для скрипта,
жгущего инъекции, это плюс. Тесты.

### 2.5 Отдельный потолок медиа-задач

Общий `AI_CALLS_PER_USER_PER_DAY` (300) не сдерживал медиа-разборы, где
один вызов стоит на порядки дороже текстового. Добавлен
`AI_MEDIA_CALLS_PER_USER_PER_DAY` (дефолт 20, 0 = выключено), счёт по
`taskType` запроса (у медиа-задач свои типы; отдельного столбца «медиа»
нет, заводить его ради счётчика — лишняя миграция). Документировано в
`API-AND-KEYS.md`. Тест.

### 2.6 Мелкое, исправлено

- `AIRouterNoCapableModelError` нёс общий текст «либо… либо…», точная
  причина уходила только в лог; теперь причина в сообщении (нет
  строк / нет ключа у кого / устаревший `preferredModelVersionId`).
  Имена переменных окружения — не секреты, значения не попадают.
- `EnvSecretProvider` писал ERROR на каждый штатный вопрос «есть ли
  ключ» (`providerHasUsableKey` на каждом подборе модели, STT на каждом
  фоллбеке) → debug.
- Ветка `fallbackModelVersionId` названа тем, что она есть: рабочий, но
  никем не активируемый механизм (джоба создаётся внутри `prepareJob`,
  «проставить через update перед execute» невозможно). Код оставлен под
  будущий выбор запасного движка.
- Комментарии `ai-error-passthrough` («50 сервисов» — фактически 48
  файлов; переформулировано без цифры).

### 2.7 Отклонено

- «Стейл-комментарии о taskType в схеме и сиде» — комментарии описывают
  историю поля и помечены датами; не дезинформируют.
- «Стейл-тест ai-engines» — спека проверяет текущий контракт селектора
  (`providerHasUsableKey`), расхождения с кодом не найдено.

Пробелы в покрытии, названные аудитом, подтверждены и закрыты тестами:
«enqueue без ключа Gemini» (точная причина в ошибке: `google
(GEMINI_API_KEY)`), «фоновая модель через execute()» (отвергается с
названием модели и полосы), «суточный лимит на enqueue()»,
«идемпотентность против выбора движка», «повторный вход pollRunning»
(форма claim-запроса).

## 3. job-landing и воронка

### 3.1 Абсолюты в секции «Приватность»

`jobs.ts` (три словаря): «нигде не хранится» / «never stored»,
«не публикуются» / «never published». Первое — обещание за
субподрядчика, которое страница дать не может (звук обрабатывает Soniox
/ AssemblyAI по своим условиям); второе неверно буквально — у продукта
есть публичные ссылки по явному действию пользователя. Переписано в
проверяемую форму с именами провайдеров — те же, что в тексте
согласия TMA (§1.4). Принцип проекта: честная документация вместо
выгодной.

### 3.2 Переключатель языка терял utm

С `/ru/jobs?utm_source=x` выбор «UK» уводил на `/uk/jobs` без query — и
в Telegram человек уходил без кампании. `withLocale()` вынесен в
`lib/locale-path.ts` (чистая функция, тест), сохраняет query;
компонент читает `window.location.search` в эффекте, а не
`useSearchParams()` — последний на статической странице требует
Suspense-границы, иначе падает `next build`.

### 3.3 Квиз не знал, откуда пришёл человек

Источник посадочной сохранялся в `IntakeSession.source`, но ни на что не
влиял: первый экран показывал пример «в меня въехали на парковке», а
классификатор получал только текст. Теперь `intake/page.tsx` подставляет
вводный текст и пример под аудиторию (`candidate` / `agency`), а
`IntakeService.landingContextHint(source)` добавляет классификатору
контекст («пришёл с посадочной для соискателей — если описание не
противоречит, это job-search»). Подсказка, не приказ: сценарий
предлагает модель, подтверждает пользователь (§2.2 ТЗ intake не
нарушен); неизвестный источник (токен приглашения) подсказки не даёт.
Тест.

### 3.4 Панели interview-pool и ошибки

`InterviewPoolWorkspace.tsx` хранил ошибки строками и печатал их как
есть — на 403 «нет согласия» пользователь видел `Consent required:

этого и был написан ([ai-errors-ui]). У «Пересчитать» релевантность —
`try/finally` без `catch`: отказ уходил в unhandled rejection. Все

свой catch с текстом.

## 6. Продолжение того же дня — закрытые «названо, не сделано»

### 6.1 `releaseMediaConsumer` — атомарный декремент

Было: «прочитать → посчитать → записать» двумя запросами; два
потребителя, освобождающиеся одновременно (вебхук расшифровки и
завершение паралингвистики), могли оба прочитать 2 и оба записать 1 —
файл висел до сторожевой. Стало: условный `updateMany` с `decrement`
(`pendingMediaConsumers >= count`, иначе прижим к нулю), а удаление
файла — под условием «ссылка ещё та же»: обнулить её может один вызов,
и только он удаляет байты. Тесты: два одновременных освобождения — одно
удаление, счётчик 0, ссылка снята; лишний релиз не уводит в минус.

### 6.2 Имя и MIME файла для Soniox

`Content-Type` запроса клиента теперь идёт от контроллеров (разговор,
спарринг, чат по материалам) через `SttService.uploadAudio` до
провайдера; Soniox получает `Blob` с типом и имя с расширением
(`audio.webm`, `audio.m4a`…) вместо безымянного `audio` без типа.
Нормализация (`audio/webm;codecs=opus` → `audio/webm`), не-аудио —
без типа. AssemblyAI параметр не использует. Тесты.

### 6.3 `previewShare` — флаг `accepted`

Повторно открытая ссылка «Поделиться кандидатом» показывала кнопку
«Принять» на уже принятом профиле, нажатие давало 400. Превью отдаёт
`accepted: boolean` (кто принял — не раскрывается), экран
`/candidate-shares/[token]` показывает «уже принят ранее» вместо кнопки.

### 6.4 Документация

`README.md`: таблица документов утверждала «14 отчётов аудитов, последний
— `AUDIT-RERUN-2026-08-30`» при фактических 22 и восьми сентябрьских;
не упоминала разбор STT-провайдера и ТЗ job-landing в корне. Исправлено.
Добавлены два теста роутера из списка пробелов (§2.7).

### 6.5 Сторожевая голосовых реплик — гап, вскрытый состоянием PROCESSING

У `SparringVoiceReplyJob` / `MaterialChatVoiceReplyJob` не было
никакого терминального исхода без вебхука: не пришёл вебхук (провайдер
не доставил, задача упала у него без уведомления, секрет сменили
посреди полёта) — PENDING навсегда; с 1.2 обработчик, умерший посреди
ответа оппонента (таймаут функции), оставлял бы PROCESSING навсегда.
Клиент при этом опрашивал статус каждые 2 с без потолка.

Сделано: `VoiceReplyReaperService.reapStale()` — PENDING старше 30 мин
и PROCESSING старше 5 мин (по `updatedAt`) → FAILED с честной причиной
(«результат от провайдера так и не пришёл» / «обработка прервалась
после распознавания — повторите запись»); вызывается тем же тиком
`POST /internal/ai-jobs/reap`, расписание pg_cron не меняется. Клиент
(обе секции TMA) перестаёт опрашивать через 3 минуты и прямо предлагает
записать заново. Восстановления результата в сторожевой нет намеренно —
это повторило бы весь обработчик вебхука с его гонками ради редкого
случая. Тесты: пороги, свежие и терминальные не трогаются.

### 6.6 Что остаётся у провайдера после удаления у нас

Три связанных пробела, найденных по следу 1.3:

- **AssemblyAI хранил текст транскрипта бессрочно.** Уборка 1.3 была
  сделана только для Soniox; у AssemblyAI после чтения результата ничего
  не удалялось — при том, что согласие обещает «у нас — расшифровка, у
  провайдера — ничего». Теперь `DELETE /v2/transcript/{id}` после чтения
  (вебхучная и синхронная полосы), best-effort; удаление снимает данные
  транскрипта, оставляя пустую запись со статусом — так это и названо в
  тексте ответа `DELETE /privacy/account` и на экране `/privacy`.
- **Бесхозные задачи.** Вебхук на разговор или реплику, удалённые до
  завершения, подтверждался — и всё: задача с записью оставалась у
  провайдера на весь retention. Провайдер в этот момент известен только
  по форме вебхука (`transcript_id` — AssemblyAI, `id` — Soniox), поэтому
  `parseSttWebhookPayload` отдаёт `providerHint`, а
  `SttService.discardOrphan(hint, id)` убирает задачу (у Soniox — и файл,
  file_id читается из статуса). Все три обработчика вебхуков вызывают её
  на «не найдено».
- **Удаление аккаунта не знало про аудио разговоров и задачи в полёте.**
  Шаг «внешние артефакты» удалял только доказательства ДТП; транзитный
  файл разговора (`Conversation.audioBlobPathname`) после каскада
  оставался в хранилище без ссылки — навсегда, потому что сторожевая
  ищет по строкам, а строки уже нет; задачи в TRANSCRIBING и голосовые
  реплики PENDING/PROCESSING оставались у провайдера. Теперь
  `PrivacyCenterService.discardInFlightAudio` до каскада удаляет файлы
  и отзывает задачи (best-effort, счётчики — в ответе и в AuditLog).
  `PrivacyCenterModule` для этого импортирует `ConversationsModule`
  (AudioBlobService) и `SttModule`.

Тесты: форма вебхука → подсказка провайдера; `discardOrphan` по
подсказке и без; отказ уборки не бросает; AssemblyAI `fetchResult` →
GET затем DELETE; все три вебхука на неизвестный id → уборка; удаление
аккаунта → файлы разговоров и три задачи (включая голый legacy-id как
AssemblyAI) убраны до каскада.

### 6.7 Удаление проекта — тот же пробел, что у аккаунта

`DELETE /projects/:id` делал `prisma.project.delete` — каскад снимал
строки, а доказательства ДТП в Blob, транзитное аудио разговоров и
задачи распознавания в полёте оставались (в TMA кнопки на этот эндпоинт
сейчас нет, но эндпоинт публичный и защищён только владением). Уборка из
6.6 вынесена в общий `ExternalArtifactsCleanupService`
(`common/external-artifacts/`, свой модуль — его импортируют
`PrivacyCenterModule` и `ProjectsModule`; граф модулей проверен
`app-bootstrap.spec`): `discardForUser` / `discardForProject` с одним
отчётом (доказательства найдено/удалено/не удалось, файлы разговоров,
задачи отозваны). `ProjectsService.remove` вызывает её до каскада;
`PrivacyCenterService.deleteAccount` — её же вместо собственной копии.
Тесты: спека сервиса (обе области, голый legacy-id как AssemblyAI, без
токена Blob), `remove()` убирает артефакты только для своего проекта,
отчёт доезжает до ответа и журнала аудита.

### 6.8 Следы AI-вызовов после удаления аккаунта

`AIJob.requestUserId` — не FK, каскад `user.delete` его не касается. После
удаления аккаунта в базе оставались: сериализованный запрос неисполненных
джоб (`pendingRequest` — текст пользователя целиком), обрывки ответов
провайдера (`partialResult`) и все выводы AI (`ai_inferences.output` —
разбор его ситуации), а воркер продолжил бы исполнять QUEUED/RUNNING
джобы удалённого человека и записывать результат. Теперь
`PrivacyCenterService.scrubAiTraces` после каскада: инференсы джоб
пользователя удаляются (все связи на `AIInference` объявлены
`SetNull`/`Cascade` — проверено по схеме, а сущности пользователя к этому
моменту уже сняты каскадом), QUEUED/RUNNING → CANCELLED (воркер выбирает
только QUEUED/RUNNING), `pendingRequest` и `partialResult` обнуляются.
Строки джоб остаются — телеметрия по типу задачи и статусу без
содержимого; это названо в ответе и на экране `/privacy`. Честная
граница: фоновую задачу, уже отправленную Gemini, у провайдера мы не
отменяем — она завершится по его политике, результат у нас не
сохраняется. Тест: выводы удалены, очередь отменена, тексты обнулены,
чужие джобы не тронуты, порядок «после каскада».

### 6.9 «Скачать все мои данные» отдавало три коллекции

`GET /privacy/export` (GDPR art. 15) собирал проекты с пятью связями,
персон с фактами и согласия — без разговоров и транскриптов, ответов
квиза, спарринга, чатов по материалам, заметок, обязательств, профилей
кандидатов, медиа-очередей. То есть большая часть продиктованного
продукту в «все мои данные» не попадала. Теперь выгрузка включает эти
коллекции (транскрипты — с сегментами по порядку, сессии — с
сообщениями) и рядом честный `notIncluded`: аудио не хранится,
обезличенная телеметрия AI-вызовов, служебный журнал аудита, данные
других участников команд. Тест фиксирует набор ключей ответа как
контракт полноты: новая коллекция без записи в выгрузке роняет тест, а
не остаётся тихой неполнотой. TMA отдаёт JSON как есть — правок там не
понадобилось.

Проверена и обратная сторона — поля `*UserId` без FK по всей схеме:
кроме `AIJob.requestUserId` (закрыто в 6.8) и `AuditLogEntry.actorId`
(намеренно), все остальные каскадируют через Person / PersonFact /
Project / DtpEvidenceItem.
