# Исчерпывающий аудит Google Fact Check Tools API — 2026-08-30

Проверка `discrepancy-analysis.service.ts` (`fetchFactCheckClaims`/`checkAgainstFactCheckAPI`)
по трём источникам: официальной документации Google (`developers.google.com/fact-check/tools/api`,
прочитана целиком — REST-референс метода `claims.search` и схема ресурса `claims`),
реальным реализациям на GitHub (`josemreis/google-factCheck-helpers`, официальные
`google-api-nodejs-client`/`google-api-go-client`), и построчным сравнением с кодом.

## Endpoint, auth, схема запроса — проверено, соответствует документации

- `GET https://factchecktools.googleapis.com/v1alpha1/claims:search` — точное совпадение
  с REST-референсом. `v1alpha1` в пути — не признак нестабильности или устаревания:
  API официально остаётся на этой версии с момента запуска (~2018), Google не
  анонсировал `v1`. Не путать с ситуацией AssemblyAI/SerpApi сегодня раньше —
  эндпоинт живой и рабочий.
- Авторизация — `key=<API_KEY>` query-параметром. Подтверждено и документацией, и
  референсной Python-обёрткой на GitHub (`"key": 'XXXX...'` в примере вызова) —
  верный способ, не спутан с OAuth (OAuth нужен только для `pages.*`-методов,
  управления ClaimReview-разметкой, которыми проект не пользуется).
- `query` — единственный обязательный параметр (если не задан
  `reviewPublisherSiteFilter`) — используется корректно, через `URLSearchParams`
  (безопасное кодирование, без риска двойного кодирования).

## Схема ответа — проверено полями по официальному REST-референсу ресурса `Claim`

| Поле в коде | Путь в официальной схеме | Совпадает |
|---|---|---|
| `text` | `Claim.text` | ✅ |
| `claimant` | `Claim.claimant` | ✅ |
| `claimDate` | `Claim.claimDate` | ✅ |
| `publisher` | `Claim.claimReview[].publisher.name` | ✅ |
| `textualRating` | `Claim.claimReview[].textualRating` | ✅ |
| `reviewUrl` | `Claim.claimReview[].url` | ✅ |

Ни одного расхождения в именах полей — в отличие от сегодняшних находок в
AssemblyAI/SerpApi, здесь исходная реализация была построена по актуальной и
стабильной документации и не разошлась с ней.

## Найдено и исправлено — тело ответа при ошибке отбрасывалось

Тот же класс проблемы, что чинился сегодня дважды (AssemblyAI, ElevenLabs):
`if (!response.ok) throw new BadGatewayException(...response.status...)` — без тела
ответа. Google для этого API обычно возвращает
`{"error":{"code","message","status"}}` с точной причиной — например
`PERMISSION_DENIED` («API не включён в Google Cloud Console для этого проекта»),
`RESOURCE_EXHAUSTED` (квота), `INVALID_ARGUMENT` (плохой ключ). Без тела все три
неотличимы друг от друга по одному HTTP-статусу — оператор видел бы только «403»,
без единой подсказки, что делать. Исправлено: тело читается и попадает в текст
исключения (обрезано до 300 символов, тот же лимит, что в сегодняшних фиксах
AssemblyAI/ElevenLabs). Тест не существовал вообще — добавлен, с реалистичной
формой ошибки Google.

## Проверено, не изменено — не баги, а сознательно не покрытые возможности

- **`pageSize` не задаётся явно** — дефолт API 10 результатов. Для сценария
  использования (точечная проверка одной конкретной реплики, не исследовательский
  запрос) это разумно. Референсная Python-обёртка на GitHub в реальном
  использовании задаёт `pageSize: 50` для батчевого поиска по нескольким темам —
  другой сценарий использования, не аргумент, что 10 здесь неверно.
- **`ClaimReview.title` и `ClaimReview.reviewDate`** существуют в схеме API, но не
  извлекаются текущим кодом (`claimDate` — дата исходного утверждения — извлекается,
  `reviewDate` — дата публикации разбора, потенциально более релевантная для оценки
  свежести вердикта — нет). Не баг, полноценная опция для UI на будущее, не
  добавлено без отдельного запроса.
- **Пагинация (`nextPageToken`) не реализована** — код смотрит только первую
  страницу. Соответствует сценарию «есть ли вообще фактчек по этой реплике»,
  не «собрать все существующие фактчеки» — сознательный, не случайный охват.

## Итог

Один настоящий, исправленный баг (отброшенное тело ошибки — снижает диагностируемость,
не ломает основной happy path) — заметно меньше, чем у AssemblyAI/SerpApi сегодня,
потому что базовая схема запроса/ответа была построена по актуальной документации
с самого начала и с тех пор не разошлась с реальностью (в отличие от вебхуков
AssemblyAI и особенно SerpApi, где сама внешняя API изменилась под ногами проекта).
Jest: 63 сьюта / **511** тестов (было 510), 1 новый регрессионный тест.

## Расширено на будущее (2026-08-30, по прямому запросу)

Три опции, отмеченные выше как «не баг, полноценная опция на будущее», реализованы:

- **`pageSize=20`** задаётся явно (было — дефолт API, 10).
- **Пагинация**: `fetchAllPages()` следует `nextPageToken` до `FACT_CHECK_PAGE_LIMIT`
  (3) страниц — до 60 claims на один вызов вместо 10. Потолок — намеренный: без
  него одна проверка одной реплики могла бы утянуть неограниченно много страниц у
  API с исторически невысокой квотой; честно останавливается раньше потолка, если
  Google не вернул `nextPageToken`, не запрашивает заведомо пустые страницы.
- **`title` и `reviewDate`** из `ClaimReview` добавлены в `FactCheckClaim` (backend
  и клиентский тип TMA) — заголовок разбора и дата его публикации (не путать с
  `claimDate` — датой исходного утверждения). `title`, если есть, попадает и в
  текст доказательства (`factCheckSourceDescription`), и в саму ссылку в TMA
  (вместо обезличенного «разбор»); `reviewDate` показывается рядом. Оба поля
  опциональны — код не падает и не подставляет пустышку, если фактчекер их не
  указал (отдельный тест на этот случай).

Не тронуто: `pageSize` не вынесен в конфигурацию/env — константа в коде, тот же
принцип, что у `PAGE_LIMIT`; `reviewPublisherSiteFilter`/`languageCode`/`maxAgeDays`
не добавлены — под них нет сформулированного сценария использования, добавление
«про запас» без него было бы спекуляцией, не расширением.

Backend: 63 сьюта / **516** тестов (было 511, +5 — pageSize, пагинация с
объединением страниц, потолок пагинации, title/reviewDate в happy path, отсутствие
title не ломает описание). TMA: `tsc` и `next build` чистые.
