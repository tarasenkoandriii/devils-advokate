# Аудит интеграции AssemblyAI — 2026-08-30

Сверка `apps/api/src/conversations/transcription.service.ts` и трёх вебхук-хендлеров
(`conversations`, `sparring`, `material-chat`) с официальной документацией AssemblyAI
(проверено веб-поиском по docs.assemblyai.com — не только по присланному промпту,
который сам себя называет снимком и просит перепроверять live-доки).

## Критическая находка — вебхуки читали несуществующие поля

**Реальное тело вебхука AssemblyAI:** `{ "transcript_id": "...", "status": "completed" }`
— и больше ничего. Ни текста, ни `utterances`, ни поля `error`. За полным результатом
нужен отдельный `GET /v2/transcript/{transcript_id}` (подтверждено официальной
страницей `docs.assemblyai.com/pre-recorded-audio/webhooks` и независимо ещё четырьмя
источниками).

Код проекта был написан так, будто вебхук уже несёт всё целиком:
- Все три хендлера читали `payload.id` — поля `id` в реальном ответе нет, только
  `transcript_id`. Значение было ВСЕГДА `undefined`.
- В `conversations.service.ts` это уходило в `prisma.conversation.findFirst({ where:
  { externalTranscriptionJobId: undefined } })` — Prisma трактует `undefined` в `where`
  как «условие не задано» и возвращает **первую попавшуюся запись в таблице**. Реальный
  риск привязать транскрипт к чужому разговору, не гипотетический — воспроизведено
  отдельным тестом с честной имитацией Prisma-семантики (фейк в существующем тесте
  был слишком строгим и не ловил бы эту проблему сам по себе).
- `payload.utterances` тоже был обречён быть пустым всегда — ни один разговор никогда
  не получил бы ни одного сегмента транскрипта, даже при полностью исправной во всём
  остальном интеграции.

**Исправлено:**
- `TranscriptionService.getTranscriptResult()` — новый метод, `GET /v2/transcript/{id}`.
- `parseTranscriptResult()` вместо `parseWebhookPayload()` — работает над результатом
  GET, не над телом вебхука.
- `AssemblyAiWebhookPayload` переписан под реальную форму: только `transcript_id` +
  `status`.
- Все три хендлера: сопоставление по `payload.transcript_id`, явный fail-closed guard
  на пустое значение (не полагаемся на то, что Prisma «как-нибудь разберётся»), затем
  отдельный GET за результатом — и для `completed`, и для `error` (текст ошибки тоже
  не в вебхуке).

## Вторая находка — `speech_models` не задавался явно

Параметр опциональный; при отсутствии AssemblyAI молча откатывается на
`["universal-3-pro", "universal-2"]`, не на текущий флагман. Для продукта, который
специально полагается на качество диаризации (детекторы манипуляций работают на
разборе по репликам), разница между моделями не косметическая. Добавлено
`speech_models: ['universal-3-5-pro', 'universal-2']` в `submitJob()`.

## Проверено — соответствует документации, без изменений

- **Auth header** — `Authorization: apiKey` без `Bearer`-префикса, во всех трёх местах
  (`submitJob`, `getTranscriptResult`, `streamUpload`). Правильно для REST (Voice Agent
  API, которого в проекте нет, требовал бы `Bearer` — не перепутано).
- **Устаревшие параметры** (`auto_chapters`, `summarization`, `summary_model`,
  `summary_type`) — не используются нигде.
- **`/v2/upload`** — сырой поток (`body: fileStream`), не multipart; без явного
  `Content-Type`, что соответствует официальному примеру proxy-загрузки.
- **`webhook_auth_header_name/value`** — уже был правильно реализован более ранним
  проходом аудита сегодня (`ASSEMBLYAI_WEBHOOK_SECRET`, `AssemblyAiWebhookGuard`),
  штатный, документированный механизм аутентификации вебхуков без HMAC-подписи.
- **`language_code`** передаётся только когда пользователь его явно указал
  (`dto.languageCode` опционален) — при отсутствии `JSON.stringify` просто опускает
  ключ, и `universal-3-5-pro` code-switch’ит нативно между 18 языками без конфигурации.
  Уже было правильно, специально ничего не менял.
- **Sync API** (короткие клипы, единый запрос без polling) — не применим к этому
  продукту (записи разговоров произвольной длины), и не используется. Правильный выбор
  архитектуры — асинхронный submit + webhook, что и реализовано.
- **Realtime STT, слой минтинга токена** (`LiveSessionService.mintTranscriptionToken`)
  — выдача короткоживущего токена браузеру, сервер не проксирует аудио, соответствует
  разделу 9/12 промпта. Эндпоинт `GET streaming.assemblyai.com/v3/token`, заголовок
  `Authorization` без `Bearer`, `expires_in_seconds` — верно; значение не клиентское
  (фиксированные 300, в допустимом диапазоне 1–600), инъекция параметра невозможна.

## Третья находка (продолжение, отдельный проход) — WebSocket без speech_model/mode

`connectLiveTranscription()` в TMA (клиентская сторона live-подключения) строил URL
`wss://streaming.assemblyai.com/v3/ws?sample_rate=16000&speaker_labels=true&token=...`
— **без `speech_model` и `mode` вообще**. Это ровно то, что сам промпт называет «самой
частой ошибкой интеграции» применительно к путанице singular/plural, но здесь хуже —
параметр отсутствовал полностью, не был перепутан с pre-recorded вариантом.

Проверка живой документации показала **расхождение между источниками**: одна
официальная страница `docs.assemblyai.com/streaming/universal-streaming` утверждает
«параметр обязателен, дефолта нет, при отсутствии запрос будет отклонён», changelog —
что параметр «недавно стал опциональным, при отсутствии использует дефолт аккаунта».
Сам API в этой части, по всей видимости, ещё не устоялся. При любой трактовке
отсутствие параметра — плохой исход: либо соединение не открывается вовсе, либо тихо
закрепляется за моделью, отличной от нужной продукту (старые `universal-streaming-*`
модели не поддерживают часть параметров, которые уже используются в связке).

**Исправлено:** добавлены `speech_model=universal-3-5-pro` (та же модель, что в
async-пути после первой находки — согласованность между двумя путями транскрипции) и
`mode=balanced` (основной регулятор латентность/точность, который сама документация
советует ставить в первую очередь). Функция `connectLiveTranscription()` не имела
вообще ни одного теста — добавлен один, с минимальными браузерными заглушками
(`WebSocket`/`AudioContext`), проверяющий итоговый URL.

## Четвёртая находка (продолжение) — сессия не завершалась явным Terminate

`connectLiveTranscription().stop()` вызывал `ws.close()` напрямую, никогда не отправляя
управляющее сообщение `{"type": "Terminate"}`. Документация называет это обязательным
шагом дважды (разделы 9 и 15: «Always terminate realtime sessions explicitly», «Always
send this when done!») и объясняет цену: «An abandoned WebSocket keeps accruing charges
until the 3-hour cap». Раз в проекте уже включён `speaker_labels=true`, есть и вторая
цена: `SpeakerRevision` (уточнение диаризации по всей сессии) приходит СТРОГО в ответ на
`Terminate`, прямо перед закрытием — без него клиент никогда не получил бы уточнённые
метки говорящих для live-функций.

**Исправлено:** `stop()` теперь отправляет `Terminate` первым действием, если сокет
открыт, и форсирует закрытие защитным таймаутом (2 с) только если сервер не закрыл
соединение сам — вместо немедленного `ws.close()`. Разбор самого `SpeakerRevision`
сообщения (ретроактивное обновление уже показанных реплик в UI) — отдельная,
более крупная задача, не сделана в этом проходе, честно не заявлена как исправленная.
Тест на `stop()` подменяет `global.setTimeout` на no-op локально в тесте (не в
продакшен-коде — там `setTimeout` браузерный, `.unref()` недоступен), чтобы не
держать процесс раннера открытым лишние 2 секунды на каждый прогон.

## Пятая находка (продолжение) — серверное закрытие сокета не сообщало ничего пользователю

`connectLiveTranscription()` не имел `ws.onclose` вообще — только `ws.onerror`. По
спецификации WebSocket это разные события: серверное закрытие с конкретным кодом
(документация перечисляет 1008, 3005–3009) не обязано порождать `error`, только
`close`. Практическое следствие: если AssemblyAI закрывал сокет (истёк токен, сессия
превысила лимит, чанк аудио вне диапазона 50–1000 мс), live-функции (подсказки, экран
сопровождения) молча переставали получать транскрипт — `onError` никогда не
вызывался, пользователь продолжал считать сессию активной без единого сигнала о
проблеме. Для функции, которая может использоваться в напряжённом разговоре, это не
косметический пробел.

**Исправлено:** добавлен `ws.onclose` с таблицей сообщений по каждому
задокументированному коду (1008/3005/3006/3007/3008/3009 — конкретный текст на
русском под каждый, не общая фраза). Отдельно обработан конфликт с собственным
`stop()`: `closingIntentionally`-флаг отличает намеренное закрытие (после отправки
`Terminate`) от серверного — не полагаемся на угадывание, каким кодом AssemblyAI
закроет сокет после нашего же `Terminate` (документация explicitly этого не
специфицирует). Два теста: серверное закрытие с кодом из таблицы → осмысленное
сообщение без единого `onerror`; собственный `stop()` → тишина независимо от кода,
которым ответит сервер.
