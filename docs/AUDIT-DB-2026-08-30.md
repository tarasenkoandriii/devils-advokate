# Аудит моделей БД — 2026-08-30

`apps/api/prisma/schema.prisma`: 155 моделей, 85 enum'ов, 6035 → 6201 строк
после правок (только добавления, ни одной изменённой или удалённой строки — проверено diff'ом).
Проверка — скриптами по схеме и исходникам, не чтением.

## 1. Исправлено (аддитивно, без потери данных)

### 1.1 Индексы на FK-колонках — 120 штук
Postgres не индексирует внешние ключи автоматически, Prisma в режиме `foreignKeys` —
тоже. В схеме индексы были только на «главных» связях (`projectId` большинства
моделей, `userId` на consent/ai-jobs), а у **120 FK-колонок их не было вообще** —
включая `Project.ownerId` (каждый список проектов пользователя — seq scan по
`projects`), все `configId`/`advisorId`/`providerId`/`opportunityId`/`variantId` шести
доменов, все `generatedByInferenceId` (~30 моделей), `MediaReviewQueueItem.conversationId`.
Последствия: медленные `findMany({ where: { configId } })` при росте таблиц и —
важнее — **медленные каскадные удаления** (`onDelete: Cascade` на каждую дочернюю
таблицу без индекса по FK даёт seq scan при удалении родителя; удаление пользователя с
историей превращается в минуты).
Добавлено `@@index([fk])` перед `@@map` в каждой модели. SQL — `CREATE INDEX
CONCURRENTLY IF NOT EXISTS` (без блокировки таблиц на проде).

### 1.2 `updatedAt` — 41 модель
Модели, которые код реально обновляет (`update`/`updateMany`/`upsert`), но у которых
нет `updatedAt`: `User`, `ConsentRecord`, `ScheduledConversation`, `SparringSession`,
`LibraryEntry`, `VenueApplication`, `MediaReviewQueueItem`, все консультации/встречи
шести доменов, `DtpParticipantInsurance` и др. Без него нельзя ни отсортировать по
«последнему изменению», ни отличить застрявшую запись от свежей — ровно поэтому в
операторской панели media-review пришлось считать «застрявшие» через `conversation.updatedAt`.
Добавлено `updatedAt DateTime @default(now()) @updatedAt` — `@default(now())` нужен,
чтобы миграция прошла на непустых таблицах.

### 1.3 `createdAt` — 5 моделей
`EvaluationMetric`, `ProjectLogEntryPerson`, `SteelmanSupportingFact`, `LibraryArgument`,
`PoolRelevanceEntry` не имели **ни одной** временной метки. Добавлен `createdAt`. У
13 других моделей без `createdAt` есть семантическая метка (`joinedAt`, `occurredAt`,
`changedAt`, `decidedAt`…) — там ничего не добавлялось, дублировать нечего.

### 1.4 Enum-поля, которые TMA отправлял как свободный текст (мой дефект фазы B)
Анализ «значения enum'ов, не встречающиеся в src» показал `DtpFaultSource`,
`FamilyLawStatusSource`, `FamilyLawPartyRole` целиком неиспользуемыми — потому что
манифесты TMA делали `source`/`role` текстовыми полями. Backend валидирует
(`400 Unknown source`), т.е. **форма «Определение вины» и «Статус» никогда не могла
сохраниться**. Исправлено: селекты с человеческими подписями в манифестах и в доменной
вёрстке (`FAULT_SOURCE_LABEL`, `STATUS_SOURCE_LABEL`).

### 1.5 Конвенции схемы как тест
`src/__tests__/schema-conventions.spec.ts`: каждая модель имеет `@@map`, каждая
FK-колонка — индекс, каждая модель — хотя бы одну временную метку. Следующая модель
без индекса упадёт на CI, а не на следующем аудите.

Файлы: `prisma/manual-migrations/schema_audit_2026_08_30.sql` (166 statements).

## 2. Найдено, НЕ исправлено — нужно решение владельца

### 2.1 Деньги как `Float` — 20 полей
`EvaluationResult.value`, `ApprovedVenue.referralFeeAmount`, `VenueBookingConfirmation.referralFeeOwed`, `MajorPurchaseConfig.budgetMin`, `MajorPurchaseConfig.budgetMax`, `PurchaseVariant.askingPrice`, `MarketComparison.extractedPrice`, `InvestmentConfig.targetBudget`, `InvestmentGroupMember.pledgedAmount`, `HealthConfig.targetBudget`, `HealthConsultation.estimatedCost`, `FamilyLawConfig.targetBudget`, `FamilyLawConsultation.estimatedCost`, `DtpConfig.targetBudget`, `DtpConsultation.estimatedCost`, `DtpParticipantInsurance.coverageAmount`, `DtpBudgetLineItem.amount`, `FamilyLawAsset.estimatedValue`, `FamilyLawBudgetLineItem.amount`, `HealthBudgetLineItem.amount`.
`Float` = `double precision`: 0.1 + 0.2 ≠ 0.3, суммы в бюджетах и взносах группы будут
плыть на копейках. Правильно — `Decimal @db.Decimal(14, 2)`. **Не исправлено**, потому
что это не аддитивная правка: Prisma отдаёт `Decimal` как объект `decimal.js`, а код
складывает суммы `+` в ~15 местах (`byCurrencyMap`, `totalEstimatedCost`,
`totalPledged`, `netBudget`…) — нужен проход по всем сервисам с `.toNumber()`/`Decimal.add`
и обновление тестов. Оценка: полдня, отдельный пункт.

### 2.2 Неиспользуемые модели — ровно 7, с доказательством (→ решение принято, см. 3)
README называл «11–13»; точная проверка по `prisma.<model>.` во всех сервисах даёт
**7 моделей без единого обращения**: `FactAssertion`, `Observation`, `AIInferenceSource`,
`ProjectLogEntry`, `ProjectLogEntryPerson`, `SteelmanSupportingFact`, `AIModel`.
Уточнения: `AIModel` используется в `seed.ts` и как родитель `AIModelVersion` (которая
используется) — удалять нельзя; `ProjectLogEntry` совпадает по имени с TS-интерфейсом в
`project-log.service.ts`, но таблица не читается — лог считается derived. Остальные 5 +
`ProjectLogEntry` — остатки ранней архитектуры фактов (заменена
`PersonFact`/`ConversationSignal`/`FactSource`). Семейство `Evaluation*`/`ReleaseGate`
**используется** (admin/prompts, evaluation runs) — в список «неиспользуемых» оно
попало ошибочно. Удаление — `DROP TABLE` × 6 + правка `User`/`Project`/`Person` relations;
решение за вами, как и было записано.

### 2.3 «Неиспользуемые значения enum'ов» — исправлено на методологию, не на код (2026-08-30, третий заход)
Повторная проверка нашла методологическую ошибку в исходном списке: grep по литералам
`\bVALUE\b` в `src` не видит значения, которые приходят от КЛИЕНТА через DTO
(`type!: RelationshipType`, `scope: input.scope`, `toStatus: ArgumentLifecycleStatus`) —
сервис использует ТИП, а не хардкодит конкретное значение. По этой причине
`RelationshipType/Direction`, `FactScope.PRIVATE_TO_USER/PUBLIC_DERIVED_ONLY`,
`ArgumentLifecycleStatus.TESTED` объявлены ложно — все они реально достижимы через API,
просто ни один сервис пока не ветвится по ним отдельно. Удалять их было бы неверно.
`ObservationSourceType`/`ProjectLogEventType`/`LogColorTone` сняты с повестки —
удалены вместе с моделями в разделе 3.1.

**Настоящая находка того же класса, что уже чинился в проекте (Пункт 77, LOCATION):**
`ConsentType.PUBLIC_SHARING` был в enum'е и в `GrantConsentDto` (клиент МОГ его
запросить), но `PublicDiscussionService.enableSharing()` ни разу его не проверял —
включение публичного обсуждения делало весь проект читаемым по токену без единого
согласия. **Исправлено**: `requireConsent(userId, ConsentType.PUBLIC_SHARING, projectId)`
перед выдачей токена, тем же паттерном, что LOCATION/HEALTH_DATA; TMA — экран согласия
перед первым включением (`PublicDiscussionSection.tsx`), отдельный от общего
`ConsentGate`, с объяснением именно этого доступа. Регрессионный тест: без согласия —
`ForbiddenException`, токен не выдаётся.

`ConsentType.PERSON_RESEARCH` — единственное подтверждённо мёртвое значение: под него
нет ни одной фичи (не спутать с `PUBLIC_IMAGE_SEARCH`, который уже используется
реверс-поиском фото). Оставлено как задокументированный задел, не удалено — потолок
для потенциального будущего использования дешевле, чем миграция `ALTER TYPE`
на не мешающее enum-значение.

### 2.4 Удаление пользователя (GDPR) не реализовано
В `User` — `onDelete: Cascade` почти везде, `RetentionClass`/`DeletionBehavior` описаны в
схеме, но **эндпоинта «удалить мои данные» нет** (`grep delete-account|erase` пусто).
Для продукта, который хранит транскрипты разговоров, медицинские и семейные данные,
это обязательный пункт ТЗ, а не улучшение. С индексами из 1.1 каскад уже не будет
занимать минуты.

### 2.5 Мелочи
- 9 связей без явного `onDelete` — все на справочники (`AIModelVersion`,
  `PromptVersion`, `EvaluationDataset`, `EvaluationMetric`); дефолтный `Restrict`
  для них правильный, оставлено.
- `IntakeSession.suggestedScenario/chosenScenario` — `String`, не enum: значения
  включают `'UNIVERSAL'` и dashed-id доменов; документировано в комментарии.
- 15 `Json`-полей (`criteriaBreakdown`, `answers`, `content`…) — форма задана только
  TS-типами сервисов; для `criteriaBreakdown` четырёх доменов форма одинакова,
  кандидат в общую таблицу, но не дефект.

## 4. По решению владельца (2026-08-30, второй заход) — закрыты оба пункта раздела 2

### 4.1 Деньги: Float → Decimal(14,2) — 19 полей
`EvaluationResult.value` оставлено `Float` — это метрика оценки промпта, не деньги.
Оказалось, что арифметика на деньгах в коде есть всего в **9 местах** (не в ~15, как
оценивалось): суммы бюджетов по валютам ×3 домена, `totalEstimatedCost` ДТП,
`totalPledged` инвест-группы, `totalFeesOwed` заведений. Решение:
- `src/common/money.ts` — `sumMoney()` (точная сумма через `Prisma.Decimal`, результат
  округлён до копеек), `toMoney()`, `decimalsToNumbers()`;
- `ApiResponseInterceptor` рекурсивно превращает `Decimal` → `number` на границе API —
  **контракт с TMA/admin не изменился** (иначе Prisma сериализует Decimal строкой);
- запись: DTO с `number` Prisma принимает для Decimal-полей без изменений.
Тест `money.spec.ts`: 0.1 + 0.2 = 0.3 ровно, 100 × 0.01 = 1.00, обход вложенных
структур без мутации входа. Миграция — `ALTER COLUMN … TYPE NUMERIC(14,2)` ×18
таблиц в `schema_audit_2026_08_30.sql`.

### 4.2 Удаление аккаунта — `DELETE /privacy/account`
`PrivacyCenterService.deleteAccount(userId, confirmation)`, `confirmation` строго
`"DELETE"`. Порядок: (1) внешние артефакты — Vercel Blob с доказательствами ДТП,
best-effort, ошибка одного файла не блокирует удаление; (2) запись в `AuditLog`
**до** удаления, `actorId: null`, в записи — sha256-хеш telegramId (16 символов) и
счётчики (проекты / разговоры / люди / согласия / intake / медиа), не сами данные;
(3) `prisma.user.delete` — все 16 связей на `User` каскадные (проверено в §2.5),
с индексами из §1.1 каскад больше не seq scan.
Ответ честно перечисляет, что НЕ удаляется здесь: копии транскриптов у STT-провайдера
(по его политике; у нас удалён текст), журнал аудита (без ПД), команды и группы (остаются
без вашего членства). TMA: блок «Удалить аккаунт и все данные» внизу `/privacy` —
ввод слова УДАЛИТЬ + confirm, после удаления — отчёт, что именно удалено и сколько
файлов не удалось убрать из внешнего хранилища. 4 теста.
Сознательное решение: `CandidateProfile.ownerUserId → Cascade` означает, что профили
кандидатов, созданные удаляемым пользователем и расшаренные в команду, удаляются
вместе с ним — право на удаление сильнее удобства команды; зафиксировано в
комментарии сервиса.

## 5. Продолжение (2026-08-30, четвёртый заход) — систематическая проверка ConsentType

После находки в §2.3/4 проверил остальные значения `ConsentType` тем же методом,
что подвёл в прошлый раз (не только grep по литералу, но и чтение каждого
потребителя `mintTranscriptionToken`/аналогичных точек входа).

- `RELIGIOUS_CONTENT` — ложная тревога: не проходит через `requireConsent()`, а
  через прямой `consentRecord.findFirst/create` в `ensureReligiousContentConsent()`
  (implicit opt-in с явным revoke) — реально обеспечивается, просто другим кодовым
  путём, который grep по имени хелпера не находил.

- **Настоящая находка: `THIRD_PARTY_AUDIO_RECORDING` не требовался нигде, кроме
  `DtpService.addEvidence()`.** Между тем `LiveSessionController.mintTranscriptionToken()`
  — точка входа в live-транскрипцию для ТРЁХ фич (`LiveHintsSession`,
  `AssistanceScreen` — экран сопровождения, `VoiceTextInput` в доменном
  онбординге/intake-квизе) — открывает канал browser→AssemblyAI, куда живой звук
  разговора (включая голос собеседника, не только пользователя) стримится
  напрямую, в реальном времени, без единой проверки согласия. Это ровно случай,
  под который заведено `THIRD_PARTY_AUDIO_RECORDING`, судя по её собственному
  doc-комментарию в schema.prisma («юридичний статус самого факту запису чужого
  голосу без його обізнаності»), и ровно тот прецедент, что уже применён к
  доказательствам ДТП.
  **Исправлено:** `mintTranscriptionToken(userId)` требует согласие первым
  действием (до обращения к AssemblyAI — подтверждено тестом: consent не дан →
  `fetch` не вызывается). Эндпоинт раньше не знал `userId` вообще — добавлен
  `@CurrentUser()`. TMA: `THIRD_PARTY_AUDIO_RECORDING` добавлен в клиентский
  `ConsentType` (его не было — тот же класс упущения, что `HEALTH_DATA` в фазе
  intake), новый компонент `ThirdPartyAudioConsentPrompt.tsx` (тот же паттерн,
  что `LocationConsentPrompt`), подключён во все три потребителя ПЕРЕД
  `startLiveAudioCapture` — сначала спрашивает браузер о микрофоне, только имея
  согласие пользователя приложению. 10 тестов (`live-session.service.spec.ts` +
  `public-discussion.service.spec.ts`).
  **Сознательное упрощение:** один тип согласия на все три сценария, хотя строго
  говоря `VoiceTextInput` обычно используется для надиктовки собственного ответа
  без второй стороны — разводить на `purpose`-параметр и второй тип согласия
  (`VOICE_PROCESSING`, уже используемый для TTS) не стал: усложнение не
  окупается, а текст согласия одинаково честен в обоих случаях (звук
  технически уходит третьей стороне всегда), и более строгая защита не создаёт
  трения, неприемлемого для одиночной надиктовки одной лишней кнопки.

Итог четвёртого захода: 61 jest-сьют / 494 теста + 666 standalone, TMA build — 0 ошибок.
