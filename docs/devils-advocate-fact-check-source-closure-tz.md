# Devil's Advocate — ТЗ: Закриття четвертого джерела звірки §3.16 через Fact Check Tools API

> Компаньон-документ до `devils-advocate-tz.md` (§3.16 implementation-ready) та
> `devils-advocate-media-review-tz.md`. Виникло з прямого запиту: раніше пошук публічно
> відомих фактів був свідомо звужений (Пункт 37/40) — тепер є конкретний, вже реалізований
> шлях (Google Fact Check Tools API з Пункту [media-review]) закрити цей розрив ширше, не
> тільки для аналізу YouTube-контенту.

---

## 1. Історія питання — чому це не нова фіча, а формальне визнання вже зробленого

**Пункт 37** (`DiscrepancyAnalysisService`, §3.16 implementation-ready) описував звірку по
ЧОТИРЬОХ джерелах: (1) база аргументації проекту, (2) минулі розмови з тим самим фігурантом,
(3) внутрішня несуперечність розмови, (4) **публічно доступні факти**. Реалізовано було (1)-(3)
— (4) **чесно виключено**, з формулюванням прямо в коді: вимагає зовнішнього пошуку, якого в
розгорнутому застосунку немає взагалі.

**Пункт 40** частково звузив цей розрив — `checkAgainstUserSource()`: користувач сам вставляє
конкретне посилання, сервер завантажує ЛИШЕ його. Явно НЕ автономний пошук — рішення, прийняте
з формулюванням «автономний AI-пошук по імені людини — інструмент стеження за конкретною
приватною особою незалежно від упаковки».

**Пункт [media-review]** (окремий ТЗ, режим тестування системи на YouTube-контенті) додав
`checkAgainstFactCheckAPI()` — **на той самий сервіс `DiscrepancyAnalysisService`**, не в
окремий модуль. Перевірено прямо в коді перед написанням цього документа: метод не має
жодної прив'язки до media-review контексту — приймає `conversationId` будь-якої розмови,
що належить користувачу, той самий guard (`TelegramAuthGuard`), той самий шлях авторизації
власності через `findOwnedConversationWithTranscript()`, що й усі інші методи цього сервісу.

**Висновок, який формалізує цей документ:** `checkAgainstFactCheckAPI()` **вже зараз** закриває
частину четвертого джерела §3.16 для ВСЬОГО продукту (переговори, важливі розмови — не тільки
YouTube-аналіз) — просто це ніколи не було явно визнано й задокументовано як таке, коментар у
коді Пункту 37 досі каже «(4) НЕ реалізовано», хоча це вже неправда для вузького класу
тверджень, які покриває Fact Check Tools API.

## 2. Що саме закривається, а що — ні (та сама межа, що вже встановлена в media-review §5.3a)

**Закривається:** широкі фактичні твердження співрозмовника в БУДЬ-ЯКІЙ розмові продукту —
не тільки в контексті оглядин нерухомості/авто чи аналізу YouTube-контенту. Приклад із
переговорного контексту: співрозмовник каже "усі наші конкуренти вже підняли ціни на 20%" —
це твердження того самого типу, яке фактчекери реально перевіряють (економічна/галузева
статистика), не унікальне для media-review чи major-purchase доменів.

**НЕ закривається (та сама межа, що вже зафіксована раніше, підтверджена тут повторно, не
випадково пропущена):**
- Твердження про КОНКРЕТНУ ЛЮДИНУ як об'єкт пошуку — Fact Check Tools API фізично не має
  параметра "знайди все про Івана Петренка", тільки `query` тексту твердження (та сама
  структурна гарантія, що вже описана в `devils-advocate-media-review-tz.md` §3, п.1).
- Ціни/вартісні оцінки (той самий висновок, що вже зафіксований у
  `devils-advocate-major-purchase-tz.md` §5.3a) — фактчекери не публікують `ClaimReview` на
  теми "чи справедлива ця ціна".
- Автоматичне масове сканування ВСІХ реплік розмови — і далі тільки вручну, по одному
  твердженню, обраному аналітиком (той самий принцип, що вже реалізований).

## 3. Що реально потрібно зробити — три пункти, не переписування backend

### 3.1 Виправити застарілий коментар у коді Пункту 37

`discrepancy-analysis.service.ts`, рядки над класом — досі стверджує «(4) НЕ реалізовано,
вимагає зовнішнього пошуку, якого немає». Оновити на: «(4) частково реалізовано —
`checkAgainstFactCheckAPI()` (Пункт [media-review]) закриває вузький клас тверджень через
Google Fact Check Tools API; повний автономний веб-пошук і далі відсутній і не планується
(розділ 2 цього документа)». Дрібна правка, але важлива — коментар, що бреше про стан
реалізації, гірший за відсутність коментаря взагалі.

### 3.2 Включення в `exportFactsToVerify()` (Пункт 41) — ПЕРЕВІРЕНО, знайдено й виправлено реальний баг

**Перша версія цього розділу стверджувала "вже працює правильно без змін" — це виявилось
НЕПРАВДОЮ при детальнішій перевірці, не просто обережним припущенням.** `exportFactsToVerify()`
дійсно вибирає всі `ConversationSignal` типу `FACTUAL_DISCREPANCY` без фільтра по джерелу — це
частина правди. Але `resolveSignalDetails()` (внутрішній метод, що формує `sourceDescription`
для кожного сигналу) ітерував `evidence[]` і **пропускав** будь-який запис без `aiInference` —
а `checkAgainstFactCheckAPI()` ніколи не викликає AI. Наслідок: сигнали з Fact Check API
отримували `sourceDescription: null` і **хибно потрапляли в категорію "ще вимагає перевірки"**,
хоча щойно були перевірені.

**Виправлено:** нове поле `ConversationSignalEvidence.factCheckSourceDescription`,
записується одразу при створенні evidence в `checkAgainstFactCheckAPI()`; `resolveSignalDetails()`
перевіряє його першим; `exportFactsToVerify()` розпізнає обидва детектовані маркери джерела.
Два нових регресійних тести в `discrepancy-fact-check-api.spec.ts` (13 разом з уже наявними 11).

**Урок, вартий фіксації окремо, не тільки факту фіксу:** твердження "це вже працює правильно"
на основі читання сигнатури методу й where-клаузи — недостатня перевірка для acceptance-тесту.
Реальна перевірка вимагала прослідкувати весь ланцюжок аж до форматування вихідного тексту.

### 3.3 TMA UI — чесно визнана прогалина, СПІЛЬНА для всього `DiscrepancyAnalysisService`, не унікальна для цього ТЗ

Перевірено: жоден метод `DiscrepancyAnalysisService` (включно з уже давнім
`checkAgainstUserSource()`, Пункт 40) не має TMA-інтерфейсу — весь сервіс наразі backend-only.
Це НЕ прогалина, унікальна для Fact Check API — той самий стан, що вже був до цього ТЗ. Кнопка
"перевірити через Fact Check API" на конкретному сегменті розмови — природне продовження вже
запланованого (але не реалізованого) UI для `checkAgainstUserSource()`, не окрема робота.
**Свідомо поза обсягом цього документа** (розділ 5) — фіксується тут як прозорий, явний борг,
не замовчується.

## 4. Юридичні межі — ідентичні вже встановленим, не нові

Розділ 3 `devils-advocate-media-review-tz.md` (одиниця пошуку — твердження, не людина;
ініціація — вручну аналітиком; прозорість запиту й відповіді; жодного накопичення в профіль
`Person` між сесіями) застосовується тут **без жодної зміни** — це той самий метод того самого
сервісу, ті самі гарантії вже діють на рівні коду (не потребують повторної реалізації), просто
тепер явно визнано, що вони застосовні до всього продукту, не тільки media-review контексту.

## 5. Acceptance-тести

```
Given будь-яка Conversation основного продукту (переговори, не media-review/major-purchase)
When аналітик формулює claimText із репліки й викликає check-against-fact-check-api
Then запит обробляється успішно — той самий шлях, що для media-review, жодної додаткової
     перевірки контексту "чи це media-review розмова" немає й не повинно з'явитись

Given сигнал FACTUAL_DISCREPANCY, створений через checkAgainstFactCheckAPI (не через detect()
      чи checkAgainstUserSource())
When викликається exportFactsToVerify() для тієї ж розмови
Then сигнал присутній у пронумерованому списку на експорт нарівні з сигналами інших джерел
     ТА класифікований як "Уже проверено вручную", не "ТРЕБУЕТ ПРОВЕРКИ" — перше твердження
     виявилось правдою одразу, друге вимагало реального фіксу (factCheckSourceDescription),
     підтверджено регресійним тестом (discrepancy-fact-check-api.spec.ts), не припущенням з коду

Given коментар у discrepancy-analysis.service.ts над визначенням класу сервісу
Then текст явно визнає, що (4) публічно доступні факти ЧАСТКОВО реалізовано через
     checkAgainstFactCheckAPI — не стверджує "НЕ реалізовано" як і раніше

Given спроба сформулювати claimText, що фактично є іменем людини без конкретного твердження
      ("Іван Петренко")
When викликається check-against-fact-check-api
Then Fact Check Tools API поверне порожній/нерелевантний результат за своєю природою (query по
     тексту твердження, не по імені) — структурна, не договірна гарантія від профілювання
```

## 6. Що свідомо виключено з цього проходу

- **TMA UI для цього чи будь-якого іншого методу `DiscrepancyAnalysisService`** (розділ 3.3) —
  давній, спільний борг, не розширюється й не звужується цим документом.
- **Повний автономний веб-пошук** — і далі відсутній, той самий принцип, що вже зафіксований
  у трьох попередніх документах (Пункт 40, media-review §2.4/§3, major-purchase §2.3).
- **Автоматичне позначення "цей факт варто перевірити через Fact Check API"** на основі AI-
  детекції потенційно перевірних тверджень у транскрипті — це вже було б кроком до автоматизації
  вибору "що перевіряти", який свідомо залишається за аналітиком (та сама межа, що вже
  зафіксована в media-review §3, п.2).
