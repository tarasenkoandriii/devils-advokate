# ESLint + CI + strict — 2026-09-01

Последний открытый пункт бэклога аудитов («ESLint + CI отсутствуют;
strict:false; спеки вне тайпчека», п.4 раздела «Требует решения
владельца»). Инфраструктурный проход: сначала измерение, потом
включение, потом разбор всего, что включение показало.

Решения владельца по объёму: полный `strict` сразу (не поэтапно), CI —
GitHub Actions, все существующие `eslint-disable` разобрать поимённо.

## Что теперь есть

| Команда | Что делает |
| --- | --- |
| `npm run lint` | ESLint 9 (flat config) по всему монорепозиторию |
| `npm run lint:fix` | то же с `--fix` |
| `npm run typecheck` | tsc по api/tma/admin/landing, **спеки внутри** |
| `npm test` | jest + standalone-раннер (как раньше) |
| `npm run ci` | lint + typecheck + тесты одной командой (сборки — отдельно, `npm run build`) |
| `make lint`, `make ci` | то же с хоста, рядом с докерными целями |

CI: `.github/workflows/ci.yml`, пять независимых джоб — **lint**,
**typecheck**, **test**, **build** (nest build + три next build),
**prisma** (validate). Джобы раздельные намеренно: красный CI должен
называть сломанное, а не «пайплайн». Общий шаг установки (Node 20,
`npm ci`, `prisma generate`) вынесен в composite-действие
`.github/actions/setup`. `prisma generate` обязателен до всего
остального: без сгенерированного клиента `tsc` в apps/api сыплет
сотнями «Property … does not exist on type PrismaClient», и поломка
выглядит как ошибка кода, а не как пропущенный шаг сборки.

## strict: измерение и результат

Под полным `strict` + спеки в тайпчеке первый прогон дал 2811 ошибок —
из них **2793** были одной конфигурационной: у спек не было `types:
["node","jest"]`, то есть `describe`/`it`/`process` не резолвились.
После починки конфига осталось **18 реальных ошибок**, все исправлены:

- **11 × «Expected 6 arguments, but got 5»** в `sparring.service.spec.ts`
  (7) и `material-chat.service.spec.ts` (4). Это главная находка
  прохода: обоим сервисам шестым аргументом добавили `ConsentService`
  (голос уходит внешнему провайдеру), а спеки продолжали
  конструировать их пятью — и «зеленели», потому что покрытые
  сценарии до `this.consent` просто не доходили. Тайпчек этого не
  видел: спеки были исключены из него строкой `"**/*spec.ts"`.
  Исправлено: во все конструкторы передан фейк согласия. Отдельно
  выяснилось, что у MaterialChat, в отличие от Sparring, **вообще не
  было теста на проверку согласия** перед выгрузкой голоса — он
  добавлен (`streamUploadVoiceReply` без согласия: `ForbiddenException`,
  и ни одного байта провайдеру).
- **1 × перегрузка `$transaction`** в `chat-import.service.ts`: явная
  аннотация `(tx: typeof this.prisma)` шире клиента транзакции, из-за
  чего TS выбирал перегрузку «массив промисов», и возвращаемый тип
  `importChat` вырождался в `any[]`. Спека это молча проглатывала
  (`result.sourceType` на `any[]`). Аннотация убрана — тип выводится
  контекстно, как в остальных 13 транзакциях колбэк-формы (всего
  `$transaction` в проекте 25: 14 колбэком, 11 массивом промисов).
- **3 × `strictPropertyInitialization`** в DTO `arguments.controller.ts`
  и `prediction.controller.ts`: `!` по конвенции, уже принятой в
  проекте — из 168 DTO-классов `!`-поля есть у 137 (остальные состоят
  из опциональных полей); эти два просто выпали из конвенции.
- **3 × следствия** предыдущих (свойства на `any[]`).

Дополнительно в тайпчек включены `prisma/**` и `scripts/**`: сиды и
диагностический скрипт не входили ни в один tsconfig — ни тайпчека, ни
линта у них не было вообще, хотя `seed.ts` исполняется на каждом
деплое. Сборка не задета: `nest build` переведён на
`tsconfig.build.json`, спеки и скрипты в `dist` не попадают.

## ESLint: что нашёл первый честный прогон

**183 срабатывания** на исходном коде (163 ошибки + 20 предупреждений о
лишних директивах); если снять и все 45 подавлений — 188 ошибок.
Цифра перемерена повторным аудитом: в первой редакции этого отчёта
стояло 208 — сумма, в которой 20 лишних директив были посчитаны дважды.
Ядро правил — type-aware: `no-floating-promises`, `no-misused-promises`,
`await-thenable`; `react-hooks/exhaustive-deps` поднят до **error**
(см. ниже, почему).

**113 × no-floating-promises.** Разбор по природе:

- 67 — `run();` в конце standalone-спек. Заменено на
  `run().catch(err => { console.error(err); process.exit(1); })`:
  падение вне тела теста (в фейке, в модульном коде) теперь провал
  файла с внятным текстом, а не unhandled rejection.
- 41 — вызовы самообрабатывающихся функций из `useEffect` и
  обработчиков (`reload()`, `load()`, `Promise.all([...]).finally(...)`).
  Помечены `void`: ошибки обрабатываются внутри, маркер делает это
  видимым.
- 4 — **реальные потери ошибок**: `new Audio(...).play()` в
  `SpeakButton`, `CompromiseSheetSection`, `UserVoiceRecordingSection`.
  `play()` отклоняется, когда браузер блокирует автовоспроизведение;
  отказ уходил в никуда. В SpeakButton кнопка показывала «озвучено»
  без звука; в UserVoiceRecordingSection молчание выглядело как баг
  сохранения (прослушивание — обязательное условие кнопки
  «Сохранить»). Везде добавлен `await` с честной обработкой отказа.
- 1 — **`bootstrap()` в `main.ts`**: падение старта (занятый порт,
  недоступная БД, кривой env) было unhandled rejection. Теперь
  `.catch` с сообщением и `process.exit(1)`.

**1 × react-hooks/rules-of-hooks** — `DomainExtrasManual.tsx`: функция
`useDevice()` не хук, но `use*`-имя нарушало соглашение React и
правило справедливо ругалось на вызов из `onClick`. Переименована в
`takeDeviceLocation`.

**30 × no-unused-vars.** Существенная часть — привязки у проверок
владения: `const project = await assertProjectOwnership(...)`, где
результат не используется, а сам вызов обязателен (бросает при чужом
объекте). Привязки убраны, вызовы на месте — 8 сервисов. Остальное:
неиспользуемые импорты (12), девять срабатываний в самих спеках
(мёртвые фикстуры, захваченные и не проверенные значения), мёртвое
состояние `scrollIndex` в
`UserVoiceRecordingSection` (телесуфлёр так и не прокручивался),
`projectId` в `assertUnderOcrRateLimit` — лимит на пользователя, не на
проект (SANDBOX-COVERAGE.md), параметр убран из сигнатуры, чтобы не
выглядело потолком «10 в сутки на каждый проект».

Мелочь: 11 × `prefer-const`, 2 × лишний escape в regex, 1 тернарник
вместо `if` в `admin-sandbox.service.ts`.

## Разбор всех 45 eslint-disable

До этого прохода они не подавляли ничего — линтера не существовало.
После включения:

- **20 оказались лишними** (правило не срабатывает) — удалены `--fix`.
- **22 × exhaustive-deps исправлены по существу.** Типовой случай:
  `function reload() {…}` + `useEffect(() => void reload(), [projectId])`.
  Переведено на `useCallback(…, [projectId])` с честными
  зависимостями эффекта — поведение то же (идентичность `reload`
  меняется ровно при смене projectId), подавление не нужно. Отдельно:
  - `ConversationsSection` — поллинг с проп-функцией `onChanged` в
    зависимостях пересоздавал бы интервал на каждый рендер родителя;
    функция вынесена в ref, интервал живёт по статусу.
  - `admin/sandbox/page.tsx` — `loadQueue` объявлялась ПОСЛЕ эффекта,
    который её зовёт; объявление поднято (иначе ссылка в dep-массиве
    — ReferenceError на рендере).
  - **Два бага, которые подавление прятало:**
    `admin/moderation/users` — чекбоксы «только ограниченные/
    заблокированные» меняли состояние, но список не перезагружали:
    фильтр выглядел нерабочим, пока не нажмёшь Enter в поиске.
    Разделены строка поиска и применённый запрос: фильтры
    перезагружают сразу, поиск — по Enter/«Обновить».
    `admin/telemetry` — то же разделение для диапазона дат: иначе
    кнопка «Обновить» тянула бы стартовый диапазон (замыкание) либо
    каждое движение в поле даты било бы в API двумя запросами.
- **3 оставлены осознанно, каждая с обоснованием в коде:**
  - `useJson` в `InterviewPoolWorkspace` — dep-массив со spread,
    статически неразрешим для правила в принципе.
  - `DomainOnboarding` — ДВЕ директивы на ДВУХ разных эффектах:
    открытие онбординга (deps `[projectId]`: conversationId он
    выставляет сам, повтор был бы вторым проходом создания) и
    подгрузка чек-листа (deps `[category]`: conversationId и manifest
    здесь условие применимости, а не триггер).

  20 + 22 + 3 = 45, сходится.

- **Отдельно: 2 директивы завёл сам этот проход** —
  `@typescript-eslint/no-this-alias` в `live-transcription.spec.ts`
  (тестовый дубль WebSocket: экземпляр создаёт тестируемый код,
  добраться до него можно только через `lastInstance = this`). Они не
  входят в разбор 45 старых и названы здесь отдельно, чтобы счёт
  «разобрано» не прикрывал собственные новые подавления.

## Что осталось за рамками

- `landing` собирается в песочнице с ошибкой Google Fonts (сеть) —
  свойство окружения, не кода: `tsc` чист, падение только на
  `Failed to fetch 'Inter'/'Unbounded'`. Что сборка пройдёт на Vercel и
  в Actions — ожидание, а не наблюдение: workflow до сих пор ни разу не
  запускался, это первое, что стоит проверить после пуша.
- Правило `no-console` оставлено предупреждением (не ошибкой) —
  массовой чистки логов этот проход не делал.
- `@typescript-eslint/no-explicit-any` выключен: фейки в спеках и
  Prisma-JSON — осознанный `any`, включение потребовало бы отдельного
  прохода с реальными типами.

## Самопроверка прохода

Диф отревьюен отдельным проходом против исходного архива. Найдено и
исправлено уже в этом же проходе:

- `admin/moderation/users` — кнопка «Обновить» в первой редакции звала
  `load()` напрямую и параллельно меняла применённый запрос: два
  запроса на клик и гонка, в которой старый ответ мог затереть новый.
  Применённый запрос сделан объектом (как в телеметрии): клик всегда
  даёт ровно один запрос через эффект.
- `CompromiseSheetSection` — отказ автовоспроизведения попал в общий
  `try` с генерацией озвучки и выглядел бы как её провал, хотя озвучка
  уже сгенерирована; отказ `play()` обрабатывается отдельно.
- строки из одних пробелов, оставшиеся на месте удалённых директив
  (промежуточное состояние после `--fix`, в дифе его не видно);
  формулировки двух комментариев про `!activeSession` (объясняли
  правку неверно) — переписаны.
- `npm run ci` честно назван тремя джобами из пяти: сборки в него не
  входят (минуты), про `npm run build` сказано прямо в README и
  Makefile.
- CI переведён на `push: [main, master]` + `pull_request`: с
  `branches: ['**']` каждый внутренний PR гонял бы все пять джоб
  дважды (concurrency их не схлопывает — это разные ref'ы).
