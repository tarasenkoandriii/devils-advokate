# Devil's Advocate — ТЗ: Unified Admin Panel (`apps/admin`)

> ⚠️ **Конфиденциально.** Технический компаньон-документ к `devils-advocate-prompt-framework-tz.md`,
> `devils-advocate-telemetry-tz.md` и основному ТЗ (`devils-advocate-tz.md`, §3.23, §4.5, §8).
> Коммерческая ценность та же — не подлежит разглашению третьим лицам без согласия автора.

**Статус:** первая ревизия. `apps/admin` в монорепо существует как пустой каталог с README
(«запланировано, не начато») — эта ревизия превращает намерение в конкретный, реализуемый план.
По прямому решению — **один унифицированный** Next.js-админ-app с вкладками, не несколько
раздельных приложений.

**Как читать:** раздел 1 — что уже готово на backend и что нужно достроить (аудит кода, не
предположение); раздел 2 — ключевое архитектурное решение по аутентификации и почему
существующий `TelegramAuthGuard` не переиспользуется напрямую; раздел 3 — структура приложения
и вкладки; раздел 4 — API-контракты новых частей; раздел 5 — acceptance-тесты; раздел 6 — что
сознательно не входит.

## 1. Аудит: что уже есть, что действительно нужно построить

Проверено в коде перед проектированием, не предположение.

### 1.1 Полностью готово на backend, нужен только UI

**Модерация библиотеки аргументов** (`isLibraryModerator`, Пункт 57, §3.5) —
`GET /library/moderation-queue`, `PATCH /library/:entryId/moderate` уже существуют и работают.

**Модерация заявок заведений + монетизация** (`isVenueModerator`, Пункт 66, §3.23) —
`GET /venue-applications/moderation-queue`, `PATCH /venue-applications/:id/moderate`,
`PATCH /approved-venues/:id/referral-fee`, `PATCH /approved-venues/:id/priority-partner`,
`GET /approved-venues/:id/commission-summary` — всё уже реализовано. При аудите TMA
(`apps/tma/src/lib/features.ts`) эти функции ранее были найдены «осиротевшими» — не забытая
недоделка, а функции, ожидавшие именно этот интерфейс, не обычного пользователя TMA.

### 1.2 Спроектировано отдельными ТЗ, backend ещё не реализован

**Prompt Registry + Evaluation Gates** — полный API-контракт в
`devils-advocate-prompt-framework-tz.md` (`/admin/prompts/*`, `/admin/evaluation-*`). Backend
для этой ревизии ещё предстоит построить — эта ревизия описывает вкладку админки, которая
станет UI-слоем поверх него.

**Telemetry** — полный API-контракт в `devils-advocate-telemetry-tz.md`
(`/admin/telemetry/*`). Backend аналогично не реализован, эта ревизия добавляет вкладку.

### 1.3 Честно не найдено вообще, требует новой работы в этой ревизии

**§4.5 «модерация публичных обсуждений» — переосмыслено, не то, чем казалось.** Проверено
напрямую: `PublicArgumentSubmission.moderate()` использует `assertProjectOwnership`, не
`isLibraryModerator`/`isVenueModerator` — модерирует **владелец конкретного проекта** через
собственную TMA-сессию, не сайтовый администратор. Это уже полностью реализовано, работает
и **не относится к админ-панели вообще** — упоминание в исходном README `apps/admin` было
неточным, эта ревизия его не включает.

**§8 «ручные approve-флоу из юридического чек-листа» — сведено к одному конкретному пункту.**
Проверены все 15 пунктов чек-листа (раздел 8 `devils-advocate-tz.md») — только пункт 11 описывает
что-то, требующее ручного административного действия: «модерация вправе ограничить аккаунт при
аномальном паттерне». Остальные 14 пунктов — архитектурные принципы и продуктовые решения, не
операционные флоу. При этом **в схеме нет ни единого поля** для ограничения аккаунта
(`grep suspended|restricted|isBanned` → пусто) — это не недоделанный UI поверх существующего
backend, это полностью новая, маленькая функциональность (см. §4.3).

## 2. Ключевое архитектурное решение: аутентификация

**Существующий `TelegramAuthGuard` не переиспользуется напрямую.** Он проверяет заголовок
`X-Telegram-Init-Data` — подписанную строку, которую генерирует **клиент Telegram при запуске
Mini App внутри самого Telegram**. У обычного браузера, открывшего URL админки напрямую (не как
Mini App), такого заголовка физически нет и быть не может — это не настройка, а фундаментальное
свойство того, как Telegram Mini Apps работают.

**Рассмотрены три варианта:**

1. **Сделать саму админку тоже Telegram Mini App** — переиспользует `TelegramAuthGuard`
   без единой строки нового backend-кода. Минус: доступ только через сам Telegram
   (бот-команда/меню), неудобно для спокойного просмотра телеметрии с ноутбука в обычном
   браузере.
2. **Telegram Login Widget** — отдельный, официальный механизм Telegram именно для обычных
   веб-сайтов (не Mini Apps): кнопка «Войти через Telegram» на обычной странице, redirect-флоу,
   backend получает подписанный payload (другой формат подписи, чем initData, но та же идея —
   HMAC тем же bot token). Работает в обычном браузере, использует уже настроенный
   `TELEGRAM_BOT_TOKEN`.
3. **Отдельный shared-пароль** (Basic Auth/переменная окружения) — проще всего технически, но
   теряет привязку к конкретному `User.id` и его флагам `isLibraryModerator`/`isVenueModerator`
   — все, кто знает пароль, получили бы одинаковый полный доступ, что противоречит уже
   заложенному в схему принципу «разные домены ответственности» (см. обоснование над
   `isVenueModerator` в schema.prisma).

**Решение: вариант 2 (Telegram Login Widget).** Сохраняет привязку к существующим per-user
флагам, работает в обычном браузере, не требует нового секрета — тот же bot token. Требует
новой (небольшой) серверной валидации — см. §4.1.

## 3. Структура приложения

`apps/admin` — Next.js App Router, тот же стек, что `apps/landing`/`apps/tma` (единообразие
монорепо, не новая технология ради одного приложения).

```
apps/admin/
  src/
    app/
      login/page.tsx              — Telegram Login Widget
      moderation/
        library/page.tsx          — вкладка «Библиотека»
        venues/page.tsx           — вкладка «Заведения»
        users/page.tsx            — вкладка «Пользователи» (§4.3, новое)
      prompts/
        page.tsx                  — список PromptVersion по promptId
        [id]/page.tsx             — детали версии + запуск evaluation + промоушен
      telemetry/
        page.tsx                  — сводка (devils-advocate-telemetry-tz.md §4.1)
        [taskType]/page.tsx       — детализация (§4.2)
    components/
      AdminNav.tsx                 — навигация по вкладкам, одна на всё приложение
      ModerationQueueTable.tsx     — переиспользуется для Library И Venues (одинаковая форма:
                                      список PENDING-записей + Accept/Reject) — не дублируется
      TelemetryChart.tsx
    lib/
      admin-auth.ts                 — клиентская сессия (см. §4.1)
```

**Одна навигация, три раздела** (Модерация → 3 подвкладки, Промпты, Телеметрия) — по прямому
решению объединить в одном приложении, не создавать отдельные `apps/admin-moderation`,
`apps/admin-telemetry`.

## 4. API-контракты (новые части)

### 4.1 Admin-аутентификация

```prisma
// Новая модель — сессия админки, ОТДЕЛЬНАЯ от TMA-сессий (те не имеют
// состояния на сервере вообще, initData проверяется на каждый запрос
// заново). Админ-панели удобнее held session (не показывать Telegram
// Login Widget на каждый клик) — компромисс в другую сторону, чем TMA,
// осознанно, не по инерции.
model AdminSession {
  id     String @id @default(cuid())
  userId String
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)

  token     String   @unique // случайная строка, отдаётся клиенту как httpOnly cookie
  expiresAt DateTime // 7 дней от создания — компромисс между удобством и риском кражи cookie

  createdAt DateTime @default(now())

  @@index([token])
  @@index([userId])
  @@map("admin_sessions")
}
```

| Метод | Путь | Описание | Тело | Ответ |
|---|---|---|---|---|
| `POST` | `/admin/auth/telegram-callback` | Принимает payload от Telegram Login Widget, валидирует подпись (HMAC тем же `TELEGRAM_BOT_TOKEN`, отдельная функция от `validateTelegramInitData` — формат payload другой), создаёт `AdminSession` | `{ id, first_name, username?, photo_url?, auth_date, hash }` (стандартный shape от Telegram Login Widget) | `{ token, expiresAt }`, ставится как httpOnly cookie |
| `POST` | `/admin/auth/logout` | Удаляет `AdminSession` | — | `{ ok: true }` |
| `GET` | `/admin/auth/me` | Текущий пользователь + его флаги доступа | — | `{ userId, isLibraryModerator, isVenueModerator }` |

**Guard `AdminSessionGuard`** — новый, параллельный `TelegramAuthGuard`, не расширяет его
(разный источник токена: cookie vs заголовок initData). Проверяет `AdminSession.token` из
cookie, `expiresAt > now()`, кладёт `request.userId`.

**РЕАЛИЗОВАНО (аудит кода после реализации, не первоначальный план):** первоначальная
формулировка этого раздела предполагала «переключить `library`/`venue-application` контроллеры
с `TelegramAuthGuard` на `AdminSessionGuard` — единственная правка, замена guard'а в двух
контроллерах». При реализации эта формулировка оказалась неточной и была явно исправлена
(комментарий в самом коде, не молчаливое расхождение) — оба контроллера содержат **смесь**
обычных пользовательских действий TMA (например `LibraryController.submit()` — любой
пользователь публикует проект в библиотеку; `VenueApplicationController.confirmBooking()` —
самоотчёт о брони) и модераторских действий, защищённых `assertModerator()`. Слепая замена
guard'а на уровне всего контроллера сломала бы первые для всех обычных пользователей.

**Что сделано вместо буквального плана:** каждый исходный контроллер расщеплён на два
отдельных класса — оригинальный остаётся на `TelegramAuthGuard` и сохраняет только
пользовательские эндпоинты; новый (`LibraryModerationController`/
`VenueApplicationModerationController`) объявлен с `@UseGuards(AdminSessionGuard)` и содержит
ровно те методы, которые `LibraryService`/`VenueApplicationService` реально защищают через
`assertModerator()` внутри (проверено в коде, не предположение — это тот же метод проверки,
что применяется к каждому ТЗ в этом проекте). Сами сервисы (`LibraryService`/
`VenueApplicationService`) не изменились вообще — `assertModerator(userId)` продолжает
работать как прежде, потому что оба guard'а кладут `userId` в `request` одним и тем же именем
(acceptance-тест §5.4 остаётся верным буквально, только описание пути к нему изменилось).

**Доступ по вкладкам** — не все админ-пользователи равны:
- Вкладка «Библиотека» — требует `isLibraryModerator = true`
- Вкладка «Заведения» — требует `isVenueModerator = true`
- Вкладки «Промпты», «Телеметрия», «Пользователи» — новый третий флаг (см. ниже), т.к. это не
  модерация контента, а операционное управление проектом; смешивать с `isLibraryModerator`/
  `isVenueModerator` (домены модерации контента) было бы нечестным переиспользованием флага не
  по смыслу.

```prisma
model User {
  // ...существующие поля...

  // Пункт [N]: доступ к операционным вкладкам админки (промпты,
  // телеметрия, управление пользователями) — ОТДЕЛЬНЫЙ флаг от
  // isLibraryModerator/isVenueModerator, тот же принцип "разные
  // домены ответственности, разное суждение", что уже применялся к
  // разделению двух других флагов. Пока единственный практический
  // сценарий — сам разработчик (соло-проект), поэтому не заводится
  // отдельная RBAC-система ради одной операционной роли.
  isOperator Boolean @default(false)
}
```

### 4.2 Prompt Registry / Evaluation / Telemetry — backend

Полностью описаны в `devils-advocate-prompt-framework-tz.md` (раздел 5) и
`devils-advocate-telemetry-tz.md` (раздел 4). Эта ревизия не переопределяет их контракты —

### 4.3 Управление пользователями (новое, §8 п.11)

```prisma
model User {
  // ...существующие поля...

  // §8 юридического чек-листа, п.11: "модерация вправе ограничить
  // аккаунт при аномальном паттерне". Намеренно простое bool-поле, не
  // градация степеней ограничения — при реальной необходимости более
  // тонкой модели (временная блокировка, частичное ограничение
  // конкретных фич) это отдельная, более поздняя ревизия поверх этого
  // минимального фундамента, не проектируется заранее вслепую.
  isRestricted   Boolean   @default(false)
  restrictedAt   DateTime?
  restrictedNote String?   // причина, видна только операторам, не самому пользователю
}
```

| Метод | Путь | Описание | Параметры | Ответ |
|---|---|---|---|---|
| `GET` | `/admin/users` | Список пользователей с базовой активностью | `?search=&restricted=true` | `AdminUserRow[]` |
| `GET` | `/admin/users/:id` | Детали + счётчики (проекты, разговоры, последняя активность) | — | `AdminUserDetail` |
| `PATCH` | `/admin/users/:id/restrict` | Ограничить/снять ограничение | `{ restricted: boolean, note?: string }` | `User` |

**Что именно значит `isRestricted = true` на практике** — намеренно определяется минимально в
этой ревизии: `TelegramAuthGuard` при `user.isRestricted = true` продолжает пропускать запрос
(не блокирует полностью — это решение о степени жёсткости оставлено явно открытым, не
реализуется втихую как полная блокировка), но добавляет `request.userRestricted = true`,
которое достаточно чувствительные write-эндпоинты обязаны проверять и отклонять с понятным
сообщением.

**РЕАЛИЗОВАНО (по прямому запросу, после аудита кода):** `NotRestrictedGuard`
(`src/telegram-auth/not-restricted.guard.ts`) — новый, второй слой guard'ов (тот же принцип,
что `AdminSessionGuard` выше), проверяет `request.userRestricted`, кидает
`ForbiddenException` с понятным сообщением. Применён на уровне МЕТОДА (не класса контроллера
целиком — блокировать весь контроллер сломало бы обычные read-действия ограниченного
пользователя, что прямо противоречило бы "не блокирует полностью" выше). Список конкретных
эндпоинтов оказался шире исходных трёх примеров при реальной инвентаризации кода — девять
точек: семь отдельных `createProject` (по одному на каждый режим проекта —
`STANDARD`/major-purchase/interview-pool/investment/health/family-law/dtp), `LibraryController
.submit()`, `VenueApplicationController.submit()`. → `apps/api/prisma/README.md`, «Пункт
[not-restricted-guard]».

**Вторая степень (РЕАЛИЗОВАНО, см. §6):** `User.isBlocked` — независимое от `isRestricted`
поле, полная блокировка аккаунта. Проверяется в `TelegramAuthGuard` ДО выдачи
`request.userId` (не только сигнализирует, как `isRestricted` — отклоняет запрос целиком) и в
`AdminAuthService.loginWithTelegram()`, чтобы отдельный вход админки не стал обходным путём.

## 5. Acceptance-тесты (Given/When/Then)

### 5.1 Аутентификация

```
Given обычный пользователь TMA без isLibraryModerator/isVenueModerator/isOperator
When он проходит Telegram Login Widget на /admin/login
Then AdminSession создаётся успешно (сама аутентификация не требует прав),
     но GET /admin/auth/me возвращает все три флага = false —
     UI не показывает ни одной вкладки, честное «нет доступа», не ошибка входа
```

```
Given AdminSession с token существует, но expiresAt уже в прошлом
When любой /admin/* запрос выполняется с этим cookie
Then AdminSessionGuard отклоняет (401), UI перенаправляет на /admin/login —
     не молчаливый показ пустых данных
```

### 5.2 Разделение доступа по вкладкам

```
Given User.isLibraryModerator = true, isVenueModerator = false
When он открывает вкладку «Заведения»
Then GET /venue-applications/moderation-queue возвращает 403 —
     тот же принцип, что уже задокументирован в venue-application.service.ts:
     "разные домены ответственности требуют разного суждения", не общий доступ
     по факту наличия ЛЮБОГО админ-флага
```

### 5.3 Ограничение пользователя

```
Given User.isRestricted = false
When оператор вызывает PATCH /admin/users/:id/restrict {restricted: true, note: "..."}
Then isRestricted = true, restrictedAt проставлен, restrictedNote сохранён;
     сам пользователь при следующем TMA-запросе не получает 401
     (сессия TMA не обрывается автоматически — решение п.11 оставлено явно открытым, §4.3)
```

### 5.4 Переиспользование существующих эндпоинтов

```
Given library.controller.ts расщеплён на LibraryController (обычные пользовательские
      эндпоинты, TelegramAuthGuard) и LibraryModerationController (модераторские
      эндпоинты, AdminSessionGuard) — см. §4.1
When AdminSessionGuard кладёт request.userId для модераторских эндпоинтов
Then listPendingForModeration()/moderate() внутри LibraryService не меняются —
     assertModerator(userId) продолжает работать как прежде, т.к. userId
     кладётся в request.userId тем же способом, только другим guard'ом на другом
     классе контроллера, не на том же самом
```

## 6. Что сознательно не входит

- ~~**Степень жёсткости `isRestricted`**~~ **РЕАЛИЗОВАНО (по прямому запросу).** Обе части
  этого пункта закрыты: (а) список конкретных эндпоинтов, обязанных проверять
  `request.userRestricted` — `NotRestrictedGuard` применён на девяти реально найденных
  write-точках (см. §4.3); (б) полная блокировка аккаунта целиком — новое, НЕЗАВИСИМОЕ поле
  `User.isBlocked`/`blockedAt`/`blockedNote`, проверяется в `TelegramAuthGuard` ДО выдачи
  `request.userId` (отклоняет запрос целиком, не только девять write-точек) и в
  `AdminAuthService.loginWithTelegram()` (тот же принцип для отдельного входа админки — не
  становится обходным путём мимо основного ограничения). `PATCH /admin/users/:id/block
  { blocked, note? }` — новый эндпоинт рядом с `.../restrict`, тот же паттерн
  `AuditLogService.record()`. → `apps/api/prisma/README.md`, «Пункт [full-block]».
- **Регистрационная форма «стать модератором/оператором»** — как и `isLibraryModerator`/
  `isVenueModerator` до этого, `isOperator` включается вручную в БД тем, кто управляет
  деплойментом, не self-service — тот же, уже принятый в проекте принцип.
- **Backend для Prompt Registry и Telemetry** — описан в двух предыдущих ТЗ, не переописывается
  здесь; эта ревизия — про UI-слой и то, что не было покрыто ими (аутентификация, модерация,
  пользователи).
- **Мобильная версия админки** — Telegram Login Widget и сами операционные задачи
  (просмотр телеметрии, оценка промптов) ориентированы на десктоп-браузер по своей природе,
  адаптив под телефон не проектируется в этой ревизии.
- **Многоуровневая RBAC-система с ролями/правами** — сознательно НЕ вводится и в этой ревизии
  (третий bool-флаг `isOperator`, не таблица ролей) — тот же принцип, что уже применён к первым
  двум флагам: в проекте нет концепции ролей вообще, вводить её целиком ради текущего
  соло-масштаба использования было бы избыточной инфраструктурой.

## 7. Аддендум: isBlocked в UI (§6 «Пункт [full-block]») — реальный, узкий пробел

**Перевірено перед написанням, не за припущенням.** Пряме твердження "UI-шар апп/admin ще не
написаний" виявилось неточним при перевірці реального коду — `apps/admin` уже реалізований
майже повністю за цим ТЗ (аутентифікація, чотири вкладки модерації, Prompt Registry,
телеметрія — підтверджено прямим читанням файлів). **Реальний, вузький пробіл:** `isBlocked`
(Пункт `[full-block]`, `apps/api/prisma/README.md`) реалізований у backend вже ПІСЛЯ того, як
цей фронтенд був написаний — UI про нього нічого не знає.

**Три конкретні файли, що відстали від backend:**
1. `src/lib/types.ts` — `AdminUserRow`/`AdminUserDetail` не мають `isBlocked`/`blockedAt`/
   `blockedNote`.
2. `src/lib/endpoints.ts` — немає `blockUser()`, лише `restrictUser()`.
3. `src/app/moderation/users/page.tsx` — немає кнопки блокування; **гірше** — текст під
   заголовком сторінки прямо каже оператору неправду: "ограниченный пользователь пока
   продолжает проходить TelegramAuthGuard как обычно, конкретные write-эндпоинты, обязанные
   это учитывать, — задача следующего прохода" — обидва твердження вже НЕ відповідають
   реальності (дев'ять точок `NotRestrictedGuard` реалізовано, `isBlocked` теж).

**Рішення — мінімальне розширення наявних файлів, не новий екран.** Кнопка "Заблокировать" —
поруч із наявною "Ограничить" у тому самому рядку таблиці, той самий UI-патерн
(input для нотатки + кнопка перемикання стану), не новий компонент. Текст-пояснення під
заголовком переписується на точний, не видаляється — користувач має розуміти різницю між
двома ступенями (`isRestricted` = дев'ять конкретних дій, `isBlocked` = все, включно з входом).

**Знахідка при аудиті UI, виправлена в backend, не тільки в документі:** проєктуючи кнопку
"Заблокировать" в UI, з'ясувалось — `AdminUsersService.blockUser()` не мав захисту від
self-lockout. Оператор міг заблокувати власний акаунт і втратити доступ до адмінки НАЗАВЖДИ
(`isBlocked` відхиляє вхід цілком, включно з окремим входом адмінки) — особливо критично для
соло-масштабу проєкту з одним оператором, де нема кому попросити розблокувати. Виправлено —
`blockUser` явно відхиляє спробу `operatorUserId === targetUserId`, з розблокуванням той самий
метод дозволяє (тільки блокування самого себе небезпечне, зняття — ні).
