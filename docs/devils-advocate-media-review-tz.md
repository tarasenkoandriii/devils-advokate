# Devil's Advocate — ТЗ: Public Media Review (тестування системи на публічних відео)

> Компаньон-документ до `devils-advocate-tz.md` та `devils-advocate-prompt-framework-tz.md`
> (`DiscrepancyAnalysisService`, Пункт 37). Виникло з прямого запиту: «чи можна протестувати
> систему на публічних відео з YouTube — соло-контенті та дискусіях двох і більше людей».
> Формат — production-бриф, достатній для передачі виконавцю без додаткових уточнень.

---

## 1. Контекст і межі того, що тут вирішується

Основний продукт Devil's Advocate побудований навколо **власної, приватної розмови користувача**
з конкретною метою (переговори, важлива розмова) — уся інфраструктура консенту, retention-класів,
voice-біометрії заточена під це. Публічний YouTube-контент — принципово інший випадок:

- контент вже публічний, консенту від його учасників не потрібно (те саме `ConsentType.EXTERNAL_AI`,
  яке й так вимагається від власника акаунту для будь-якого виклику зовнішнього AI-провайдера, —
  жодного НОВОГО консент-гейту не потрібно, перевірено в коді `ConsentService`/`conversations.service.ts`);
- користувач виступає **спостерігачем**, не учасником — модель `ConversationParticipant.isSelf`
  вже підтримує `false` для всіх учасників без помилок (перевірено в коді, не припущення);
- мета — не підготовка до власних переговорів, а **стрес-тест самої системи** на реальному,
  різноманітному публічному контенті.

Це НЕ окремий продукт і НЕ нова вертикаль — це режим тестування вже наявного аналітичного
конвеєра (`ManipulationDetectorService`, `DiscrepancyAnalysisService`, `TurningPointsService`)
на вхідних даних іншого походження. Тому архітектурне рішення (розділ 2) свідомо мінімальне —
нова точка входу даних + одне розширення джерела звірки, не новий конвеєр.

## 2. Архітектурне рішення — чотири окремі, слабко зв'язані компоненти

Свідомо НЕ один моноліт «YouTube-фіча» — чотири незалежні частини з різним рівнем ризику й
різними причинами існувати окремо.

### 2.1 YouTube Search (discovery) — `YouTubeSearchService`

Обгортка над офіційним **YouTube Data API v3** (`search.list`) — легальний, документований,
безкоштовний в межах квоти шлях. Повертає тільки метадані (заголовок, канал, thumbnail,
тривалість, дата публікації, videoId) — жодного відео/аудіо контенту не завантажує.

**Квота — реальне архітектурне обмеження, не дрібниця.** За станом на 2026 рік кожен запит
`search.list` коштує **100 quota-одиниць з денного ліміту 10 000** — тобто **не більше ~100
пошукових запитів на добу** на один Google Cloud проєкт (сам read окремого відео — 1 одиниця,
різниця на два порядки). Для соло-тестування системи цього достатньо з великим запасом, але це
означає: **автоматичний, доступний-для-множини-акаунтів пошук неможливий на цьому рівні
безкоштовно** — прийнятно для внутрішнього/дослідницького використання, не для продукту з
багатьма користувачами без окремого узгодження підвищення квоти з Google.

### 2.2 Video Acquisition — СВІДОМО НЕ автоматизовано на цьому проході

**Найважливіше архітектурне рішення цього ТЗ.** Не будується жоден серверний завантажувач відео
(`yt-dlp` чи еквівалент) як частина цього проєкту. Причина — не гіпотетична обережність, а
конкретний, актуальний правовий факт:

> **23 січня 2026 року** подано федеральний позов у Central District of California
> (справа **2:26-cv-00754**, TED Entertainment / MrShortGame / Golfholics проти Snap Inc.) —
> позивачі стверджують, що відповідач **масово завантажував YouTube-відео саме через `yt-dlp`
> з ротацією IP та автоматизованими віртуальними машинами САМЕ ДЛЯ AI-аналізу контенту**.
> Це буквально той самий технічний патерн, який тут розглядається (сервер, що завантажує
> YouTube-контент для подачі в AI), не абстрактна аналогія.

Сам `yt-dlp` як інструмент — легальний (відкритий код, Unlicense-ліцензія, мільйони завантажень
на місяць); питання не в законності інструменту, а в тому, **хто й з якою метою** його
використовує, і серверне масове завантаження стороннього контенту для AI-конвеєра — саме той
патерн, що зараз перебуває під судовим розглядом.

**Рішення — той самий принцип, що вже застосований в проєкті (Пункт 40,
`checkAgainstUserSource`): відповідальність і контроль лишаються за користувачем, система сама
нічого не завантажує.**

- «Вибір відео» (розділ 2.3) формує ЧЕРГУ посилань (`videoId` + метадані з YouTube Data API),
  не завантажує вміст.
- Реальний вміст (аудіо/відео файл) користувач отримує **сам, поза застосунком**, будь-яким
  способом на власний розсуд і власну відповідальність (той самий принцип особистого
  добросовісного використання/дослідження, що вже застосовується в багатьох юрисдикціях до
  завантаження контенту для особистого аналізу — але це юридична сіра зона, не гарантія, чесно
  зазначено в розділі 9).
- Файл потім завантажується в застосунок через **вже наявний** флоу `UPLOADED_VIDEO`
  (`ConversationSourceType.UPLOADED_VIDEO`, той самий, що для персональних записів) — нового коду
  для прийому файлу не потрібно взагалі.
- UI (розділ 2.3) з'єднує «вибрані з пошуку відео» з «завантаженими файлами» через збіг
  `videoId` (введений користувачем вручну або зчитаний з імені файлу за домовленою конвенцією
  найменування) — не автоматичний зв'язок.

Це свідоме звуження, не технічна недоробка — перевірено окремо, чи є легальна альтернатива
(розділ 2.2a).

### 2.2a Розглянута й відхилена альтернатива — офіційні субтитри YouTube

YouTube Data API має метод `captions.download`, який теоретично дав би текст без завантаження
відео взагалі. **Відхилено** — цей метод вимагає OAuth-авторизації як **власника каналу** цього
відео (перевірено документацію API) — недоступний для чужого контенту без дозволу автора,
не обхід проблеми 2.2, а той самий бар'єр в іншому вигляді.

### 2.3 Sequential batch review — нова вкладка TMA

UI-компонент — послідовний перегляд і аналіз кількох відео підряд, саме та можливість, яку
запитував користувач як «ідеальний варіант тестування системи загалом».

**Потік:**
1. Рядок пошуку → `YouTubeSearchService.search(query)` → список карток (thumbnail, заголовок,
   канал, тривалість, дата).
2. Мультивибір карток → черга `MediaReviewQueue` (нова сутність, розділ 4).
3. Для кожного елементу черги — статус `AWAITING_UPLOAD` (показує videoId + посилання на
   YouTube для власного перегляду/завантаження користувачем) → `READY` (файл завантажено й
   зв'язано) → `PROCESSING` (транскрибація/аналіз) → `DONE`.
4. **Послідовний режим перегляду** — «Далі» проводить користувача по черзі один елемент за
   раз: показує результати аналізу поточного відео (маніпуляції, розбіжності, turning points),
   дає перейти до наступного без ручного повернення до списку. Це і є механізм «пройти по
   кількох роликах поспіль», який запитувався.
5. Підсумкова зведена картка по завершенню черги — скільки відео опрацьовано, скільки
   маніпулятивних патернів/розбіжностей знайдено сукупно (агрегація вже наявних
   `ConversationSignal` по всіх розмовах черги, не нова модель метрик).

### 2.4 Розширення `DiscrepancyAnalysisService` під web-пошук — джерело #4

Четверте джерело звірки з §3.16 ТЗ (implementation-ready), явно виключене в Пункті 37 через
відсутність інфраструктури пошуку. Тепер є конкретний, вузький, легальний шлях —
**Google Fact Check Tools API** (`claims:search`), не відкритий веб-пошук.

**Чому саме цей API, не загальний веб-пошук — принципова відмінність:**

| | Fact Check Tools API | Відкритий веб-пошук по темі/людині |
|---|---|---|
| Що шукає | Конкретне ТВЕРДЖЕННЯ (текст claim), проти вже проведених фактчеків | Що завгодно про будь-що, включно з людиною як об'єктом |
| Джерела | Структуровані `ClaimReview`-розмітки від акредитованих фактчекерів (PolitiFact, Snopes, FactCheck.org, Reuters Fact Check тощо) | Довільні сайти, без верифікації публікатора |
| Прозорість | Точний запит і точний список джерел — видно, що саме шукали і хто відповів | Непрозоро, "AI сам вирішив, що шукати" |
| Профілювання людини | Неможливе за дизайном — API не має "пошуку за особою", тільки за текстом твердження | Пряма можливість — це і є те, що вже було відхилено в Пункті 40 |

**Розділ 3 — детальне етичне обґрунтування цього вибору.**

## 3. Етичні межі — узгодження з рішенням Пункту 40

Пункт 40 (`checkAgainstUserSource`) явно відхилив **автономний AI-пошук по імені людини**,
сформулювавши це як «інструмент стеження за конкретною приватною особою незалежно від
упаковки». Це рішення НЕ скасовується і НЕ обходиться тут — воно звужується до чіткіших меж.

**Ключова відмінність, яка робить розширення прийнятним, а не порушенням попереднього рішення:**

1. **Одиниця пошуку — ТВЕРДЖЕННЯ, не ЛЮДИНА.** Fact Check Tools API фізично не має параметра
   "знайди все про Івана Петренка" — тільки `query: string` тексту твердження. Неможливо
   випадково побудувати профіль людини через цей ендпоінт, структурно, не лише за домовленістю.
2. **Ініціація — користувач, не автоматика.** Система НЕ сканує кожну репліку відео і НЕ
   запускає перевірку автоматично на всі 40+ тверджень типової розмови. Аналітик (користувач)
   **вручну вибирає конкретне твердження** з уже знайденої `DiscrepancyAnalysisService`
   розбіжності (той самий UX, що вже є в `checkAgainstUserSource` — кнопка "перевірити" на
   конкретному сегменті, не батч-операція).
3. **Публічність контенту не скасовує принцип, а лише змінює баланс.** Публічна фігура в
   публічному відео має нижче очікування приватності, ніж приватна особа в приватній розмові —
   але дискусія на YouTube МОЖЕ включати звичайних коментаторів/гостей, не тільки публічних
   осіб. Тому обмеження застосовується **однаково до всіх учасників розмови**, не лише до
   "неважливих" — не система вирішує, хто досить публічний, щоб його можна було перевіряти
   агресивніше.
4. **Прозорість запиту й відповіді.** Кожен виклик логується як `ConversationSignalEvidence`
   з точним текстом запиту, що пішов у Fact Check Tools API, і точним списком джерел, що
   повернулися — той самий принцип аудитованості, що вже застосовується до
   `checkAgainstUserSource`.

**Що залишається свідомо ЗА межами цього ТЗ, той самий клас рішення, що в Пункті 40:**
- Немає кнопки "перевір усе відео цілком одним натиском" — це знову стало б автоматичним
  масовим скануванням, тим самим паттерном, що вже відхилений.
- Немає збереження результатів пошуку Fact Check Tools API як частини профілю конкретної
  `Person` для накопичення "історії брехні" тієї людини через сесії — кожен виклик прив'язаний
  до конкретного `ConversationSignal` цієї розмови, не до `Person` глобально. Якщо в майбутньому
  захочеться такого накопичення — це окреме рішення, що вимагає окремого обговорення meж, не
  тихе розширення цього ТЗ.

## 4. Схема — нові сутності

```prisma
// Черга відео, відібраних із YouTube-пошуку для послідовного огляду.
// НЕ зберігає сам відео-контент (розділ 2.2) — тільки метадані й
// статус зв'язку з реальною завантаженою Conversation.
model MediaReviewQueue {
  id      String @id @default(cuid())
  userId  String
  user    User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  title   String // назва черги, задає користувач ("Дебати про клімат — жовтень")

  items MediaReviewQueueItem[]

  createdAt DateTime @default(now())

  @@index([userId])
  @@map("media_review_queues")
}

model MediaReviewQueueItem {
  id      String            @id @default(cuid())
  queueId String
  queue   MediaReviewQueue  @relation(fields: [queueId], references: [id], onDelete: Cascade)

  youtubeVideoId String
  title          String
  channelName    String
  thumbnailUrl   String
  durationSeconds Int?
  publishedAt    DateTime?

  status MediaReviewItemStatus @default(AWAITING_UPLOAD)

  // Заповнюється, коли користувач завантажив файл і зв'язав його —
  // звідси й далі вся аналітика йде через уже наявний конвеєр
  // Conversation/ConversationParticipant/ConversationSignal, нових
  // полів під аналіз тут немає.
  conversationId String?
  conversation   Conversation? @relation(fields: [conversationId], references: [id], onDelete: SetNull)

  orderIndex Int // порядок у черзі для послідовного режиму перегляду

  createdAt DateTime @default(now())

  @@index([queueId, orderIndex])
  @@map("media_review_queue_items")
}

enum MediaReviewItemStatus {
  AWAITING_UPLOAD // відео вибрано з пошуку, файл ще не завантажений користувачем
  READY           // файл завантажено й зв'язано, готовий до аналізу
  PROCESSING      // Conversation.status у процесі (STT/аналіз)
  DONE
}
```

`ConversationSignalEvidence` (вже існує) отримує ще один тип посилання —
`factCheckClaimId: String?` (id claim з відповіді Fact Check Tools API, для аудитованості
розділу 3, п.4) поруч із уже наявними `personFactId`/`observationId`/`aiInferenceId`.

## 5. Backend API contract

```
GET  /media-review/youtube-search?query=...
  → { videoId, title, channelName, thumbnailUrl, durationSeconds, publishedAt }[]
  Обгортка search.list, TelegramAuthGuard. Rate-limit на рівні сервісу — не більше
  N запитів на користувача на добу (конкретне число — калібрується під реальну квоту
  Google Cloud проєкту, не вигадується наперед).

POST /media-review/queues
  Body: { title: string }
  → MediaReviewQueue

POST /media-review/queues/:id/items
  Body: { youtubeVideoId, title, channelName, thumbnailUrl, durationSeconds?, publishedAt? }
  → MediaReviewQueueItem (status: AWAITING_UPLOAD)

PATCH /media-review/queue-items/:id/link-conversation
  Body: { conversationId: string }
  → MediaReviewQueueItem (status: READY, якщо Conversation існує й належить тому ж userId)

GET  /media-review/queues/:id
  → MediaReviewQueue з items[], відсортованими по orderIndex — основа послідовного режиму

POST /discrepancy-analysis/segments/:segmentId/check-against-fact-check-api
  Body: { claimText: string } // текст твердження, який АНАЛІТИК сформулював/скоротив
                               // з реплики — не сирий текст сегмента автоматично
  → { claims: FactCheckClaim[] } (результат Google Fact Check Tools API, збережений
    як ConversationSignalEvidence з factCheckClaimId)
```

## 6. Acceptance-тести

```
Given порожня черга MediaReviewQueue
When користувач шукає "climate debate 2026" і додає 3 відео в чергу
Then усі 3 мають status=AWAITING_UPLOAD, orderIndex 0/1/2

Given елемент черги AWAITING_UPLOAD
When користувач завантажує відповідний файл через звичайний UPLOADED_VIDEO флоу
     і викликає link-conversation
Then status стає READY, і після завершення STT/аналізу — DONE

Given послідовний режим перегляду черги з 3 елементами, перший DONE
When користувач натискає "Далі"
Then показується другий елемент, не потрібно вручну повертатись до списку

Given сегмент розмови з реплікою політика
When аналітик вручну формулює claimText і викликає check-against-fact-check-api
Then система НЕ виконує пошук по імені політика — тільки по тексту claimText,
     результат зберігається з посиланням на конкретний factCheckClaimId

Given система обробила 40 реплік одного відео
Then НІ ОДНА з них не була автоматично відправлена в Fact Check Tools API без
     явної дії аналітика на кожну — немає кнопки "перевір усе відео"
```

## 7. Що свідомо виключено з цього проходу

- **Серверне завантаження відео** (розділ 2.2) — не з технічних причин, з юридичних (активний
  позов саме на цей патерн). Переглянути це рішення можна тільки після появи ясності по справі
  2:26-cv-00754 або окремої юридичної консультації, не за замовчуванням "тепер можна".
- **Транскрипти YouTube через API** — заблоковано авторизацією власника каналу (розділ 2.2a).
- **Автоматичний батч-фактчекінг усього відео одним натиском** — свідомо, не тимчасово
  (розділ 3).
- **Накопичення результатів фактчекінгу в профіль конкретної Person між сесіями** — окреме
  рішення, не тихе розширення.
- **Multi-user/продуктовий масштаб пошуку** — квота 100 запитів/добу (розділ 2.1) достатня для
  одноосібного тестування, не для багатьох користувачів без запиту на підвищення ліміту Google.
- **Оцінка "хто бреше більше" між кількома фігурантами** — система фіксує розбіжності по
  конкретних твердженнях, не видає сумарний вердикт/рейтинг правдивості людини — це вже було б
  формою профілювання, того самого класу, що відхилений в Пункті 40.
