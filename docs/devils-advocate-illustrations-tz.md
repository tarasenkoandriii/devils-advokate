### 2.2 Технические требования к SVG

- **Сетка**: 24×24 viewBox, безопасная зона отрисовки — 20×20 (2px отступ со всех сторон)
- **Толщина обводки**: 1.5px для навигационных/UI-иконок, 2px для крупных смысловых иконок (главный цикл, приватность)
- **Стиль**: line-icons (обводка), без заливки, кроме status-иконок индикатора накала (2.1) — там заливка несёт цветовую семантику и должна быть однозначной
- **Скругление углов**: 2px радиус на всех прямых углах — единый стиль по всей системе, никаких смешанных острых/скруглённых иконок
- **Naming convention**: `kebab-case`, `{category}-{name}` (например, `escalation-critical`, `source-ai-guess`) — соответствует enum-значениям из ТЗ (`escalationCategory: calm|rising|high|critical`, `sourceType`), чтобы имя файла напрямую маппилось на код без ручного сопоставления
- **Экспорт**: `.svg` оптимизирован (SVGO, без метаданных редактора, без лишних `<g>`-обёрток), плюс `.png` fallback 24/48/96px для мест, где SVG недоступен (Telegram push-уведомления)

### 2.3 Цветовые токены

Обязательное соответствие уже определённой в продукте цветовой семантике — не вводить новые цвета произвольно:

| Токен | Назначение | HEX (плейсхолдер — фиксируется бренд-гайдом) |
|---|---|---|
| `--signal-calm` | escalation-calm, спокойное состояние | зелёный |
| `--signal-rising` | escalation-rising | жёлтый |
| `--signal-high` | escalation-high | оранжевый |
| `--signal-critical` | escalation-critical | красный |
| `--source-public` | source-public-fact | синий |
| `--source-personal` | source-personal-record | зелёный |
| `--source-ai-guess` | source-ai-guess | жёлтый |
| `--source-user-guess` | source-user-guess | серый |
| `--neutral-ink` | обычные UI-иконки | тёмно-серый/чёрный по теме |

**Правило**: ни одна иконка не использует hex-код вне этой таблицы токенов напрямую — только через переменную/токен. Это то, что программно проверяется на этапе приёмки (2.4).

### 2.4 Программная валидация (обязательный этап приёмки)

По аналогии с уже отработанным пайплайном:

1. **XML well-formedness** — каждый `.svg` парсится и проверяется на валидность XML, отсутствие оборванных тегов
2. **Pixel-level bounding box** — автоматическая проверка, что отрисовка не выходит за пределы безопасной зоны 20×20 (2.2), и не имеет пустых/вырожденных path
3. **Color-token compliance** — скрипт сверяет все `fill`/`stroke` атрибуты со списком разрешённых токенов (2.3), любое отклонение — блокирующая ошибка
4. **JSON Schema манифеста** — `icons-manifest.json` с полями `{id, category, tags[], viewBox, fileSizeBytes, tokensUsed[]}` на каждую иконку, манифест валидируется JSON Schema перед сборкой
5. **Дедупликация** — проверка на визуально идентичные/почти идентичные иконки (например, случайно продублированный `argument-pro` под другим именем)

Иконка не считается принятой, пока не проходит все 5 проверок — не ручная вычитка, а автоматический gate, аналогично `ReleaseGate` для AI-моделей в техническом ТЗ.

## 3. Иллюстрации

### 3.1 Hero-иллюстрация лендинга — растровое изображение
*Уточнено: hero, карта фич (3.2a) и сценарии использования (3.2b) выполняются растровыми изображениями, а не SVG — по аналогии с уже отработанным подходом (фотореалистичные растровые иллюстрации для hero и инфографики на лендингах других проектов), в отличие от иконочной системы (раздел 2), которая остаётся строго векторной.*

Визуализация главного цикла (Prepare → Practice → Talk → Review → Learn, раздел 3.2 ТЗ лендинга) — не абстрактная сцена, а читаемая композиция из 5 стадий:
- **Стиль** — фотореалистичный или полу-реалистичный растровый рендер (не плоская флэт-иллюстрация, не 3D-рендер с пластиковыми персонажами), консистентный по свету/цветовой грейдировке с остальными растровыми иллюстрациями лендинга (3.2a, 3.2b)
- **Композиция** — циклическая схема из 5 стадий, читаемая как последовательность, а не единый неразделимый сюжет — совмещает иконографию цикла (2.1) как встроенные визуальные акценты поверх растровой сцены
- **Технические требования**: минимальная ширина исходника — 3000px (retina/2x-3x экспорт для hero-баннера полной ширины), форматы поставки `.png` (с прозрачностью, если требуется наложение на цветной фон) и `.webp` для продакшена, цветовой профиль sRGB

### 3.2a Карта фич (feature map) — растровая инфографика
Гибридная инфографика продукта — не список карточек с иконками, а единая композиция, показывающая, как основные фичи (Red Team/Steelman, Карточка разговора, Приватность/Safe Share, Track Record) связаны друг с другом в рамках главного цикла:
- Растровое изображение с встроенными подписями/лейблами (текст — часть композиции изображения либо накладывается HTML-слоем поверх — решить на этапе фронтенд-вёрстки, чтобы не жертвовать локализацией текста ради цельности картинки)
- Та же фотореалистичная/полу-реалистичная стилистика, что и hero (3.1) — карта фич не должна визуально выбиваться как отдельный, несвязанный с остальным лендингом стиль
- Технические требования — как в 3.1 (минимум 3000px по большей стороне, `.png`/`.webp`, sRGB)

### 3.2b Сценарии использования (how it's used) — растровые иллюстрации
Набор иллюстраций, показывающих контексты, в которых применяется продукт — по аналогии с уже отработанным паттерном «режимов использования» (несколько сценариев, каждый — отдельная растровая иллюстрация в едином стиле):
- **Личная встреча** — подготовка/спарринг перед очным разговором
- **Телефонный/аудиозвонок** — использование во время звонка (с учётом Capability Matrix основного ТЗ — это иллюстрация сценария использования, не гарантия технической доступности live-режима на всех платформах)
- **Видеозвонок** — тот же сценарий для видеоформата

Каждая иллюстрация — отдельный растровый файл в единой стилистике с hero (3.1) и картой фич (3.2a), не три разных художественных языка. Технические требования — как в 3.1.

### 3.3 Фичевые иллюстрации (лендинг, раздел 3.5 landing-ТЗ)
По одной иллюстрации на каждую из 2-3 отобранных ключевых фич, не входящих в карту фич (3.2a) как отдельные акценты в тексте секций:
- **Red Team / Steelman** — визуальная метафора «две стороны одного стола» или «зеркальное отражение позиции» — не буквальные два человека спорят (клише), лучше абстрактная композиция из реплик/аргументов с двух сторон
- **Карточка разговора** — сама карточка как UI-мокап, стилизованный, не реальный скриншот продукта на этапе, когда UI ещё не финализирован
- **Калибровка/Track Record** — график/кривая обучения, минималистичная инфографика, не декоративная

Формат — на усмотрение на этапе концепта: растровый (консистентно с 3.1/3.2a/3.2b) либо векторный (консистентно с иконочной системой, раздел 2) — решить в зависимости от того, ближе ли конкретная иллюстрация по духу к «сцене» или к «диаграмме».

### 3.4 Ограничение на иллюстрации архетипов перспектив — важный нюанс
Продукт использует именованные архетипы для симуляции перспектив («ревнивая жена», «скандалист», «юрист», «полицейский», «бабушка у подъезда» и т.д. — раздел 3.11 основного ТЗ). **Эти архетипы не иллюстрируются буквально как персонажи-карикатуры**, в том числе и в растровом исполнении. Причины:
- Буквальная иллюстрация архетипа (например, визуально утрированная «ревнивая жена») превращается в обидный стереотип, что противоречит и здравому вкусу, и репутационным рискам публичного сервиса
- Вместо портретных иллюстраций — **абстрактная иконография** (векторная, раздел 2): каждый архетип получает нейтральную иконку-символ (весы для юриста, значок безопасности для полицейского, дом для соседа/бабушки и т.д.), не лицо и не фигуру человека с гендерными/возрастными стереотипными чертами
- Если для UI нужен визуальный «аватар» перспективы — использовать нейтральные геометрические/цветовые метки (буква/инициал + цвет), не иллюстрированного персонажа

### 3.5 Визуальный язык индикатора накала
Расширение цветовой системы (2.3) в анимированный/статический визуальный компонент для экрана сопровождения разговора (3.33 основного ТЗ):
- 4 состояния (calm/rising/high/critical) как единая шкала/градиент, не 4 разрозненные иконки без связи между собой
- Опциональная лёгкая анимация перехода между состояниями (pulse/glow) — специфицируется отдельно на этапе frontend-реализации, не часть иконочного пакета как такового
- Формат — векторный (часть иконочной системы, раздел 2), не растровый, так как компонент используется внутри продукта в реальном времени и должен масштабироваться без потери качества

### 3.6 Приватность / Safe Share — визуальный язык
Отдельная последовательная иконография для privacy-flow (Privacy Preflight, экспорт, удаление) — должна визуально считываться как «под контролем», не тревожная/угрожающая эстетика замков-и-щитов из типового SaaS-стока:
- Спокойная, не алармистская палитра (не ярко-красные щиты «ОПАСНОСТЬ», а нейтральный, уверенный визуальный тон)
- Единая пиктограмма для «локально» (устройство) и «на сервере» (облако) — переиспользуется везде, где идёт речь о `LOCAL_ONLY`/`EPHEMERAL_SERVER`

### 3.7 OG-изображения (соцсети)
- Один универсальный OG-шаблон на 1200×630, с локализуемым текстовым слоем (заголовок позиционирования на 3 языках — EN/UA/RU, см. landing-ТЗ раздел 4)
- Не переиспользовать hero-иллюстрацию 1:1 — OG требует более крупного, читаемого на маленьком превью текста и упрощённой композиции
- Формат — растровый (`.png`), как и hero (3.1), фрагмент композиции hero допустимо переиспользовать как основу, но не как финальный кадр без адаптации под формат 1200×630

## 4. Технологии и процесс генерации

- **Пайплайн производства (векторные активы — иконки, раздел 2)**: бриф → референс/концепт (в т.ч. AI-генерация для проработки направления) → векторная отрисовка/чистовая отрисовка вручную или через AI+ручная доводка → программная валидация (2.4) → манифест
- **Пайплайн производства (растровые активы — hero 3.1, карта фич 3.2a, сценарии использования 3.2b, OG 3.7)**: бриф со детальным описанием композиции и стиля → AI-генерация (фотореалистичный/полу-реалистичный рендер) → ручной ретушь/доводка (цветокоррекция, устранение артефактов генерации, приведение к единой стилистике между всеми растровыми активами) → экспорт в требуемых разрешениях и форматах
- **Иконки — вручную/через векторизацию**, не финальный AI-рендер как есть: AI-сгенерированные растровые иконки почти всегда требуют перерисовки в чистый SVG для соответствия сетке (2.2) и токенам (2.3) — контроль качества строже, чем для декоративных иллюстраций
- **Растровые иллюстрации (3.1, 3.2a, 3.2b) — AI-генерация как основа с доработкой** — растровый экспорт должен быть в разрешении, достаточном для retina-дисплеев (минимум 2x-3x от отображаемого размера, минимум 3000px по большей стороне для hero и карты фич)
- **Единство стиля обязательно между всеми растровыми активами** (3.1, 3.2a, 3.2b, 3.7) — если генерация ведётся отдельными запросами/сессиями, обязателен этап сведения к общей цветовой грейдировке и художественному языку перед финальной приёмкой, чтобы лендинг не выглядел собранным из разностильных кусков
- **Выбор конкретного инструмента генерации** — не фиксируется этим ТЗ, определяется на этапе исполнения; проверка соответствия финального результата брендбуку (цвета, стиль, ограничение 3.4) обязательна независимо от инструмента

## 6. Приоритизация

**v1 (для запуска лендинга и MVP)**: главный цикл (5 иконок), escalation-иконки (4), source-provenance иконки (4), базовая UI-навигация (8), hero-иллюстрация (растр, 3.1), карта фич (растр, 3.2a), 2 фичевые иллюстрации (3.3), OG на 1 язык, favicon/manifest

**v2**: полный набор иконок (~52), сценарии использования (растр, 3.2b, все три), приватность-иконография (3.6) как отдельная согласованная серия, OG на 3 языка, визуальный язык индикатора накала с анимацией

**v3+**: иконография для архетипов перспектив (с учётом ограничения 3.4), иллюстрации для расширенных фич (партнёрка заведений, планировщик) — по мере того, как эти фичи выходят из roadmap v3/v4 основного ТЗ в разработку
