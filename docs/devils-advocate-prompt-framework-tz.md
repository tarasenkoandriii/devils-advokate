## 1. Разрыв между спецификацией и реализацией (находки аудита кода)

Проверено напрямую в коде, не предположение.

**Что уже читает из системы промптов:** 35 сервисов по всему проекту (`argument-generation`,
`archetype-perspective`, `best-next-move`, `breaking-questions`, `material-chat` и другие) уже
запрашивают активную версию промпта:

```typescript
const activePrompt = await this.prisma.promptVersion.findFirst({
  where: { promptId: TASK_TYPE, status: 'ACTIVE' },
  orderBy: { createdAt: 'desc' },
});
// ...
systemPrompt: activePrompt?.template ?? SYSTEM_PROMPT, // честный fallback на хардкод
```

Это реальная, работающая интеграция — не аспирационная. Каждый AI-вызов в проекте уже готов
подхватить версию промпта из БД, если она там появится.

**Чего нет вообще:** ни одного контроллера или сервиса, создающего или обновляющего запись
`PromptVersion`. Таблица существует, 35 потребителей на неё готовы, но записать в неё можно
только вручную через прямой доступ к БД. Практическое следствие: `PromptVersionStatus.ACTIVE`
физически не может появиться иначе, как ручной SQL — раздел 6 implementation-ready.md описывает
flow `draft → testing → evaluation → active`, но ни один из переходов этого flow не реализован.

**Отдельная, более глубокая проблема:** `EvaluationDataset` в текущей схеме —
```prisma
model EvaluationDataset {
  name        String
  version     String
  description String?
}
```
— то есть только имя и версия, **без единого поля для хранения самих тестовых кейсов**
(вход + ожидаемый результат). Даже если бы существовал API создания `EvaluationRun`, запускать
было бы физически не над чем — негде хранить, что именно проверяется. Это не второстепенная
недоделка, это отсутствие фундамента, без которого раздел 6 не может заработать вообще ни для
одной фичи.

**Проверено — нет ни одного места, где `EvaluationRun`/`ReleaseGate` создаются:**
```
grep -rln "evaluationRun.create\|releaseGate.create" apps/api/src → пусто
```

Итог: раздел 6 implementation-ready.md — корректная, продуманная спецификация целевого
состояния. Но между «схема существует» и «gate реально работает» — весь объём этого документа.

## 2. Что уже работает и не требует изменений

Чтобы не переделывать то, что не сломано:

- **`PromptVersion` как модель** — поля (`promptId`, `version`, `template`, `changelog`, `status`)
  достаточны, менять не нужно.
- **Чтение активной версии 35 сервисами** — уже работает, с честным fallback на хардкод-промпт.
  Этот паттерн **не меняется** — при появлении API управления версиями сервисы-потребители
  трогать не нужно, они уже готовы.
- **`AIJob`/`AIInference`** — уже фиксируют `promptVersionId` на каждый вызов (когда он есть).
  Это значит, что как только появится реальный `ACTIVE` `PromptVersion`, история его использования
  начнёт накапливаться автоматически, без дополнительной работы.
- **Полиморфизм `EvaluationRun.subjectType`** (`PROMPT_VERSION | MODEL_VERSION`) — архитектурно
  оправдан для классификационного типа оценки (см. §4.1), сохраняется.

## 3. Недостающая модель данных

### 3.1 `EvaluationCase` — новая сущность

Без неё evaluation запускать не над чем. Один кейс — один тестовый пример.

```prisma
model EvaluationCase {
  id                  String            @id @default(cuid())
  evaluationDatasetId String
  evaluationDataset   EvaluationDataset @relation(fields: [evaluationDatasetId], references: [id], onDelete: Cascade)

  // Вход — то, что реально уйдёт в AI-вызов при прогоне (тот же shape,
  // что userPrompt конкретного сервиса-потребителя). Свободный текст,
  // не типизируем структуру заранее — она разная для каждого promptId.
  input String

  // Ожидаемый результат — ЕДИНОГО формата для всех типов оценки НЕТ
  // (см. §4, три gate работают по-разному). Поле свободный JSON,
  // конкретную форму задаёт caseType.
  expectedOutput Json?

  // "classification" — expectedOutput это {label: string} или {labels: string[]},
  //   сравнивается с фактическим выводом AI напрямую (§4.1).
  // "structural" — expectedOutput не используется, проверяется свойство
  //   самого вывода (например, наличие поля), не сравнение с образцом (§4.2).
  caseType String

  createdAt DateTime @default(now())

  results EvaluationCaseResult[]

  @@index([evaluationDatasetId])
  @@map("evaluation_cases")
}
```

### 3.2 `EvaluationCaseResult` — новая сущность

`EvaluationResult` (уже существует) хранит **агрегированную** метрику по всему прогону
(`accuracy = 0.87`). Это подходит для отчёта, но не даёт разработчику увидеть, **какие именно**
кейсы провалились — а без этого отчёт о провале gate бесполезен для отладки (implementation-ready.md
прямо требует «разработчик получает отчёт с деталями провала», раздел 6). Нужен детальный уровень:

```prisma
model EvaluationCaseResult {
  id               String         @id @default(cuid())
  evaluationRunId  String
  evaluationRun    EvaluationRun  @relation(fields: [evaluationRunId], references: [id], onDelete: Cascade)
  evaluationCaseId String
  evaluationCase   EvaluationCase @relation(fields: [evaluationCaseId], references: [id], onDelete: Cascade)

  actualOutput String  // реальный вывод AI на этом кейсе
  passed       Boolean // прошёл ли именно этот кейс (не агрегат)
  note         String? // например, для structural-кейсов — какое поле отсутствовало

  createdAt DateTime @default(now())

  @@unique([evaluationRunId, evaluationCaseId])
  @@index([evaluationRunId])
  @@map("evaluation_case_results")
}
```

`EvaluationRun` дополняется связью `caseResults EvaluationCaseResult[]`.

### 3.3 Изменения в существующих моделях

`EvaluationRun` — без изменений структуры, только новая связь (`caseResults`) добавляется.

`EvaluationDataset` — добавляется связь `cases EvaluationCase[]`.

## 4. Три обязательных gate — они НЕ одинаковы по механике

Implementation-ready.md называет три high-risk фичи, обязанные пройти gate «без исключений», но
не определяет метрики (явно отложено «на этап технического проектирования» — это именно тот
этап). При проектировании обнаружено: три фичи требуют **трёх разных типов оценки**, не одного
шаблона. Попытка притянуть все три к единому механизму `EvaluationDataset` + фиксированный
threshold была бы нечестной — не отражала бы, как эти фичи реально устроены.

### 4.1 Детектор расхождений/уловок/прощупывания (`ConversationSignal`) — классификация

Классическая задача: дан фрагмент транскрипта, детектор должен(не должен) найти сигнал.
`caseType: "classification"`.

- **Датасет:** размеченные вручную фрагменты транскриптов с ожидаемой меткой
  (`{label: "strong_discrepancy"} | {label: "none"} | ...`).
- **Метрики:** `precision`, `recall`, `false_positive_rate` — считаются прямым сравнением
  `actualOutput` каждого кейса с `expectedOutput.label`.
- **Обязательный порог false positive для `strong_discrepancy`** — implementation-ready.md
  требует явно. Стартовое значение: **`false_positive_rate ≤ 0.05`** для этой категории
  (не более 1 ложного срабатывания на 20 кейсов) — сознательно консервативно, потому что
  false positive здесь означает обвинение пользователя в противоречии, которого не было.
  Это стартовая, не окончательная цифра — калибруется по факту первого реального прогона
  (см. §7, что сознательно не фиксируется).
- **Минимальный размер датасета для валидного прогона:** 40 кейсов на категорию сигнала —
  меньше даёт слишком широкий доверительный интервал для принятия production-решения.

### 4.2 Анализ мотивов (`PersonMotiveAnalysis`) — структурная проверка, не классификация

Implementation-ready.md формулирует это не как точность распознавания, а как требование
полноты: **«каждая гипотеза в тестовом наборе обязана иметь `alternativeExplanation`, иначе gate
не пройден»**. Это буквально проверка наличия непустого поля в каждом сгенерированном элементе,
не сравнение с «правильным» ответом — в задаче мотивного анализа единственно верного ответа
не существует по своей природе (мотив — гипотеза, не факт). `caseType: "structural"`.

- **Датасет:** входные сценарии (ситуация + доступные факты о фигуранте), `expectedOutput`
  не используется вообще — сам факт наличия датасета нужен только чтобы иметь на чём прогнать
  генерацию.
- **Метрика:** `alternative_explanation_completeness` = доля сгенерированных гипотез, где
  `alternativeExplanation` непустой. **Порог: 100%** — implementation-ready.md формулирует это
  как жёсткое «иначе gate не пройден», не как процент с запасом.
- **`EvaluationCaseResult.note`** для непройденных кейсов явно указывает, у какой по счёту
  гипотезы в выводе отсутствует `alternativeExplanation` — иначе разработчик получает только
  «не прошло», без возможности отладки.

### 4.3 Прогнозы по сценариям (`calibratedProbability`) — калибровка на реальных исходах, не фиксированный датасет

Здесь `EvaluationDataset`/`EvaluationCase` в буквальном смысле не подходят — калибровка
вероятности не проверяется на заранее размеченных примерах, она проверяется на том, **насколько
предсказанные вероятности соответствовали реально произошедшим исходам** — а исходы появляются
только после того, как реальные пользователи реально прошли через реальные разговоры и
зафиксировали результат (`Prediction`, Пункт 25, уже существует и уже накапливает эту пару
«предсказано / что случилось на самом деле»).

- **Механизм принципиально другой:** не «нажать кнопку прогнать оценку», а плановая
  (`pg_cron`, тот же паттерн, что уже используется в проекте для повторяющихся задач)
  пересборка калибровочной статистики по накопленным `Prediction`-записям.
- **Метрика — ИСПРАВЛЕНО АУДИТОМ (полный проход по коду):** первоначальная формула здесь
  указывала Brier score как `mean((calibratedProbability - actualOutcome)²)` — то есть против
  только что эмпирически выведенной самой `calibratedProbability`. При реализации это было явно
  выявлено и исправлено как логическая ошибка, не как вкусовщина: если Brier score считать
  против того же значения, которое он якобы измеряет, метрика становится тавтологией — измеряет
  саму себя, не реальную точность категорий уверенности. **Верная формула:** Brier score
  считается против ФИКСИРОВАННЫХ якорей категорий уверенности —
  `LOW → 0.25`, `MEDIUM → 0.5`, `HIGH → 0.75` — `mean((anchor(confidence) - actualOutcome)²)`
  по всем `Prediction` с заполненным фактическим исходом. `calibratedProbability` остаётся
  ОТДЕЛЬНЫМ, эмпирическим значением (доля подтверждённых исходов в корзине конкретной категории
  уверенности) — записывается обратно в `OutcomeScenario` как лучшая текущая оценка вероятности
  для новых сценариев той же категории, но НЕ участвует в собственном вычислении Brier score.
  **АУДИТ, вторая правка в этом же абзаце:** "за скользящее окно" здесь тоже не соответствует
  реализации — код берёт ВСЮ накопленную историю подтверждённых исходов без временной
  фильтрации, скользящего окна не существует. Честно зафиксировано как отсутствующее — не
  добавлено молча в реализацию задним числом, потому что у самого понятия "скользящее окно"
  нет зафиксированного размера ни в этом документе, ни в implementation-ready.md — вводить его
  сейчас значило бы гадать конкретное число, а не переносить уже принятое решение.
- **Обязательное условие из implementation-ready.md, буквально:** `calibratedProbability` не
  активируется, «пока датасет исходов меньше минимального размера выборки». Стартовое значение
  минимальной выборки: **30 предсказаний с известным исходом** — ниже этого Brier score
  статистически ненадёжен для production-решения.
- **`ReleaseGate.gateType`** для этого случая — новое значение `"calibration_threshold"`
  (наряду с уже описанными в схеме `"prompt_promotion"` / `"model_activation"`), фиксирует
  именно этот, отличный от двух других, тип решения.
- Пока минимальная выборка не набрана — `calibratedProbability` продолжает работать в текущем
  режиме (uncalibrated/экспериментальный), это НЕ блокирует саму фичу «прогнозы», блокирует
  только доверие к конкретному числу вероятности — честная деградация, тот же принцип, что уже
  применяется по всему проекту.

## 5. API-контракты

Расширяет черновой набросок из implementation-ready.md §2.10 до полного контракта.

### 5.1 Prompt Registry

| Метод | Путь | Описание | Тело | Ответ |
|---|---|---|---|---|
| `POST` | `/admin/prompts` | Новая версия промпта, статус `draft` | `{ promptId, version, template, changelog? }` | `PromptVersion` |
| `GET` | `/admin/prompts/:promptId` | Все версии одного промпта | — | `PromptVersion[]` |
| `GET` | `/admin/prompts/:promptId/active` | Текущая активная версия | — | `PromptVersion \| null` |
| `PATCH` | `/admin/prompts/:id` | Изменить `template`/`changelog` — **только пока `status: draft`** | `{ template?, changelog? }` | `PromptVersion` |
| `POST` | `/admin/prompts/:id/promote-to-testing` | `draft → testing` | — | `PromptVersion` |
| `POST` | `/admin/prompts/:id/rollback` | Откат на предыдущую `ACTIVE`-версию тем же `promptId` — одна операция, не восстановление из бэкапа (implementation-ready.md §7, правило 4) | — | `PromptVersion` (новая активная) |

`PATCH` после `testing` запрещён намеренно — версия, уже прошедшая (или проходящая) оценку,
не должна тихо измениться под тем же id; правка контента требует новой версии.

### 5.2 Evaluation

| Метод | Путь | Описание | Тело | Ответ |
|---|---|---|---|---|
| `POST` | `/admin/evaluation-datasets` | Новый датасет | `{ name, version, description? }` | `EvaluationDataset` |
| `POST` | `/admin/evaluation-datasets/:id/cases` | Добавить кейсы (батчем) | `{ cases: [{input, expectedOutput?, caseType}] }` | `EvaluationCase[]` |
| `POST` | `/admin/prompts/:id/evaluate` | Запустить прогон — **только для `caseType: classification/structural`**, не для калибровки (§4.3, отдельный механизм) | `{ evaluationDatasetId }` | `EvaluationRun` (со статусом `RUNNING`, опрашивается через `GET`) |
| `GET` | `/admin/evaluation-runs/:id` | Статус + агрегированные метрики + список провалившихся кейсов | — | `EvaluationRun & { results: EvaluationResult[], failedCases: EvaluationCaseResult[] }` |
| `POST` | `/admin/prompts/:id/promote-to-active` | `testing → active`, **только если** последний `EvaluationRun` для этой версии имеет `ReleaseGate.passed = true` — иначе `403` с указанием, какой конкретно порог не пройден | — | `PromptVersion` |

`promote-to-active` — единственная операция, физически создающая `PromptVersionStatus.ACTIVE`.
Прямой `PATCH status: active` не предусмотрен нигде в контракте — намеренно, чтобы гарантировать,
что в системе не может появиться активная версия в обход gate (implementation-ready.md §7,
правило 4: «каждая новая... версия проходит evaluation gate... прежде чем заменить текущую
активную»).

### 5.3 Calibration gate (§4.3, отдельный от остальных)

| Метод | Путь | Описание | Ответ |
|---|---|---|---|
| `GET` | `/admin/calibration/scenario-predictions` | Текущий Brier score, размер выборки, статус относительно порога | `{ sampleSize, brierScore, threshold: 30, gatePassed: boolean }` |

Без `POST` **для оператора** — ручной запуск от Telegram-администратора не предусмотрен, это
отражает саму природу метрики (нельзя «прогнать оценку» на ещё не случившихся исходах).

**АУДИТ (полный проход по коду) — уточнение, не отменяет предыдущий абзац:** "без POST" здесь
касается только admin-facing управления, не механизма самого планового пересчёта. Реально
существует `POST /internal/calibration/recompute` (`CalibrationDispatchController`) — именно
этот эндпоинт `pg_cron` реально вызывает по HTTP (Supabase не может вызвать TypeScript-функцию
напрямую), защищён сверкой заголовка `X-Dispatch-Secret` с секретом
(`SCHEDULER_DISPATCH_SECRET`, тот же секрет, что уже использует `SchedulerDispatchController`
для других плановых задач в проекте, не заведён отдельный ради одной новой задачи). Первая
версия этого раздела не упоминала этот эндпоинт вообще — не потому что его не должно быть, а
потому что раздел был написан до того, как встал вопрос "как именно pg_cron физически
дотягивается до кода", а инфраструктурный ответ на этот вопрос (HTTP dispatch endpoint,
не прямой вызов) появился при реализации.

## 6. Acceptance-тесты (Given/When/Then)

### 6.1 Registry — нельзя обойти gate

```
Given версия промпта в статусе testing
When вызывается POST /admin/prompts/:id/promote-to-active
     без предшествующего прогона evaluation для этой версии
Then запрос отклоняется (400, BadRequestException) — evaluation обязателен, не опционален
```

**АУДИТ (полный проход по коду после написания документа):** первоначальная формулировка этого
теста указывала (409). Реализация и написанный вместе с ней тест (`prompt-registry.service.
spec.ts`, «promoteToActive отклоняется без EvaluationRun вообще») согласованы между собой и
используют `BadRequestException` (400) — запрос буквально некорректен на данном этапе жизненного
цикла версии (нет предпосылки для запрошенного действия), не конфликт с параллельным изменением
состояния, для которого 409 был бы точнее. Формулировка теста здесь приведена в соответствие с
уже реализованным и протестированным поведением, не наоборот.

```
Given версия промпта прошла evaluation, ReleaseGate.passed = false
When вызывается POST /admin/prompts/:id/promote-to-active
Then запрос отклоняется (403), в ответе — конкретная непройденная метрика и её значение,
     не общее "провалено"
```

### 6.2 Классификационный gate (§4.1)

```
Given датасет с 40 размеченными кейсами для discrepancy-детектора,
      из них 3 кейса с меткой strong_discrepancy размечены НЕВЕРНО детектором
      (ложное срабатывание на кейсах без реального расхождения)
When завершается EvaluationRun
Then false_positive_rate для категории strong_discrepancy считается точно по этим 3 кейсам,
     если результат > 0.05 — ReleaseGate.passed = false
```

### 6.3 Структурный gate (§4.2)

```
Given датасет из 10 сценариев для анализа мотивов
      AI сгенерировал по 2 гипотезы на сценарий (20 гипотез всего),
      у одной гипотезы alternativeExplanation пустой
When завершается EvaluationRun
Then alternative_explanation_completeness = 19/20 = 0.95, порог 100% не пройден,
     EvaluationCaseResult для этого кейса содержит note с указанием,
     у какой именно гипотезы отсутствует поле
```

### 6.4 Калибровочный gate (§4.3)

```
Given накоплено 25 записей Prediction с заполненным фактическим исходом
When запрашивается GET /admin/calibration/scenario-predictions
Then gatePassed = false, sampleSize = 25 — явно меньше порога 30,
     calibratedProbability продолжает работать в uncalibrated-режиме,
     сама фича прогнозов не блокируется
```

```
Given накоплено 30+ записей Prediction с исходом, Brier score посчитан
When новая запись Prediction получает фактический исход
Then калибровочная статистика пересчитывается плановым заданием (не синхронно на каждую запись —
     та же экономия, что уже применяется к другим агрегатам в проекте)
```

## 7. Что сознательно не входит в эту ревизию

- **Скользящее окно для калибровочной статистики** (§4.3) — реализация берёт всю накопленную
  историю `Prediction`/`OutcomeScenario` без временной фильтрации; конкретный размер окна (30
  дней? 90? количество записей вместо времени?) не зафиксирован ни здесь, ни в
  implementation-ready.md — добавление окна без конкретного, обоснованного числа было бы
  гаданием, не переносом уже принятого решения.
- **Точные пороги для `precision`/`recall`** (только `false_positive_rate` зафиксирован явно
  требованием implementation-ready.md) — калибруются по факту первого реального прогона на
  реальных данных проекта, не как гипотетические цифры здесь.
- **UI для управления промптами и датасетами** — эта ревизия описывает только API-контракт
  (admin-facing, как и весь §2.10 implementation-ready.md); экран/страница — отдельная задача,
  синхронизированная с фактической потребностью (сейчас записи можно создавать через сам API
  напрямую, без UI).
- **Human-in-the-loop разметка датасетов** (интерфейс для ручной разметки транскриптов при
  создании `EvaluationCase`) — датасет создаётся через `POST` с уже готовыми кейсами, откуда
  берутся сами размеченные примеры (ручная разметка, экспорт из реальных разговоров с согласия
  пользователей и т.д.) — вопрос следующего прохода, не блокирует эту ревизию.
- **AI-as-judge оценка для генеративных задач без структурной проверки** (например — оценка
  качества сгенерированного аргумента, не сводящаяся ни к классификации, ни к проверке
  структуры) — намеренно не входит: три обязательных gate этой ревизии не требуют такого
  механизма, изобретать его заранее без конкретного потребителя — гадание.
- **Автоматический периодический ре-прогон активных версий** (защита от regression при смене
  модели-провайдера) — полезно, но отдельная фича поверх уже описанного здесь фундамента,
  не первый необходимый слой.
