# Devil's Advocate — запуск всего проекта в Docker (с дев-входами)

Полный локальный стенд: Postgres + Adminer + `apps/api` + `apps/tma` +
`apps/admin` + `apps/landing`, четыре приложения в контейнерах, вход
без настоящего Telegram-бота.

---

## 1. Быстрый старт

Нужен только Docker (Desktop на macOS/Windows, Engine + плагин
`docker compose` на Linux). Node на хосте для запуска стенда **не
требуется** — всё ставится внутри образов.

```bash
make up            # или: npm run docker:up
```

Первая сборка — несколько минут (`npm ci` дважды: один раз для образа
api вместе с движками Prisma, один — общий слой для трёх Next-образов;
`ARG APP_DIR` объявлен после установки зависимостей именно ради этого
общего кеша). Дальше — секунды: слои закешированы.

Что открывать:

| Адрес                   | Что это           | Как войти                                              |
| ----------------------- | ----------------- | ------------------------------------------------------ |
| http://localhost:3001   | TMA (Mini App)    | автоматически, заголовком `X-Dev-User-Id: 123`         |
| http://localhost:3002   | Админ-панель      | кнопка «Войти как dev-123» на `/login`                 |
| http://localhost:3003   | Лендинг           | вход не нужен                                          |
| http://localhost:3000   | API               | напрямую curl'ом, см. §4                               |
| http://localhost:8080   | Adminer (БД)      | сервер `postgres`, логин/пароль/база `devils_advocate` |

Остановить — `make down` (данные БД сохраняются), полностью пересоздать
БД — `make reset`.

### Ключи внешних API

Стенд поднимается **без единого ключа**. Пустой ключ — не ошибка: сервис,
которому он не задан, честно откажет на своём эндпоинте, а не уронит
запуск API. Когда понадобятся — `.env.docker` (создаётся автоматически
из `.env.docker.example` при первом `make up`), затем `make up` ещё раз.

## 2. Что именно происходит при `make up`

```
postgres ──(healthcheck: pg_isready)──▶ api-init ──(отработал успешно)──▶ api
                                            │                             ▲
                                            │  prisma db push             │
                                            │  seed.ts (справочники)      │
                                            │  seed-dev.ts (dev-юзер)     │
                                            ▼                             │
                                        завершается            tma / admin / landing
```

**`api-init` — отдельный одноразовый контейнер, а не первые строчки в
команде запуска API.** Причина практическая: `api` в дев-режиме
перезапускается от каждой правки кода, и схема с сидами прогонялись бы
заново по десять раз за час. `depends_on: service_completed_successfully`
— единственная конструкция, где инициализация выполняется ровно один раз
и её провал честно останавливает запуск, а не превращается в API,
работающий на пустой БД.

Образ у `api` и `api-init` **один и тот же** — значит и сгенерированный
Prisma-клиент один и тот же. Два разных образа рано или поздно разъехались
бы по версии схемы, причём молча.

### `prisma db push`, а не `migrate deploy` — и что это значит

Папки `apps/api/prisma/migrations` в репозитории нет вообще: есть
`schema.prisma`, `seed.ts` и `manual-migrations/` с SQL, который
применяется руками. `prisma migrate deploy` без единой миграции ничего
бы не создал, и API стартовал бы на пустой базе.

Отсюда прямое ограничение, которое стоит держать в голове: **локальный
стенд не проверяет миграционный путь.** Порядок миграций, обратимость,
поведение данных при `ALTER` — всё это здесь не воспроизводится. Для
дев-стенда это приемлемо; для продакшна — нет, там по-прежнему нужен
нормальный `prisma migrate` (см. `VERCEL.md`).

Файлы из `prisma/manual-migrations/` стенд **не применяет**:
`intake_session.sql` и `schema_audit_2026_08_30.sql` — эквиваленты того,
что `db push` и так делает из схемы, а `pg_cron_*.sql` требуют расширений
`pg_cron`/`pg_net`, которых в образе `postgres:16-alpine` нет. Практическое
следствие: **фоновые задания в стенде не работают** — напоминания
планировщика, автоматический перевод брошенных intake-сессий в
`ABANDONED`, калибровка. Дёргаются вручную (см. §4).

## 3. Дев-входы: как устроены и где границы

В проекте два разных механизма аутентификации, поэтому и дев-входа два.

### 3.1 TMA — заголовок `X-Dev-User-Id`

Существовал до этого стенда (`TelegramAuthGuard.tryDevBypass`).
Включается `ALLOW_DEV_AUTH=true` на бэкенде; фронтенд подставляет
заголовок сам, когда `window.Telegram` недоступен, то есть при открытии
в обычном браузере. `telegramId` получает префикс `dev-` — в БД сразу
видно, что запись тестовая, и пересечься с настоящим Telegram ID она не
может.

### 3.2 Админка — `POST /admin/auth/dev-login`

Добавлено для этого стенда. Не «для удобства»: **Telegram Login Widget
физически не работает на `http://localhost`** — Telegram привязывает
виджет к домену, который задаётся боту через `@BotFather /setdomain`, и
`localhost` туда не принимается. Без dev-входа админка в локальном
стенде недоступна в принципе, сколько переменных ни настраивай.

Что делает эндпоинт: создаёт (или дополняет) пользователя `dev-<id>`,
выставляет ему **все три флага доступа** — `isOperator`,
`isLibraryModerator`, `isVenueModerator` — и выдаёт обычную `AdminSession`
в той же `httpOnly` cookie, с тем же TTL 7 дней, что и настоящий вход.

Три флага сразу — не «так проще»: админка состоит из вкладок, каждая под
своим флагом, и вход без них показывал бы четыре одинаковых экрана «нет
доступа». Проверку флагов это не ослабляет — сервисы проверяют их как
обычно, просто у dev-пользователя они по-настоящему выставлены в БД.

`devUserId` по умолчанию `123` — тот же, что у TMA. То есть админка и
TMA работают под **одним** пользователем, и сценарий «создал проект в
TMA → нашёл его в модерации» проверяется целиком, а не наполовину.

### 3.3 Что дев-вход НЕ обходит

Границы заданы намеренно и покрыты тестами
(`src/__tests__/admin-dev-login.spec.ts`):

- **Два независимых предохранителя.** Эндпоинт работает только при
  `ALLOW_DEV_AUTH=true` **и** `NODE_ENV !== 'production'`. Одной
  случайно утёкшей в прод переменной недостаточно: на Vercel/в любом
  проде `NODE_ENV=production` выставляется платформой, и вход остаётся
  закрытым. Проверка строже, чем у TMA-bypass, ровно потому, что здесь
  на кону права оператора.
- **Ответ 404, а не 403.** Наружу эндпоинт не должен выглядеть
  существующим: 403 подтвердил бы сканеру, что механизм в сборке есть.
- **`isBlocked` уважается.** Dev-вход обходит Telegram, а не блокировки.
  Иначе локальная проверка сценария «оператор заблокировал аккаунт»
  давала бы неверный результат.
- **Сессия обычная, 7 дней.** Не «вечная дев-сессия» — иначе стенд
  проверял бы не тот механизм, который поедет в прод.
- **Кнопка в UI скрыта отдельным флагом** `NEXT_PUBLIC_ALLOW_DEV_AUTH`,
  но сам по себе он ничего не открывает: решает бэкенд.

Согласия (§7.2 ТЗ) dev-сид **не выдаёт** по умолчанию — consent-гейты
часть продукта, их стоит хотя бы раз пройти руками. Кому нужно
пропустить: `SEED_DEV_CONSENTS=true` в `.env.docker`.

## 4. Повседневные команды

```bash
make logs                 # хвост логов всех сервисов
make ps                   # статус контейнеров
make restart              # перезапустить только api
make psql                 # psql внутри контейнера postgres
make shell-api            # bash внутри контейнера api
make seed-dev             # перезапустить dev-сид
make test                 # тесты apps/api в контейнере
make reset                # снести том с БД и поднять заново
```

Правки кода подхватываются без пересборки: исходники смонтированы с
хоста, `nest start --watch` и `next dev` перезапускаются сами.

Что требует большего:

| Что изменили | Что запускать | Почему |
| --- | --- | --- |
| код (`.ts`, `.tsx`) | ничего | watch перезапускает сам |
| `prisma/seed*.ts` | `make seed-dev` или `make up` | сиды выполняет одноразовый `api-init` |
| **`schema.prisma`** | **`make up`** (не `make restart`) | Prisma Client генерируется при сборке образа, а `db push` в entrypoint идёт с `--skip-generate`. Без пересборки БД уедет вперёд, а клиент останется старым — падать будет уже в рантайме невнятной ошибкой Prisma |
| `package.json` (зависимости) | **`make reset`** | анонимные тома `node_modules` переносятся на новый контейнер при пересоздании, то есть `make up` их не обновит. `down -v` — единственный способ их выбросить |
| Dockerfile, compose | `make up` | пересборка образа |

Проверить, что API жив (публичный эндпоинт, авторизация не нужна):

```bash
curl -s http://localhost:3000/healthz | jq
# {"success":true,"data":{"status":"ok","startedAt":"…","uptimeSeconds":12}}
```

Запрос к API напрямую — тем же заголовком, что использует TMA:

```bash
curl -s http://localhost:3000/projects -H 'X-Dev-User-Id: 123' | jq
```

Эндпоинты, которые в проде дёргает `pg_cron` (в стенде его нет):

```bash
curl -s -X POST http://localhost:3000/intake/abandon-stale \
  -H "x-dispatch-secret: dev-dispatch-secret"
```

## 5. Чего стенд не даёт

Названо прямо, чтобы не искать симптомы вслепую:

1. **Вебхуки не доходят.** Транскрибация (AssemblyAI) устроена на
   вебхуке: провайдер должен сам постучаться в наш API. До `localhost`
   он не достучится. Нужен туннель (`ngrok http 3000`, `cloudflared`) и
   его https-адрес в `API_PUBLIC_BASE_URL` — тогда сквозной разбор
   аудио заработает и локально. Без этого разговор останется в статусе
   `TRANSCRIBING` навсегда — это не баг стенда.
2. **Настоящий Telegram-вход не проверяется.** Ни initData, ни Login
   Widget: и то и другое требует реального бота с настроенным доменом.
   Дев-входы проверяют всё, что *после* аутентификации, но не саму
   подпись. Её покрывают юнит-тесты
   (`telegram-init-data.spec.ts`, `telegram-login-widget.spec.ts`).
3. **Фоновые задания не выполняются** — нет `pg_cron` (см. §2).
4. **Миграционный путь не воспроизводится** — `db push` (см. §2).
5. **CORS проверяется не тот, что в проде.** В dev
   (`NODE_ENV != production`) API отражает любой Origin; в проде список
   доменов обязателен и задаётся `CORS_ORIGIN`. Различие намеренное —
   см. комментарий в `src/create-app.ts`.

## 6. Если что-то не поднялось

**`port is already allocated`** (или **`container name is already in
use`**) — почти всегда одновременно запущен базовый
`docker-compose.yml` (он тоже публикует Postgres на 5432) или на хосте
свой Postgres. Имена контейнеров у стендов разные (`devils-advocate-*`
против `devils-advocate-dev-*`), поэтому первым сработает именно
конфликт порта — но если базовый стенд поднимали давно, встретиться
может любое из двух сообщений. `docker compose down` в обоих файлах, затем
`make up`. Порт совпадает намеренно: одни и те же `DATABASE_URL` из
`apps/api/.env.example` работают в обоих режимах.

**`api-init` упал** — `make logs` покажет, на каком шаге. Чаще всего
это ошибка в `schema.prisma`: `db push` не умеет всего, что умеют
миграции (например, переименование колонки с данными). `make reset`
пересоздаёт том с нуля и обычно закрывает вопрос.

**Админка отвечает 404 на dev-вход** — на стороне `api` не выставлены
`ALLOW_DEV_AUTH=true` и `NODE_ENV=development` одновременно. Проверить:
`make shell-api`, затем `env | grep -E 'ALLOW_DEV_AUTH|NODE_ENV'`.

**Изменения кода не подхватываются** — правка в `package.json`
(зависимости) требует пересборки: `make up`.

**Всё стало странным после смены ветки** — `make reset`.

**На Linux в репозитории появились файлы, принадлежащие root** —
контейнеры работают от root, а исходники смонтированы с хоста, поэтому
созданное внутри (`next-env.d.ts`, `apps/api/dist/`) получает владельца
root. Файлы безвредны и попадают под `.gitignore`; если мешают —
`sudo chown -R "$USER" .` либо задайте `user: "${UID}:${GID}"` сервисам
в `docker-compose.dev.yml` (на macOS/Windows проблемы нет вовсе).

## 7. Файлы стенда

| Файл                        | Роль                                                       |
| --------------------------- | ---------------------------------------------------------- |
| `docker-compose.dev.yml`    | весь стенд: 7 сервисов                                     |
| `docker/api.Dockerfile`     | образ `apps/api` (он же для `api-init`)                    |
| `docker/next.Dockerfile`    | один образ на три Next-приложения, выбор через `APP_DIR`   |
| `docker/entrypoint-api.sh`  | ожидание БД → `db push` → сиды                             |
| `.env.docker.example`       | шаблон переменных (копируется в `.env.docker` автоматически) |
| `Makefile`                  | короткие команды поверх трёх обязательных флагов compose   |
| `.dockerignore`             | что не попадает в build-контекст                           |
| `docker-compose.yml`        | **не тронут** — только Postgres + Adminer, для запуска приложений на хосте |
