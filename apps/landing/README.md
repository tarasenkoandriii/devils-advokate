# apps/landing — маркетинговый лендинг

Next.js 14 App Router, статическая генерация, i18n на **en/uk/ru** (минимум по `docs/devils-advocate-landing-tz.md`, §4), деплой на Vercel Hobby.

## ⚠️ Известное расхождение hero-композиции с брифом

Hero теперь собран из четырёх иллюстраций: три «прилипающие» к углам вьюпорта на весь скролл лендинга (`hero-slogan.png`, `hero-hell.png`, `hero-lawyer.png` — `position: fixed`, скрыты на мобильных, см. `Hero.tsx`) и вернувшаяся courtroom-иллюстрация (`hero-courtroom.png`), позиционированная справа от текста в самой hero-секции, с 6 переведёнными callout-карточками под ней (полный перевод `devils-advocate-hero-courtroom-front-phone-en.json` на en/uk/ru — см. `Dictionary.courtroomCallouts`/`phoneMockup`/`bottomFeatures` в `dictionary.ts`).

Ни цикл Prepare→Practice→Talk→Review→Learn из `docs/devils-advocate-hero-brief.md`, ни исключение религиозного контента из раздела 3.5 landing-ТЗ эта композиция не соблюдает — решение реализовать её тем не менее принято по прямому повторному запросу (архив с courtroom-иллюстрацией и текстом загружался дважды). **Два конкретных callout'а описывают функциональность, которой в MVP v1 физически нет**: «live-анализ речи» (hero-001/002) и «детекция лжи» (hero-007/008) — в продукте нет real-time обработки аудио вообще. Используются как есть, не переписаны втихую — прямо помечено в `Hero.tsx` и здесь.

`phoneMockup` и `bottomFeatures` в словаре — полный перевод оставшихся 40 биндингов из JSON (детальные подписи телефонного мокапа и нижней feature-полосы), переведены на все три языка, но **пока не подключены ни к одной секции** — честно: переведено про запас по прямому запросу «сгенерировать словари для всех языков», не выдумана секция под них наспех.

## Структура

- `src/middleware.ts` — геодетекция (по заголовку Vercel `x-vercel-ip-country`, с fallback на `Accept-Language`, затем на `en`) + редирект на `/{locale}` — тот же паттерн, что уже отработан в BTW/Volia
- `src/app/[lang]/layout.tsx` — эффективный root layout (html/body здесь, не в `app/layout.tsx` — см. комментарий в файле), метаданные, hreflang, шрифты (Unbounded для дисплея с кириллицей — уже устоявшийся выбор в других проектах вместо Space Grotesk, Inter для текста)
- `src/app/[lang]/page.tsx` — сборка всех секций
- `src/app/robots.ts`, `src/app/sitemap.ts` — через Next.js Metadata API, все локали
- `src/lib/i18n/` — `config.ts` (список локалей), `dictionary.ts` (тип), `dictionaries/{en,uk,ru}.ts` (контент), `get-dictionary.ts` (загрузчик)
- `src/components/` — по одной секции на компонент: `Hero` (courtroom-иллюстрация справа от текста + 6 callout-карточек ниже + 3 sticky-иллюстрации, закреплённые за углами на весь скролл), `LanguageSwitcher` (выпадающий список с флагами — клиентский компонент), `CycleSteps` (5 шагов, §3.2 ТЗ), `Differentiation` (§3.3), `PrivacySection` (§3.4 — отдельный полноэкранный блок, не мелкий шрифт внизу), `Features` (3 фичи, §3.5), `HowItWorks` (§3.6), `FAQ` (§3.7, нативный `<details>`, без JS), `FinalCTA` (§3.8), `Footer` (§3.9)

## Секция Technology ("не фрагментировано, не забыто") — текст наложен поверх картинки

Текст размещён **поверх изображения**, привязан к позиции каждой пиктограммы — вертикально по центру плашки, с отступом справа от иконки. Иконки уже нарисованы в самой картинке (`technology.png`) — не дублируются отдельно.

**Координаты сняты вручную с изображения, дважды.** Первый проход опирался на версию картинки БЕЗ текста — координаты центрировались по пику яркости самой ИКОНКИ, а иконка сидит ближе к верху плашки, не в её истинном центре. Результат — весь текст визуально "плыл вверх" (замечено пользователем). **Второй проход** — по референсу с реальным текстом (`file_000000005fa48243bbc83875cb184691.png`): координаты пересчитаны через суммарную яркость ПО ВСЕЙ ШИРИНЕ плашки (включая видимый текст референса), что даёт истинный центр плашки. Разница между версиями доходила до 34px. Заодно увеличен горизонтальный отступ правой колонки от иконки (79.5% вместо 77.5%) — по прямому уточнению.

**Экран телефона на самом лендинге — перенесён растром из референса, не HTML.** Содержимое экрана из референса (программно найдены точные границы бок-в-бок, разница между референсом и рабочей картинкой — 0-1px) вырезано и вставлено в `technology.png` поверх прежнего упрощённого экрана — переводить там всё равно почти нечего, только "Devil's Advocate" (имя бренда) и таймстемпы (числа).

**`PhoneMockup.tsx` доведён до состояния референса отдельным проходом** — не удалён и не заброшен, приведён в порядок по прямой просьбе ("позже использовать для генерации live-экрана приложения"). Первая версия сломалась в рендере — классическая CSS-ловушка: проценты в `padding` считаются от **ширины** containing block, даже для `padding-top`/`padding-bottom`, никогда от высоты. При узком высоком боксе телефона (~172×383px в типичном рендере) это схлопнуло всю вертикальную раскладку в кашу. **Исправление** — `flex: N 0 0%` (flex-grow с обнулённым flex-basis) вместо `padding: X%`: flex-basis в процентах внутри `flex-direction: column` — единственное место, где процент действительно считается от высоты (это его прямое назначение, main-axis sizing), не от ширины. Пропорции секций (3/9/8/35/25/20, сумма 100) сняты с реальных пиксельных замеров экрана на референсе, не взяты на глаз.

Заодно иконки-заглушки (плоские квадраты/круги) заменены на настоящий inline SVG — щит, треугольник-восклицание, лампочка, прицел, микрофон, документ, флаг — минимальный line-style, подобранный визуально по референсу. Компонент **не подключён обратно** в основную композицию `Technology.tsx` (там используется растровый composite — решение из предыдущего прохода не пересматривалось), но самостоятельно проверен рендером (сравнение side-by-side с референсом) на широком вьюпорте (на узком — скрыт тем же `@media (max-width: 900px)` правилом, что и остальной оверлей).

**Честно про оставшееся расхождение**: на референсе чек-лист "Current agenda" — двухколоночный (пустые кружки слева + статус-индикаторы справа), назначение этого паттерна неочевидно даже глядя на референс напрямую (может быть декоративным элементом композиции, не осмысленным UI). Реализован однокол��ночный список с разными состояниями (`checked`/`selected`/`empty`) — более пригодная основа для будущего реального экрана с настоящими данными чек-листа, чем воспроизведение неоднозначного декоративного паттерна.

**Реальная проблема нижней строки, найденная и исправленная только рендером**: первая версия `maxWidth` (15%) была шире реального промежутка между иконками (местами всего 11.8%) — на русском/украинском «Надёжное шифрование»/«Надійне шифрування» упиралось в соседнюю плашку. Исправлено сужением `maxWidth` до 10.5% — текст переносится на вторую строку вместо наезда на соседа. Также найдено и исправлено: телефон в референсе показывает **4 строки, не 5** — прежняя версия пыталась впихнуть 5-й пункт (`risk_05`/"Case record"), которого физически нет на картинке. Текстовая группа `center_phone_risks` (индекс 1 в `dict.technology.groups`) вообще перестала рендериться как оверлей — на референсе выяснилось, что на самом телефоне нет текстовых подписей вообще, только таймстемпы; смысл каждой строки передаётся исключительно через левую/правую колонки callout'ов. Данные остаются в словаре (переведены на 3 языка), просто не выводятся на экран.

На мобильных (<900px) весь текстовый оверлей и телефон скрыты целиком — 23 фрагмента текста поверх сжатой картинки на экране 375px стали бы нечитаемым шумом.

**Осознанное упрощение**: поле `tag` в правой колонке словаря (например, «Personal record», «Public source» — теги из `we_are_not_en.json`) в overlay не рендерится вообще. Данные остаются в словаре (переведены на все 3 языка), но добавление третьей строки текста в и так плотный блок title+description увеличило бы риск перекрытия, найденный и исправленный выше для нижней строки — решил не рисковать тем же багом ради второстепенного поля.

## Секция Privacy Policy (иллюстрированная, последняя секция лендинга)

Отдельная от короткой `PrivacySection` (§3.4 ТЗ, 3 пункта раньше на странице, ссылка "Read the full Privacy Policy" никуда не вела) — эта секция полнее, стоит последней перед футером, по прямому запросу.

**Впервые из всех присланных активов — точные координаты пришли готовыми.** `privacy_policy_en.json` даёт `anchor: {x, y}` (доли от размера картинки) для каждого пункта — не пришлось вычислять вручную через PIL/scipy, как для `technology.png`. Реальная работа здесь была не в поиске координат, а в:

1. **Честной проверке заявленного количества.** JSON утверждает "pictogram_entries: 39" в поле аудита, но сам список содержит 48 пунктов в 9 группах. Разница — `bottom_capture_analysis` (5) и `bottom_guidance_review` (4) — проверено обрезкой области их `anchor` (y≈0.775): там нет ни одной видимой пиктограммы, только хвост центральной композиции. 39 = 48 − 9, ровно как заявлено в поле аудита. Эти 9 не переведены и не рендерятся — нечего привязывать без иконки.
2. **Направление подписи не универсальное.** В отличие от `Technology.tsx` (все подписи вправо/компактной строкой), здесь картинка организована по-разному: колонки слева/справа, ряд сверху, ряд снизу, 8 узлов по кругу вокруг телефона в центре — для каждой группы выбрано направление (`right`/`left`/`above`/`below`), при котором текст уходит от соседних элементов, не на них.
3. **Массовые наложения в первой версии, найденные и исправленные только рендером.** Полный title+description на всех 39 меток дал слипшийся текст почти везде — центральный круг, обе правые колонки (шаг между иконками ~63-69px), особенно `right_sources_trust` (4 пункта в полосе ~50-68px). Исправление в две стадии: (а) все группы переведены в компактный режим (только заголовок, без описания — тот же урок, что уже был на `technology.png`); (б) для `right_sources_trust`, где даже сокращённый текст ("Publicly Available Source" → "Public Source" и т.д. по всем 3 языкам) продолжал слипаться при одинаковом направлении — добавлено шахматное чередование `above`/`below`, у соседних подписей теперь разная высота.

**Второй проход по стилю — по референсу с реальным текстом** (`file_000000008f7c81f484f2b80d5dc39ec4.png`, тот же композиционный концепт, другой рендер с текстом на месте). Оттуда — три конкретных решения, не увиденных на "no text" версии: (1) заголовки ВСЕ ЗАГЛАВНЫЕ жирные, не обычный текст; (2) у центрального круга и нижней строки в референсе ЕСТЬ описание под заголовком, у левой и правой колонки — нет, только заголовок (не универсальное правило "всегда компактно" из первого прохода — под каждую группу свой формат); (3) нумерованные бейджи (1-8) на самих иконках центрального круга. Правая колонка в референсе — без подписей вовсе (пустые плашки), для неё по прямому указанию использованы уже переведённые из JSON подписи (Documents/Tables & Reports/...), оформленные в общем стиле, не выдуманные заново.

**Возврат description + бейджей вскрыл новые коллизии, тоже найденные и исправленные только повторным рендером:**
- Бейдж по единой формуле смещения для всех 8 узлов садился прямо на текст заголовка (например, "1" — в середину "PROTECTED ENVIRONMENT"). Исправлено: смещение бейджа задаётся ПРОТИВОПОЛОЖНО направлению текста лейбла (`badgeOffset` в `AnchorConfig`) — если текст уходит "above", бейдж смещается вбок, не вверх, и наоборот.
- Выросший на 1-2 строки блок (заголовок+описание) у групп с `showDesc: true` наезжал на саму иконку при прежнем маленьком отступе (10px, рассчитанном под однострочный заголовок). Добавлен отдельный CSS-модификатор `--with-desc` с большим отступом (38px вместо 12px) — не общее увеличение (это сломало бы компактные группы вроде `top_pipeline`, где просторнее не помещается).
- `central_home` (направление "above") и `pipeline_transcribe` ("SPEECH RECOGNITION", направление "below" сверху) целились в один и тот же узкий промежуток ~90px — с описанием `central_home` физически не помещался, наезжая на "SPEECH RECOGNITION". Исправлено сменой направления `central_home` на "below" (к центру композиции, где просторно — ~190px до телефона, только декоративные линии-соединители, не текст).
- Застарелая коллизия `pipeline_deliver`/`attachment_documents` в правом верхнем углу (существовала с первого прохода, не была замечена тогда) — сужен `maxWidth` (110→95px) и сдвинута X-координата `pipeline_deliver` (0.832→0.8).

На мобильных (<900px) все 39 меток и все 8 бейджей скрыты целиком — та же логика, что для `technology__overlay-item` и `.phone-mockup`.

**Левая колонка (`left_workflow`) дополнительно доувеличена по прямому запросу** — шрифт 11px → 15px, `maxWidth` пересчитан под реальный правый край плашки на рабочей картинке (не референс): сканирование яркости по строке нашло границу на x≈255px из 1536, текст стартует на x≈109px, доступно ≈146px, взято 144px с небольшим запасом до рамки. `AnchorConfig` получил необязательное поле `fontSize` — сейчас используется только здесь, остальные группы остаются на дефолтных 11px. Проверено рендером крупным планом именно этой колонки, не только общим планом секции — весь текст 1-2 строки, ничего не срезается о рамку плашки.

**Найдена и исправлена реальная ошибка привязки, не вопрос стиля**: на самой картинке в этой рамке РОВНО 5 иконок (щит-галочка / замок / человек / растущий график / глобус с листом), не 6 — обнаружено прямым просмотром колонки без наложенного текста, по прямому уточнению пользователя. Прежняя версия накладывала 6 лейблов из JSON (`workflow_prepare`…`workflow_privacy`) на эти 5 иконок — 6-й (`workflow_privacy`) либо садился поверх 5-й иконки, либо уезжал в пустой хвост рамки. `workflow_privacy` убран из `ANCHORS` (не рендерится — нет 6-й иконки, к которой его привязывать), данные в словаре не удалены — тот же паттерн, что уже применялся к `bottom_capture_analysis`/`bottom_guidance_review`. Текст остальных 5 пунктов заменён на формулировки из более раннего присланного референса с реальным текстом (тот же композиционный концепт, эти же 5 иконок уже были там подписаны: "PRIVACY FIRST / SECURE BY DEFAULT / YOU OWN YOUR DATA / FULL CONTROL AT ALL TIMES / RESPONSIBLE BY NATURE") — взяты оттуда буквально, не придуманы заново, переведены на все 3 языка. Группа переименована с "Workflow" на "Privacy Principles" — прежнее название описывало последовательность действий (Preparation→Live→Guidance→...), новое содержание — про ценности, не про процесс.

**Точное центрирование текста по центру иконки, не по центру всей строки** — по прямому уточнению. Первая версия Y-координат бралась из row-level детекции (суммарная яркость по всей ширине плашки, включая дефисную линию-разделитель и пустое пространство) — это даёт центр всей СТРОКИ, не обязательно центр самой ИКОНКИ внутри неё. Перемерено отдельно: узкая полоса сканирования по X=55-115px (только область, где рисуется графика иконки, не текст и не разделитель), порог 25% от максимума яркости. Расхождение со старыми координатами оказалось небольшим, но реальным (1-11px по разным иконкам) — из-за него текст визуально "не совпадал" с иконкой даже при формальном центрировании (`transform: translateY(-50%)` совершенно корректно центрирует блок текста на заданной Y-точке — проблема была в том, что сама точка была не совсем там, где нужно). Заодно шрифт уменьшен (15px → 13px) по прямому запросу.

**Вторая правка того же центрирования — по прямому визуальному замечанию пользователя**: "низ блока надписи оказался на уровне центра иконки", не середина блока. Проверено объективно, не на глаз: через `Playwright.bounding_box()` снята фактическая позиция отрендеренного блока на странице, наложена отладочная линия-маркер через PIL поверх скриншота на предполагаемый центр. Первая попытка отладки содержала собственную ошибку измерения (перепутаны координаты уровня страницы с координатами уже обрезанного по границам секции скриншота — `wrap.screenshot()` даёт собственный нулевой отсчёт, не совпадающий с `page`-координатами Playwright) — пересчитано правильно. После пересчёта подтвердилось: `transform: translateY(-50%)` математически центрирует блок ровно на заданную Y-точку корректно, но сама точка (порог 25% яркости) занижена мягким неоновым свечением под частью иконок, которое ярче/шире снизу, чем даёт кажущаяся граница графики — тянет расчётную нижнюю границу иконки вниз сильнее, чем нужно для истинного визуального центра. Скорректировано вручную сдвигом вверх на ≈0.012 (≈12px из 1024) для всех 5 пунктов, шрифт дополнительно уменьшен (13px → 12px).

**Третья правка — точный пиксельный сдвиг по прямому запросу** (ниже на 30px, левее на 10px, шрифт ещё меньше — 12px → 10px). `AnchorConfig` получил `offsetX`/`offsetY` — применяются через `margin-left`/`margin-top` в инлайн-стиле ПОВЕРХ уже существующего позиционирования (`left`/`top` в % + `transform`), не заменяя его: X/Y-координаты в `ANCHORS` остаются точной привязкой к измеренному центру иконки, а `offsetX`/`offsetY` — независимый дополнительный сдвиг именно текстового блока, к которому можно возвращаться и корректировать отдельно, не пересчитывая заново позицию иконки.

**Четвёртая правка — `maxWidth` подобран так, чтобы все 5 текстов давали ровно 3 строки**, не на глаз. Прогнан перебор через Playwright: сетка ширин 55-100px с шагом 5px, затем уточнение по 1px в найденном промежутке — для каждой ширины измерялась фактическая высота отрендеренного `<span>` и делилась на `line-height`, чтобы точно знать реальное число строк для каждого из пяти разных по длине текстов одновременно (они не совпадают по количеству слов — "ПОЛНЫЙ КОНТРОЛЬ ВСЕГДА" против "ОТВЕТСТВЕННОСТЬ ПО СВОЕЙ ПРИРОДЕ"). Единственное значение, дающее `[3, 3, 3, 3, 3]` для всех сразу — **82px**: на 81px "ВАШИ ДАННЫЕ ПРИНАДЛЕЖАТ ВАМ" ещё давал 4 строки, на 83px "ПРИВАТНОСТЬ ПРЕЖДЕ ВСЕГО" уже схлопывался до 2.

**Пятая правка — шрифт чуть крупнее (10px → 11px), сдвиг правее на 25px** (`offsetX`: -10 → 15) по прямому запросу. Увеличение шрифта потребовало ПЕРЕСЧЁТА `maxWidth`, не механического переноса старого значения: при 11px буквы шире, та же ширина 82px вмещает меньше символов на строку — перебор для нового кегля дал уже `[3,3,4,3,3]` при 82px, не `[3,3,3,3,3]`. Прогнан тот же перебор Playwright заново для 11px — единственное значение снова с идеальным результатом по всем пяти строкам — **90px**. Проверено: текст (95px якорь + 14px паддинг + 15px offsetX + 90px maxWidth = 214px правый край) укладывается с запасом до реальной границы плашки на картинке (~255px), не вылезает.

**Шестая правка — шрифт чуть меньше (11px → 10.5px), сдвиг влево на 5px** (`offsetX`: 15 → 10), **3-й/4-й/5-й пункты дополнительно ниже на 20px** (`offsetY`: 30 → 50, только для `workflow_guidance`/`workflow_capture`/`workflow_review` — 1-й и 2-й остаются на 30px). Смена кегля снова потребовала пересчёта `maxWidth` тем же методом (Playwright-перебор, измерение реальной высоты рендера) — при 10.5px единственное значение с результатом `[3,3,3,3,3]` — **86px**. Это первая правка в этой серии, где сдвиг применяется НЕ ко всем пяти пунктам одинаково — `offsetY` теперь различается по пунктам, задаётся индивидуально в каждой записи `ANCHORS`, не общим правилом.

**Седьмая правка — сдвиг вправо на 5px** (`offsetX`: 10 → 15), **шрифт 10.5px → 10px**. Значение `maxWidth=82px` для 10px кегля уже было найдено ранее в этой же серии правок (третья правка) — не взято по памяти, перепроверено тем же Playwright-перебором заново, подтвердилось без изменений.

## Мобильная адаптация sticky-иллюстраций

На десктопе все три sticky-иллюстрации закреплены за углами вьюпорта на весь скролл (`position: fixed`). На мобильных (<768px) все три `fixed`-версии скрыты целиком — постоянно перекрывающие контент картинки на маленьком экране были бы реальной проблемой читаемости, не то же самое, что временно занимать угол одной hero-секции. Вместо этого, по прямому запросу: слоган показан один раз в начале документа (внутри hero, в потоке, не fixed), адвокат — один раз в самом конце документа, после футера (`MobileBottomIllustration.tsx`, подключён в `page.tsx`). Ад на мобильных не показывается вовсе — этого не просили вернуть.

## Дизайн-направление

Тёмная сдержанная база (не тёплый крем+терракота — явно проверено на клише из frontend-design skill), Unbounded/Inter, акцентная триада green/amber/red — перенесённый из самого продукта индикатор накала разговора (calm→rising→high→critical), используется как единственный сигнатурный элемент (тонкая линия-разделитель между секциями `.tension-divider`), не как декоративная заливка кнопок повсюду.

## Честно о проверке

`next build`/`tsc` не прогонялся — нет сети для установки зависимостей в среде разработки, как и во всех остальных `apps/*` этого монорепо. Сделано вручную: баланс скобок по каждому файлу, сверка каждого импорта с экспортом, побайтовое сравнение структуры ключей всех трёх словарей (`diff` имён ключей en/uk/ru — идентичны), поиск неиспользуемых полей в типе словаря (найдены и удалены два мёртвых поля — `footer.legalEntity` и `nav.openInTelegram`, которые были объявлены, но нигде не читались компонентами).

**Визуальная проверка** — статический анализ выше не ловит проблемы композиции/вёрстки. При добавлении sticky-иллюстраций + вернувшейся courtroom-картинки первая версия сажала 6 callout-карточек колонками ПО БОКАМ одной строки с текстом+картинкой — при стандартном контейнере 1120px тексту оставалось ~150px, и заголовок разваливался на слово-в-строку на каждом рендере. Статический анализ (баланс скобок, сверка импортов) в принципе не может поймать такую ошибку — только реальный рендер. Прогнан через headless Chromium (Playwright) при каждой правке: до/после скролла (проверка, что sticky-иллюстрации реально остаются на месте, не просто написано `position: fixed` в файле), desktop и mobile. Итоговая структура — callout'ы отдельной строкой ПОД текстом+картинкой, не конкурируют с ними за ширину. Тем не менее это статический HTML-макет разметки, не реальная Next.js-сборка — гидратация, `next/font`, реальные `next/image`-оптимизации всё ещё не проверены по-настоящему.
