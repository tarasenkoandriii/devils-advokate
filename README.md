# Devil's Advocate — монорепо

> Конфиденциально. Коммерческая ценность, не подлежит разглашению третьим лицам без согласия автора.

## Структура

```
devils-advocate/
├── apps/
│   ├── api/       ← MVP v1 готов: инфраструктурный чекпоинт (12 пунктов) + все 13 фич + Vercel-деплой
│   ├── tma/       ← MVP v1 готов: полный флоу от дисклеймера до Safe Share, Vercel-деплой настроен
│   ├── landing/   ← готово: маркетинговый лендинг, i18n en/uk/ru, Vercel-деплой настроен
│   └── admin/     ← готово: единая админ-панель (модерация библиотеки/заведений/пользователей, промпты, телеметрия), Telegram Login Widget + AdminSession cookie
├── docs/          ← все продуктовые/технические документы
├── docker-compose.yml  ← Postgres + Adminer для локальной разработки
└── VERCEL.md      ← инструкция по деплою на Vercel Hobby
```

**Четвёртый источник сверки §3.16 добавлен отдельным пунктом («Пункт 40»)**, после явного этического разбора: автономный AI-поиск по имени человека — это базовый механизм слежки за конкретным частным лицом вне зависимости от упаковки (сам роадмап ТЗ честно называет это отдельным пунктом v3, №21, «поиск прецедентов поведения фигуранта»). Решение — не автономный поиск, а ручная вставка ссылки пользователем: сервер скачивает ИМЕННО ЕЁ, не решает сам, что искать. Первая в проекте интеграция, скачивающая URL, введённый пользователем (не заранее настроенный админом endpoint) — потребовала отдельной SSRF-защиты (`safe-url-fetch.ts`: блокировка localhost/приватных RFC 1918 диапазонов/облачных метаданных по строке URL, честно задокументированное ограничение — без резолвинга DNS, не защита от DNS rebinding). Три исхода проверки (подтверждает/противоречит/недостаточно данных) — запись создаётся только при реальном противоречии. §3.16 ТЗ закрыт полностью — все четыре источника.

## Локальная разработка

Два режима. По смыслу они не конфликтуют, но **одновременно не запускаются** — оба публикуют Postgres на 5432.

### A. Весь проект в контейнерах — **[DOCKER.md](./DOCKER.md)**

```bash
make up      # или: npm run docker:up
```

Поднимает Postgres + Adminer + `apps/api` + `apps/tma` + `apps/admin` + `apps/landing`, накатывает схему, прогоняет сиды и создаёт dev-пользователя. Node на хосте не нужен; ключи внешних API не обязательны — стенд поднимается пустым и отказывает только на тех эндпоинтах, которым ключа не хватает, а не падает целиком.

Вход без настоящего Telegram-бота: TMA — автоматически (`X-Dev-User-Id`), админка — кнопкой «Войти как dev-123» на `/login`. Кнопка появилась не ради удобства: Telegram Login Widget физически не работает на `http://localhost` (домен виджета задаётся боту через `/setdomain`, localhost туда не принимается), без неё админка в локальном стенде недоступна в принципе. Dev-вход открыт только при `ALLOW_DEV_AUTH=true` **и** `NODE_ENV != production`, вне этого отвечает 404 и не обходит `isBlocked` — границы описаны в DOCKER.md §3 и покрыты тестами (`admin-dev-login.spec.ts`).

Чего стенд не даёт (прямо названо в DOCKER.md §5): вебхуки AssemblyAI до `localhost` не доходят без туннеля, `pg_cron`-задания не выполняются, миграционный путь не воспроизводится (`db push` без истории миграций), настоящая Telegram-подпись не проверяется.

### B. Только инфраструктура, приложения на хосте

Postgres + Adminer через Docker Compose — не нужно ставить Postgres на хост вручную:

```bash
docker compose up -d
```

Поднимет Postgres на `localhost:5432` (учётные данные уже совпадают с дефолтом `apps/api/.env.example`, ничего дополнительно менять не нужно) и Adminer на `http://localhost:8080` для просмотра БД. Приложения в этом режиме запускаются на хосте — это самый прямой путь к брейкпоинтам в IDE. Полностью контейнеризированный вариант с теми же удобствами (hot-reload через volume-мапинги) — режим A выше. `docker-compose.yml` — чисто дев-инструмент, Vercel (см. ниже) его не видит и не использует, у serverless-деплоя свой билд-пайплайн.
